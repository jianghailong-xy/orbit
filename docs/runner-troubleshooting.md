# Runner troubleshooting

Start with the first matching symptom below. Run runner commands as the OS account that enrolled
the machine, using the same `ORBIT_HOME` as its service. Use the command generated by **Add a runner**
for your deployment, and keep [CLI automation](runner-cli.md) and [self-hosting](self-hosting.md) nearby.

## Find the runner logs

`orbit status` reports registration, the configured server, and the heartbeat age; it also prints
private identifiers and paths, so sanitize it before sharing. On Linux, registration prints the
installed service name. Depending on whether the host broker is installed, it is
`orbit-runner@<uid>.service` or `orbit-runner-<user>.service`; older installs may use `orbit-runner.service`.
Use the name registration printed:

```bash
# Linux/systemd; replace the placeholder with the installed service name.
ORBIT_RUNNER_UNIT='<installed-service-name>'
systemctl status "$ORBIT_RUNNER_UNIT" --no-pager
journalctl -u "$ORBIT_RUNNER_UNIT" --since '10 minutes ago' --no-pager
```

On macOS/launchd, inspect the LaunchAgent and its local log:

```bash
# macOS only; substitute the service's ORBIT_HOME if it differs from ~/.orbit.
launchctl list com.orbit.runner
tail -n 100 ~/.orbit/runner.log
```

If registered with `--foreground`, inspect the terminal running `orbit run`. Do not start a second
runner process to diagnose an already-running service.

## A. Registration or enrollment does not finish

**Symptom:** the installer cannot reach the deployment, browser approval times out, or `orbit status`
says “no runner registered”.

1. Check the origin in the UI-generated install command. From the runner machine, verify the gateway
   and API independently (use your actual HTTPS origin; localhost only works on the deployment host):

   ```bash
   ORBIT_CHECK_ORIGIN='https://orbit.example.com'
   curl -fsS "$ORBIT_CHECK_ORIGIN/healthz"
   curl -fsS "$ORBIT_CHECK_ORIGIN/api/auth/setup-status"
   ```

   Expected: `ok` and an API response with `needsSetup: false` after administrator setup. A 502 or
   refusal means the operator should check TLS/DNS/proxy settings and `docker compose ps` plus recent
   API/gateway logs. `/healthz` alone only proves nginx is answering.
2. Confirm you signed into the intended Orbit deployment and account in the browser and approved the
   pending device before it expired. Expected: enrollment succeeds and a runner appears in that account.
   For an expired one-time token or approval, generate a fresh command in **Add a runner** and retry.
   Never reuse or post an enrollment token to diagnose this.
3. Run `orbit status` as the enrolling user, with the service's `ORBIT_HOME`. Expected: a runner and the
   intended server, not “no runner registered”. If the service failed to install, inspect its reported
   error; use `--foreground` for a terminal test after stopping any existing service. For an explicitly
   invalid/revoked credential, re-enroll with `orbit register --server "$ORBIT_CHECK_ORIGIN" --force`.
   Re-registration replaces the machine credential and restarts its installed service; coordinate it
   with anyone using the runner.

**Safe issue evidence:** OS/architecture, Orbit version/source SHA, which check failed, UTC timestamps,
HTTP status/error category, and sanitized enrollment/service errors. Redact the install command's
tokens, browser codes, cookies, full server URLs if private, account/runner IDs, and all config content.

## B. Enrolled runner stays offline or heartbeats stop

**Symptom:** registration succeeded, but the UI shows offline or the heartbeat age keeps increasing.

1. Run `orbit status` twice, separated by the normal heartbeat interval, and inspect the service/logs
   above. Expected: the service is running and the age stays recent as heartbeats advance. A successful
   registration alone does not start polling when `--no-service` was used. Start the installed service
   or run `orbit run` in the intended supervised terminal. Resolve a crash loop from its first error.
2. Run the two curl probes from branch A on the runner host. Expected: both routes answer through the
   configured origin. If the gateway works but API requests return 502, inspect API/container health.
   If both fail, check DNS, TLS certificates, firewall, and the service's proxy/network environment.
   Do not disable certificate verification as a permanent fix.
3. Inspect a short runner log window for heartbeat HTTP errors. Expected: no recurring 401, connection
   refusal, timeout, or TLS error. A 401 points to a revoked/wrong runner credential: verify the deployment
   in `orbit status`, then re-enroll through **Add a runner**. Timeouts require fixing connectivity;
   repeatedly re-registering will not repair them. Verify the service and shell use the same runner home.

**Safe issue evidence:** runner/runtime versions, heartbeat ages and UTC timestamps, service state,
HTTP status/error category, and sanitized runner/API log excerpts from the same time window. Redact
tokens, authentication headers, cookies, internal network addresses, identifiers, paths, and user data.

## C. Runner is online but a task cannot start its runtime

**Symptom:** a task reports a missing CLI, login failure, provider authentication error, or quota limit.

1. Run `orbit doctor` as the runner user. Expected: the **selected** runtime is installed with a version
   and is visible on the service PATH. The command offers installation/sign-in interactively; review
   its prompts. A zero exit code only proves at least one runtime is installed, not that the selected
   runtime is authenticated. Install the missing runtime using the command doctor prints.
2. Check authentication for the selected runtime using doctor's printed sign-in command or the UI's
   runner sign-in action. Expected: its own login flow succeeds for the service user. An `unknown`
   result is inconclusive; retry a harmless task. A shell export is not inherited by an already-running
   background service. For key-based authentication, update the service's private environment and
   restart the service without logging the key. Runtime login credentials belong on the runner.
3. If the CLI works in your shell but the task still says it is missing, compare the runtime location
   (`command -v <runtime>`) with doctor's service-PATH result and the service's OS user. Expected: both
   identify an accessible binary. Correct the service PATH/user, restart it, and retry one small task.
   For a configured endpoint, also check the account provider selection and its secret privately;
   [CLI provider precedence](runner-cli.md#self-hosted-endpoints-vllm) explains runtime settings overrides.
4. A provider quota/rate-limit error after successful authentication is a provider-availability failure.
   Expected next action: wait for the reported reset or select an authorized provider with available
   quota, then retry. Use the [first-run task check](first-run.md#5-complete-a-small-task) to verify success.

**Safe issue evidence:** selected runtime/provider type, runtime and Orbit versions, doctor status for
that runtime (installed/auth/service PATH), UTC timestamps, and sanitized error text. Redact API keys,
OAuth/device codes, tokens, cookies, credential files, private provider URLs, and repository contents.

## Before opening a public issue

Use the [support guide](../SUPPORT.md#useful-diagnostic-information) and bug-report form. Include the
branch followed, expected result, actual result, and next action already tried. Review each log line:
runner logs can contain task prompts, tool output, private source files, and credential-bearing URLs.
Never attach `.env`, `~/.orbit/config.json`, runtime login files, a browser network export, or an
unredacted transcript. Follow [SECURITY.md](../SECURITY.md) for suspected vulnerabilities.
