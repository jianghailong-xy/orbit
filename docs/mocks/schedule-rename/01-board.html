Rules, decisions, delivery

The scheduled-tasks design (§2) says “no surface has a field: changes are said”. Renaming is its one exception. Decided by the owner on 2026-11-26: D1 A, D2 B.

What a rename does

  • Changes title only. Intent, prompt, rule, access and envelope stay the same.
  • Trimmed, 1–200 characters (the limit schedule_update already has). Same text after trimming = no-op, no record.
  • Writes a ScheduleRevision (changedBy USER, before/after title) → History + Undo. Undo is the existing POST /schedules/:id/undo.
  • Inside the envelope by definition: no card, no Allow, applies at once.
  • Allowed in every state but ENDED (paused, held, running). A run in progress keeps the revision it started with; its session title does not change.
  • Owner channel and personal tokens with sessions:write, like Pause. An acting session uses schedule_update, as today.
  • Other devices update through the schedule's existing realtime event.

Decided (owner, 2026-11-26)

D1 · How does a rename reach the server?
A · A narrow REST door ✓ chosenPOST /api/schedules/:id/rename {title}: title only, beside pause/resume. The name is a label, not goal, risk, budget or authority, so §2's rule still holds for everything that is. The surface spec is updated to list it.
B · Keep it saidRename… opens the Change… conversation with “Rename it to: ” typed in. No new door, but every rename starts an engine and costs a turn.
D2 · May an agent rename it afterwards?
A · A person's name sticksOnce a person has named it, a run's schedule_update with a new title is refused (SCHEDULE_TITLE_SET_BY_OWNER). A session the person is talking in may still rename it, when asked. Undoing the rename lifts the hold.
B · No hold ✓ chosenAny change is recorded with Undo; an agent may rename it later, and History shows who did, with Undo.

Delivery (cheapest first)

  1. Server: the rename door (no migration), the revision record, the surface spec listing it. Shared copy for “Rename…”, “Renamed from …”.
  2. Web: Rename… in the row menu and inspector ⋯; the inspector title as a field (reuses the session-row rename field). Vitest.
  3. macOS + iOS: the menu item, the inline field on macOS and the alert on iOS; OrbitKit API call; History line.
  4. Android: the menu item and a dialog, following iOS.
  5. Docs: scheduled-tasks design §2, §8.4 and §9.1 name the exception.

Older clients need nothing: they read title as before, and a revision record they cannot name shows as a generic change.
