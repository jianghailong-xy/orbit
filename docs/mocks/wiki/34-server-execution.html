① 今天 vs 新方案

今天，每个 wiki 作业都是 runner 上的一个 agent 会话，用的是空间 pin 的 provider。新方案里，作业在服务端执行，模型统一走部署方配置的 System model，runner 只负责读仓库。

今天

事实到达 → 触发器在隐藏的「Wiki maintenance」列表里建一个任务
↓
runner 领取会话占 1 个并发槽位；plan 起草 1–2 小时，单次运行最长 5 小时
↓
外层 Claude Code（干净启动，最多 120 轮）它的模型只负责发一条 Bash：orbit wiki maintain
↓
Go 流水线（在 runner 上）每次模型调用都起一个 claude -p --bare；每个运行最多 4 个并发，没有全局上限
↓
空间 pin 的 provider用户自己的 key 或订阅；key 在 runner 的会话环境里
本地 checkoutgit 只在 runner 上跑
占 runner 槽位花用户额度key 在 runner 上 没有全局并发上限改流水线要发 runner

新方案

事实到达 → 触发器写一条作业 wiki_jobapiserver；仍由事实驱动，不用时钟
↓
wiki-worker 领取作业（带租约）新服务，Node.js，和 apiserver 同一个镜像；运行 TS 流水线，直接用服务端的数据和写入口
↓
每次模型调用都进队列 wiki_model_request调度器按全局并发 N 和优先级领取；请求同时就是断点
↓
System model（vLLM）部署方在 .env 里配置；key 只在 worker 上
runner 仓库操作心跳时领取，在会话池之外执行：快照、片段、diff、锚点
不占 runner 槽位不花用户额度key 只在 worker 全局限流、排队可见改流水线随服务端部署

③ 模型请求队列：全局并发上限由数据库保证

流水线不直接调用模型，每次调用都写一行请求，再等它完成。调度器按 ORBIT_WIKI_MODEL_CONCURRENCY（默认 4）领取，起几个 worker 进程都不会超过这个数。

queued→running→ succeeded/failed/cancelled
running— 租约过期 →queued（attempts + 1，带上 partial）
领取（在一个事务里）
  1. 先拿一把 advisory 锁，保证同一时刻只有一个调度器在领取
  2. 数出 running 且租约未过期的请求数 r
  3. 只领取 N − r 条：按 priority 降序、enqueued_at 升序，FOR UPDATE SKIP LOCKED，每行一个新代数
  4. 流式执行：定期写回 partial 并续租；结束时按代数比较并写入结果，再用 pg_notify 唤醒等待的作业
请求即断点
  1. (job, step, unit, attempt) 唯一：作业重放时，已成功且答案能解析的请求直接复用
  2. worker 收到 SIGTERM：停止领取，中止在途请求并保存 partial，把租约截止时间设为现在
模型状态（wiki_model_status）
  1. down：停止领取，每 10 秒探测一次 /health，恢复后自动继续
  2. auth_failed（401）：停止领取，等部署方改好 key、重启 worker

已定 · 1：部署时在途的模型请求怎么办

A：不等。worker 被重建时中止在途请求，带着 partial 回到队列里续写或重做。部署不变慢，但长调用（plan 骨架最长约 13 分钟）可能重做。

B：部署前先排空。worker 停止领取，等在途请求跑完再重建。部署最多多等一次调用的时间。

owner 2026-10-07 定：选 A。如果重做太多，再加 B。

已定 · 2：多个空间怎么分 GPU

A：优先级 + 先来先得 + 每个作业的并发上限。实现简单，排队顺序一眼能看懂。

B：同一优先级内按空间轮转。更公平，但领取 SQL 更复杂，排队位置也更难解释。

owner 2026-10-07 定：选 A。出现某个空间长期占满队列时，再加 B。

  • 1为什么 worker 单独成服务：几小时的流式调用和聚类计算不压在 API 进程上；模型 key 只给 worker；worker 停了，读、搜和人工编辑都不受影响。
  • 2为什么在数据库里限流：进程内的信号量只管得住一个进程，重启就丢；数据库里的队列在多进程下也不会超过 N，重启后接着跑，排队状态也能直接展示给用户。
  • 3为什么 runner 交快照：plan 起草要读约 27 MB 原文，而 API 请求体上限是 10 MB；真正进 prompt 的只有几万字。门检查、锚点和脚注核对都查快照，不用每次回 runner 问。
  • 4旧路径一直在：ORBIT_WIKI_EXECUTOR 默认是 runner；每条流水线先只对 canary 生效，和旧路径对照后再切；P10 才删除旧路径，在那之前随时可以回退。
