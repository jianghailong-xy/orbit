44 · 没有 git 也能维护 wiki：仓库分三档

2026-11-11 · 起因：一个 space 的工作目录不再是 git checkout，维护从 11-04 起停了 6 天，健康行只显示「behind」。 owner 已定：工作目录可以当事实来源。界面文字是英文（产品文案），注释是中文。

1今天：仓库是整次运行的闸门

wiki 的原料是服务端从会话里抽好的案卷，跟仓库无关；仓库只用来核锚点和写文档。 但运行的第一步是 git 快照，这一步一失败，后面全部不跑。

为什么没人发现

  • infra 失败不计入连续失败（design §5.5），所以健康行永远停在 behind，不会变成 failing；连续失败 3 次才发的通知也不会发。
  • readWikiRepoReadiness 只看 workspace、runner 在线、有没有能力，不看 work_dir_is_git（workspace 行上有这个字段）。
  • lastFailure 已经在 health 契约里，三个客户端都没画。
  • 恢复只能靠「下一个事实」来触发，owner 没有「立即再跑」的入口。

产品自相矛盾建得了，维护不了

  • 可以建「没有仓库的 wiki」（wiki.controller.ts:104），也可以手动加入没有仓库的 workspace（design §2.1）。
  • 开维护时只要求选一个 workspace（wiki-maintenance-settings.ts:83）。
  • 可这种 space 的每一次运行都会死在 rev-parse：等于永远维护不了。
  • git 只是工作目录的一种可能：项目文件夹、monorepo 的子目录、换了位置的 worktree、别的版本控制，都很常见。

2新：仓库按档位读，读不到就降一档，不再拦住整次运行

每次运行先让 runner 判断能读到哪一档，再用这一档能做的事。只有第 0 档的事是一定要做的，而第 0 档根本不读仓库。

还是只有一个 workspace

维护设置里选的那个 workspace 决定在哪台 runner、哪个目录读。档位是读的结果，不是一个设置：owner 修好目录，下一次运行自动回到第 2 档。

git 档不变

有 git 时仍然只读 origin/main（不读未提交的改动）：今天的信任模型、fetch 锁、根提交校验都不动。文件夹档只在不是 git 时启用。

第 0 档也有锚点可核

criterion、record、merge_evidence 锚点本来就在服务端核，不需要仓库，第 0 档照样核。

3一次运行的步骤：仓库从第一步挪到「用得着的地方」

第 ②–⑤ 步不再依赖仓库。读仓库失败只影响 ⑥⑦，而且会记在运行行上，不会让整次运行无声地重试 10 次。

4文件夹档：runner 怎么读工作目录

输出和 git 快照格式完全相同（路径和大小、文档标题、符号、README 首段），所以服务端的门检查、读缓存、文档构建都能直接用。 不同的只有：读的是磁盘上的文件，而 git 档读的是某个提交。

读什么、不读什么

  • 目录里有 .gitignore 就照它排除（没有 .git 也照样读这个文件）。
  • 内置排除表，先于 .gitignore 生效：.env*、*.pem、*.key、id_*、.ssh/、node_modules/、构建产物目录、二进制文件。
  • 不跟随符号链接，不出工作目录。
  • 单个文件上限沿用 2 MB（repoOps.read.wholeFileBytes）；文件数设上限，超过就按档位 0 处理并说明原因。
  • 上传前照常脱敏：owner 的 workspace.env 真实值逐字遮蔽（design §10.2）。

快照的标识与 diff

  • 标识 = 树哈希（见第 2 部分）。文件没变，哈希就不变：skipSha 照样省掉重传。
  • 快照的文件条目多一个 hash（内容 sha256）。两份文件夹快照之间的 diff 由服务端比对两份索引得出，runner 不用存历史。
  • 索引多一个 source: "git" | "folder"；commits 为空。
  • 读原文：按 (space, 树哈希, path) 缓存，和今天的 (space, sha, path) 是同一张表。

可信度怎么标

  • 锚点复验结果的 ref 记成 folder:<树哈希>，wiki_get 能看出它是在文件夹上核的，不是在某个提交上。
  • 文件夹上的内容可能是还没提交的改动：锚点后来不见了，复验时会是 missing，走今天的 challenge 流程，不需要新机制。
  • 以后目录变成 git checkout，就自动回到第 2 档；文件夹上核过的锚点下一次在 origin/main 上重核。

6失败分两类：持久的前提错误不再进重试循环

失败归类处理
目录不存在、不是 git、文件太多降档不是失败：按能读到的档位继续，原因写进健康行。不重试。
origin 是别的仓库、根提交不一致前提错误只跑第 0 档；健康行红；连续 3 次运行发一次通知（复用今天「失败 3 次」那条通知）。不重试。
git fetch 被拒（凭据）前提错误同上，原因 Git refused the credentials for origin。
runner 掉线、端点 5xx / 429、worker 崩溃瞬时 infra和今天一样：退避重试、不计连续失败。区别是：到了重试上限，这次运行改为只跑第 0 档，不再整体以失败结束。
模型给不出可解析的结果、服务端拒绝内容不变：计入连续失败，3 次通知。

7待定 · 要你拍板

Q1　space 有仓库地址，但工作目录不是 git（就是这次的情况）：要不要也走文件夹档？
方案 A：走文件夹档 推荐
你已经定了工作目录可以当来源。路径/符号锚点照核，提交锚点等回到 git 再核。防选错目录：和上一份快照比，路径重合不到一半就当作「别的仓库」，按红色那一行处理。
方案 B：只到第 0 档
有仓库地址的 space 只认 git，文件夹档只给没有仓库的 wiki。更保守，但这次的场景就只剩「条目照收，代码不核」。
Q2　第 0 档（读不到代码）抽出来的条目怎么处理？
方案 A：照常进 Review，代码锚点标「待核」 推荐
owner 能照常确认；但锚点没核过的条目先不进 <orbit_wiki_context> 推送块（今天的规则本来就是「锚点有效」才推）。核过之后自动进。
方案 B：去掉代码锚点再提交
条目马上能推，但丢了「这条知识依赖哪段代码」，以后代码变了也不会发 challenge。
Q3　一个 wiki 只读一个 workspace，还是可以列几个备选？
方案 A：仍然只有一个 推荐
模型简单；第 0 档已经保证维护不停，剩下的交给「Check again and run now」和「Change workspace…」。
方案 B：按顺序列几个，取第一个最高档的
同一个仓库在两台机器上都有时更省心，但设置和健康行都要多讲一层。

8落地（按代价排）

  1. 服务端：仓库不再是闸门。调整 steps() 的顺序：probe 的结果是档位，第 0 档也跑 ②–⑤；没有快照时锚点保留为「待核」（改 wiki-maintain.ts:666-672）；⑥⑦ 按档位跳过，并保留 anchors_due 和推迟的节。只改 wiki-worker，runner 不用升级，马上解决「停 6 天」。
  2. 失败分类和健康行。runner 的错误带上类别（降档 / 前提 / 瞬时）；health 契约加 repo.tier 和 repo.reason；web、iOS、Android 三端的句子一起改，由 fixture 约束。
  3. Settings：开启前的探测，以及「Check again and run now」。新的 owner 路由，建一次运行，计入每日次数。
  4. runner：文件夹快照。新的能力 wiki-repo-op-folder/v1：扫目录、排除表、树哈希，路径/符号锚点在文件上核；read 操作支持 folder: 引用。旧 runner 不声明这个能力，就停在第 0 档，健康行提示升级 runner。
  5. 服务端：文件夹快照之间的 diff（比对两份索引的 hash），给锚点复验和文档跟进用。
  6. 设计文档 docs/wiki-design.md §8.2、docs/wiki-server-execution-design.md §5.5 / §7 和 contracts/wiki.contract.json 同步改。
