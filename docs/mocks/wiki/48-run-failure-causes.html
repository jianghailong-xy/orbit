④ 决定（2026-11-16 owner 选 A1 · B1 · C1）

A · 上游原文谁能看

A1推荐：只留在服务端（数据库行 + worker 日志带请求 id），任何客户端都不显示。
A2：A1 + 部署 ADMIN（User.role）在失败调用上多一个「Technical details」展开，走现有 admin/wiki 路由，owner 读接口里永远没有。
A1 最简单；A2 适合自托管、没人能进库的部署，多一个接口和三端的一个展开。

B · 正在按 infra 重试的 run

B1推荐：琥珀色 Queued + 原因 + retrying in …；用完次数或内容失败才红。
B2：保持今天：只显示 Queued · retrying in …，不写原因。
B1 让人知道「是模型挂了、会自己好」，不用点开日志。

C · 已有的旧失败行

C1推荐：迁移时用同一个分类器从旧 error 回填 cause，识别不了的记 internal。
C2：不回填，旧行统一显示 “Something went wrong on Orbit's side.”
只影响 Activity 里最近 10 个 run 和 health 的 lastFailure；C1 几十行 SQL。

⑤ 落地（按代价排）

  1. worker 分类修正：未知 SSE error 类型 → model_unavailable（可重试）；executor 按 cause 判 infra / content。单这一步就止住「引擎挂了却记成内容失败」。
  2. shared：WIKI_FAILURE_CAUSES + 句子 + 分类器及测试；合同 jobs.failureCauses（Swift / Kotlin 原生钉住），fixture 失败用例改成 cause。
  3. 读接口 + 推送：jobs.read / health lastFailure / 计划 / 导入 / 飞书「Last error」都给句子；三张表加 cause 列，迁移回填（C1）。
  4. 三端：web lib/wikiRuns.ts、OrbitKit WikiRunsLogic.swift、Android WikiRunsLogic.kt 按 cause 渲染（B1），parity 测试跟上。
