1会话运行模型与长连接：总览

Orbit 中的 session 被定义为一个 agent runtime 与 runner 绑定的可恢复多轮会话，所有交互严格遵循「先存后投」原则：用户 turn 先落库，runner 再通过出站 long-poll 从 GET /api/runner/runs/:id/inbox 领取，避免直透传导致的丢包风险。[1][2]投递层采用 lease 模型，将 PENDING 转为 IN_FLIGHT 并设置过期时间，配合 runner 侧的 turnId 幂等去重，使至少一次投递在正常路径上收敛为恰好一次。[3]传输层选择 long-poll 而非 WebSocket，以适配 runner 的 outbound-only 特性及网关限制。[2]在状态保持上，runner 不持久化 seq，而是通过 server 返回的高水位 maxSeq 在重生时重置计数器，确保事件序列跨进程重启保持单调。[4]

读完本篇，你可以掌握从 runner 领取 session、turn 经 inbox 投递至 runtime 执行，再到事件通过 SSE 回传客户端的完整链路，并明确 long-poll 轮询、控制面心跳探测及崩溃后 reclaim 恢复分别落在哪一层实现。[5][6]本篇聚焦运行模型与传输机制，不涉及状态维度、消息路由及控制面流的具体细节。

3turn 投递与 inbox 领取：long-poll 与心跳

Runner 通过出站 HTTP 轮询领取工作，不依赖入站连接，因此无需开放入站端口。[5][2]当用户提交 turn 后，服务器将该 turn 持久化为 ConversationTurn 行，并通过 long-poll 端点 GET /api/runner/runs/:id/inbox 投递给 runner。[2]Runner 发起该请求后，若当前无可投递 turn，请求将 hold 至多 25 秒后返回 204；若有 turn，则将其作为响应体返回。[2]服务器端使用 EventEmitter 实现 wakeup 机制：当 turn 入队时，notifyInbox 触发对应 runId 的信号，唤醒已 park 的 runner。[8]

为应对 wakeup 信号丢失的情况，inbox handler 在 entry 时立即检查可投递 turn，并在每次 wakeup 后重新检查。[2]内部等待切片限制在 5 秒以内，确保即使信号丢失，延迟也不会超过 5 秒而非 25 秒。[2]waitForInbox 方法通过注册 once 监听器与超时定时器实现 park 逻辑，超时或收到信号时均会 resolve。[9]

Runner 在领取工作失败时执行指数退避重试：从初始延迟开始倍增直至上限，期间保持轮询状态。[10]claimRetryDelayAfter 函数根据连续失败次数计算延迟，每次翻倍但不超过 claimRetryMaxDelay。[10]claimRetryWait 在等待期间监听上下文取消，确保 shutdown 不会被重试等待阻塞。[11]Not verified

心跳机制用于控制面探测失联的 runner。Runner 每 30 秒发送一次心跳，控制面连续 90 秒未收到心跳即判定 runner 离线，此时 resume 功能不可用。[5][12]该机制确保控制面能及时感知 runner 状态变化，为后续的会话恢复或回收提供依据。

选择 long-poll 而非 WebSocket 的原因包括：runner 仅支持出站 HTTP、网关 nginx 配置限制 WebSocket 握手、以及 long-poll 无需网关变更即可实现亚秒级 turn 投递。[2]Inbox poll 复用现有的 location /api/ 配置，turn 作为 long-poll 响应体传递，因此 proxy_request_buffering 无关。[2]

7已知的坑Rewrite pending

session 启动窗口内的竞态：会话从被 runner 领取到 supervisor 完成注册的窗口期，客户端消息可能先于 session 在 runner 本地 pool 中落地而被控制面暂存进 queue。[28]若 runner 在此窗口内因自更新或 lease-loss 触发 detach，控制面仍在广告一个与 runner 本地 pool 对不上的 supervisor/permitGeneration，导致该窗口的合并请求恒被拒为 superseded。[28][29]该问题的触发条件比「runner 重启过」更宽：充要条件是「detach 之后本地再没有替补 supervisor 注册上来」，即使无任何重启也可能卡住。[30][29]围栏（worktreeOps[id] 中的孤儿条目）仅存在于当前 runner 进程内存中，下次重启或同 id 再注册即自动解开，并非永久。[30][29]修复后，准入放行、mergeToMain 正常执行并留下 MERGED 回执；剩余的 superseded 仅对应「交接在飞」这一种真竞态，调用方可据此区分并重试。Withdrawn

Bash 后台命令不可用：会话中 run_in_background 起的是 coding-engine 子进程，engine 被回收（idle TTL、内存压力）时连带杀掉 build。[31]必须改用 mcp__orbit__bg_run，按 kind: "service"（dev server、watcher）或 kind: "job"（build、test suite）提交，用 mcp__orbit__bg_output 读输出、mcp__orbit__bg_kill 停进程。[31]

8决策与理由

runner 采用 outbound long-poll 而非 WebSocket，因为 runner 本身是 outbound-only HTTP 客户端，而网关当前的 WebSocket 握手会失败，因为 gateway/nginx.conf 强制了 Connection '' 头；启用 WebSocket 需要新增 nginx location、@nestjs/platform-ws 模块及 Go WS 客户端，并依赖外部 TLS 终端允许 Upgrade。No source相比之下，long-poll 在零网关改动的前提下即可实现亚秒级 turn 投递。[32]

turn 投递采用 at-least-once 语义并配合幂等消费，以规避原设计在 dequeue 时即 ack 的风险。原方案会在 runner 连接断在 server 状态翻转与 stdin 写入之间、或 apiserver 重启丢失 wakeup 时永久丢 turn。现改为 lease 模型：dequeue 仅将状态设为 IN_FLIGHT 并设置 leaseDeadlineAt，ack 发生在 runner 确认消费时；runner 通过 turnId 去重丢弃重投的重复项，使 happy path 收敛为 exactly-once。[33]

9约定

运行 Orbit 测试与长命令时，必须遵守几项环境隔离与进程存活约定，避免假阳性或任务卡死。

首先，runner-go 全量测试必须在 runner 宿主上执行，不能直接在引擎 Bash 里跑。[39]因为引擎 Bash 会继承会话环境变量，引入约 10 个已知 false reds。[39][40]此外，高负载下默认 10 分钟超时会导致 go test 抛出 panic: test timed out，这属于没跑完而非测试红。[39][40]长命令应放在当前轮次内等待，避免与跑完后的验收跑抢 CPU。[39][40]

其次，real-CLI 探针或任何依赖 Go 的测试，必须用 env -u 清掉 ORBIT_SESSION_ID、ORBIT_AGENT_ID 等 Orbit 变量。[41][42]否则继承的会话环境会造成干扰。[41]更隐蔽的坑是会话环境会静默覆盖配置，如 ORBIT_WIKI 会盖过 .env 导致 docker compose 解析异常且 exit 0。[43]从会话部署应走 systemd-run 或 env -u 清同名变量。[43]

最后，别用后台作业唤醒来等长命令。runner 一旦 drain 就会杀掉后台作业，唤醒可能不送达，曾因此导致会话卡死六小时。[44][45]正确做法是在轮次内用 timeout 570 tail --pid=<pid> -f /dev/null 显式等待。[44][45]
