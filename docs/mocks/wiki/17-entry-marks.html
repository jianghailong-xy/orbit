Orbit 仓库 UI 效果图生成与验收规范

客户端与界面UI 设计20 conventions9 decisions8 pitfalls18 recipes4 concepts
Updated Sep 27 at 1588c3b·written by Wiki maintenance from 59 entries·38 sessions

Orbit 仓库规定所有涉及视觉或交互的 UI 变更在修改代码前必须先生成高保真效果图，并经 owner 明确批准冻结基线后才能进入接线实现阶段。[1][2][3]效果图通常以 HTML mock 形式编写，利用 Chromium headless 渲染为 PNG 截图，并与真实 CSS、组件标记及线上项目数据进行比对以确保还原度。[4][5][6]常见的陷阱包括未指定窗口尺寸导致内容截断、并发提交导致的设计稿取回失效以及截图管线中的 CSS 标签嵌套错误。[7][8][9]

效果图生成流程与目录约定

批准的效果图（HTML 和 PNG 文件）必须按仓库惯例存放于 docs/mocks/ 目录，文件名通常遵循 project-landing-line.{html,png} 等命名规范。[10][11]渲染时须执行 chromium --headless=new --disable-gpu --no-sandbox --hide-scrollbars 命令，并通过 --force-device-scale-factor=2 保证高清输出。[7][12]关键参数 --window-size=WIDTH,HEIGHT 必须根据设计稿内容动态调整，以防止长内容在截图中被意外截断。[7][12]对于 Web 端和 iOS 端的 mock 制作，需分别复用仓库真实的 index.css 类名与 docs/mocks 中的机框，并从线上真实项目提取数据作为底稿。[4][6]

设计决策与 Owner 审批机制

涉及 UI 改动或偏离现有呈现时，必须先按真机实测值绘制效果图，并列出 2-3 档折中方案供 owner 选择，owner 拍板后才能开始改码。[1][13][2]iOS 对齐类 UI 问题严禁直接改码，需先画多版效果图并对比各方案在标题宽度、动效等方面的取舍，待 owner 选定后统一接线所有相关组件。[13][14]改动 Web UI 文案时须同步更新 docs/ux 下的对应设计稿区块，确保与代码字串完全一致以避免图码分叉。[15]若 UI 决策被推翻（如快捷键选择或链接展示），需将相关注释或代码引用更新为仅保留实测数据或按新决策执行。[16][17]

常见陷阱与调试技巧

在截图验证时，若 CDP 开启 captureBeyondViewport 会触发浏览器重排导致横向偏移，应将其设为 false 并改为按元素 rect 裁切取景。[18]构建页面时若将 extractStyle 的输出再次包裹进 <style> 标签，CSS 解析器会吞掉首条规则导致按钮意外位移，应直接将输出塞入页面。[8]修改效果图前建议先用 compare -metric RMSE 复现原图校验渲染管线，确认 RMSE=0 后再进行 HTML 修改以保证管线无误。[19]此外，headless Chromium 在容器环境中可能出现 GCM 注册报错，该错误与截图无关，可直接忽略并以输出文件字节数判断成功与否。[20]从来源分支 checkout 文件前需先 git fetch 核对 blob，防止因并发提交已合入 main 而制造空提交。[9]

改夹具前先确认它描述活库还是历史模型
仓库有过夹具不再描述真实数据库的坑，改前必须先判明夹具指向活库列还是历史 schema，别顺手删掉一段证明。
Owner
修间歇红时不得改生产击杀逻辑，只修测试对宿主时序的错误假设
terminateSessionProcessTree 是生产代码，生产里 400ms 宽限期不是问题；有问题的是测试把宿主时序当常量。
Owner
以实测证据推翻任务里错误的根因假设再动手
修复前先实测定位真实根因；本例任务断言是慢启动，但容器日志证明 postgres 6 秒就应答、只是 role does not exist，说明应修容器形态而非只加宽超时。
Owner
修 owner-only UI 边界不得放宽权限
涉及 account-owner-only 写渠道（删除项目、记录 DONE）的 UI 改动，owner-only 边界必须出来不比进去更松，不得放宽谁能触达、不得放松断言。
Owner
删除不能表达行为意图,授权须 fail-closed
删除是状态载体的消失;用 NOT EXISTS(某可删行)表达否决会被读成许可,授权必须锚在不会被删掉的载体上。
