待定 · 要你拍板

每题都给了推荐；你只需要否掉不同意的那几项。

Q1 · 卡片由谁把关？

A · 服务器保管提议推荐Agent 把提议交给服务器，服务器存一张待答的卡；只有 owner 在客户端答“是”，服务器才写入。Agent 手里的凭据始终写不了 preferences，@PatForbidden('ACCOUNT') 不动。
B · 像 provider 写入那样由 runner 先问runner 弹卡，用户点“是”后 runner 调写接口。改动少，但写接口得对 Agent 的凭据开放：一个绕过 MCP、直接 curl 的 Agent 就能跳过卡片。

Q2 · 第三档里“收窄”的改动能不能走卡片？（关闭编排、屏蔽 provider、权限更严）

A · 可以，走卡片推荐Agent 收紧自己的权限没有风险；比如“别再用 X 家模型了”可以当场确认。判断方向由服务器按 key 和新旧值决定。
B · 一律只给链接规则更简单（第三档 = 不可提议），代价是“关掉某项”也得跳去 Settings。

Q3 · 第一档要不要免卡，直接改、事后告知？

A · 也走卡片推荐设置是你的；一次点击的成本很低，且“任何设置改动都经过你”这条规则一句话就能讲清。
B · 第一档直接改少一次点击，但会出现“设置自己变了”的时刻，只能靠第 3 部分的灰字事后发现。

落地（按代价排）

  1. 分档表：src/shared 里一张 key → 档（含“收窄方向”判断）的表，服务器、runner、客户端读同一份。小
  2. 服务器：新的“设置提议”记录（会话、key、当前值、改后值、理由），只收第一、二档；第三档回 403 SETTING_OWNER_ONLY。owner 答“是”才写 preferences，并记下 changedBy {sessionId, at}，供 Settings 灰字和 Undo 使用。中
  3. runner-go：MCP settings_propose + CLI orbit settings propose，加入 operation catalog；可选的 settings_get 让 Agent 先读到当前值再提议。primer 加一句：碰到设置问题，提议，而不是指路。中
  4. Web：确认卡正文（当前 → 改后、所在页、理由）、第三档链接卡、Settings 行下灰字 + Undo。中
  5. iOS / macOS / Android：同一张卡、同一行灰字；Android 照 iOS。中
