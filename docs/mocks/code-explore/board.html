  1. 引擎主会话调用 code_explore({question, paths?})。
  2. runnerorbit mcp 交给守护进程，带上本会话的工具超时；预算取 min(25 秒, 超时的一半)。
  3. apiserver第 n 轮：带上问题、顶层目录和已经看过的结果。检查开关、配额，然后调用 DeepSeek。
  4. DeepSeek返回 JSON 动作清单：{actions: [grep | files | read …] ≤ 8}，或者 {done: true, locations}。
  5. runner在 worktree 里并发执行这些动作，输出有上限（grep 最多 200 行、read 每个最多 200 行、一轮合计最多 2.4 万字符），结果带进下一轮。最多 4 轮。
  6. runner核对：每条位置必须和实际看到过的 grep 命中或 read 区间重叠，文件和行号在当前 worktree 里存在，不满足就丢弃；去重后最多 12 条。
  7. 引擎收到 {locations: [{path, startLine, endLine, why}], coverage, usage}，只读这些区间。
  8. apiserver已经写好第 0、1 级记录，开关打开时再写第 2 级；打标签作业之后补上命中和漏召回。

失败时直接说明（例如 "code explore unavailable; search with rg"），不让 agent 反复重试。DeepSeek 限流不会影响会话本身用的 provider。

Q1 · 功能本身默认开还是关

A：所有账户默认开。采用率最高；但其他账户的代码会在用户不知情的情况下发给 DeepSeek。
B：默认关，各账户在 Settings 里自己打开推荐
部署方自己的账户上线时就打开。对其他账户开放之前，先核实 DeepSeek 的原始条款（数据在中国境内存储、是否用于训练、保留多久）。

Q2 · M0 评测从哪里拿 key

A：HPC 上放一个评测专用的 key 文件推荐
评测直接调用 DeepSeek，评测完就删除。和产品代码解耦，过不了门槛就不用做服务端。
B：先做转发接口，评测走服务端那把 key。顺带测出真实延迟；但服务端的工作要排在门槛之前。

Q3 · 每条结果要不要带理由

A：path:行区间 + 一句不超过 15 个词的理由推荐
每条约多 20 token，主会话可以据此决定先读哪一段。
B：只给 path:行区间。最省 token；主会话要自己判断先读哪段。
