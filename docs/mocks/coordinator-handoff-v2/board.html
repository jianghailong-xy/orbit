① 交接时，哪些“挂着的事”跟着走

今天的换人事务只搬 watch。其余四种挂着的事留在已结束的旧协调者身上，结果回来时被丢弃（DROPPED）。

挂着的事今天 v1建议 v2
task_await / watch✓ 在换人事务里搬走不变
delegate SubAgent 运行✗ 结束时唤醒被丢弃继续在原处跑；唤醒转给接手者（交接链可多跳）
bg_run 后台任务✗ 退出唤醒被丢弃同上：进程不动，唤醒转给接手者

未答的 owner 问题、open item✓ 项目级，本来就在不变

② owner 的裁定：从交接便条里搬出来，成为项目记录

今天“和 owner 约定的”只是便条里的一段文字；每交接一次就是“摘要的摘要”，丢一条就永远丢了。

来源 A：ask_owner 被回答问题 + 选中的选项自动成为一条裁定，原话即引文。
→
project_ruling一句话裁定 · owner 原话 · 来源（问题或对话轮次）· 谁记的 · 何时 · 可被新裁定取代（旧的标“已取代”，不删）
→
去处接手者的开场摘要逐条列出；项目页在验收标准下方显示。
来源 B：对话里的裁定协调者调用 project_ruling_record，引文必须是那一轮 owner 原话的子串（和 wiki_note 的引证检查一样）。
→
交接时便条那一轮先要求“把还没记录的裁定记下来”，再写便条。便条的 “Agreed with the owner” 改为 “Rulings not yet recorded”，正常为空。
4裁定不是验收标准，平台不据此强制任何事；它记录的是“协调者被告知了什么”。

⑤ 待定 · 要你拍板

D1 裁定存在哪

A独立记录 project_ruling：有来源、引文、取代关系，交接多少次都不丢。推荐
B追加到项目 instructions 的 “Owner rulings” 段：不改表，但又成了自由文本，且 project_update 可改。

D2 交接前的历史在接手者里怎么呈现

A不画；便条卡片上一行链接到上一任协调者。推荐
B在顶部折叠成一行，可展开。

D3 接手者的开场读取

A服务端摘要写进开场：确定、约 4k、无工具调用。推荐
B保留两次读取，给 project_get 加 brief 模式。

落地（按代价排）

  1. 挂着的事全部跟着走：唤醒转发 + wakeup/loop 搬家 + 确认弹窗列出（服务端 + 三端弹窗）。
  2. 清爽开场规则：web、iOS/macOS、Android 各改 decisionReceiptAnchor / ReceiptAnchor.place。
  3. 开场状态摘要（服务端）。
  4. 裁定记录：表、project_ruling_record、ask_owner 自动成裁定、便条提示词、项目页显示。
