Shared 会话今天没有任何 Git 栏（SessionOutputs 在 isolationStatus 为空时什么都不画）。新设计给它同一条 Main checkout 栏，审阅和提交走同一个抽屉；这里没有 Move，因为会话本身就在 Main checkout 里。

标注

  1. Commit 只做一件事：把勾选的文件在 Main checkout 当前分支上提交成一个 commit。不 push、不算会话合并、不算任务落地，结果行会明说。没写 message 时按钮不可点。
  2. Move 的目标默认是打开抽屉的那个会话。目标会话正在跑一轮时，不能选（agent 正在写的目录不能往里塞东西）。
  3. 边界写清楚：ignored 文件不在列表里，也不会被 Move、Commit 或清理；untracked 文件算在内。
  4. Shared 和 Worktree 两种模式用同一个抽屉、同一套动作。
  5. Push：Commit 结果行上直接给 Push 按钮；之后只要本地比 upstream 多出 commit，灰条就显示 “N commits not pushed · Push”（④ 的第二条）。
  6. 受管分支：如果当前分支是某个项目的 integration line 或 landing 目标，Commit 和 Push 前加一句 “This skips project X's landing check”，由人决定，不拦截。

“你看到的”就是“会执行的”

抽屉打开时，runner 给这份快照算一个指纹（HEAD + 每个文件的内容 hash）。按下任何动作时，指纹随请求带回去，runner 执行前重新算一遍：

  • 一致 → 执行；
  • 不一致（有人又改了、HEAD 动了）→ 什么都不做，回一句 “changed since you looked — review again”，抽屉自动刷新。

同一台机器上同一个目录的所有操作（Move、Commit、Save、会话 Merge）由 runner 里按真实路径加的一把锁串行。

③ 结果和拒绝：都作为一行写回对话

每个动作结束后，runner 把结果写成会话里的一行 system 记录（不是一闪而过的 toast），能回看。失败时一律不改任何东西，并说明下一步可以做什么。

每个动作 runner 端怎么做（人不用关心，但要可审计）

动作步骤失败时
Move① 核对指纹 ② 先把 Main checkout 现状存成 orbit/rescue-*（现成的 rescueWorkingTree）③ 用 3-way 把改动应用到目标 worktree（先 --check）④ 只把这些路径在 Main checkout 里恢复到 HEAD，删掉这些 untracked 文件③ 有冲突 → 目标和来源都不动；④ 前来源又变了 → 只复制、不清理，并如实写出来
Commit① 核对指纹 ② 用临时 index 只放勾选的文件，commit-tree ③ update-ref 时带上预期的旧 HEAD（CAS）④ 把真实 index 里这些路径对齐到新 HEAD，未勾选的 staged/unstaged 内容不动HEAD 变了 → 不提交；处于 merge/rebase 中、detached、没有 HEAD → 拒绝
Push① 只推当前分支到它的 upstream（没有 upstream 时推到 origin/<同名> 并设为 upstream）② 普通 git push，永不 --force ③ 用 runner 机器上已有的 git 凭据non-fast-forward 或认证失败 → 原样报出 git 的原因（去掉敏感信息），本地 commit 不动
Save & clean现有 Clean up checkout，放宽成 dirty 也能用，并加上指纹核对rescue 分支没建成就不清理（现有行为）

崩溃恢复：每步都可以安全重做。commit 已经存在就不再建；ref 已经指向它就跳过；rescue 分支名由内容 hash 决定，重做不会多出分支。

和会话 Merge 的关系

  • Merge 今天已经会在“分支改的文件在 Main checkout 里也有未提交改动”时拒绝（ffClash，worktree.go:1968）。这条保留，文案后面加一个 Review main checkout 链接，直接打开 ② 的抽屉。
  • 先 Commit to main、后 Merge：Merge 本来就会 rebase 到最新的 main，不用加新逻辑。
  • 先 Merge、后提交：抽屉里的指纹已经包含 HEAD，过期后自动要求重新审阅。
