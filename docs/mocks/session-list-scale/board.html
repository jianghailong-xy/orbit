1今天 vs 新：一次打开 workspace 发生什么

今天有文件夹或项目的 workspace 不分页（WorkspaceView.tsx:3273、BootGate.tsx:175），刷新页面没有游标，必定 full: true。新做法下首读和首屏只跟一页有关。

今天

GET /sessions?view=open&workspaceId=…&since=since 为空 → full: true，1348 行全部构建、序列化（估计数 MB）
↓
客户端分组 sessionProjectListing1348 行 × sessionLine / statusGlyphMotion；每一帧 watch、clone 进度、换选中会话都重算一遍
↓
renderSection → 1348 × SessionListRow没有虚拟化；行没有 memo，每行的菜单、swipe、onOpen 每次渲染都重建
读 O(N)算 O(N)/帧DOM O(N)

新

GET /sessions/listing?workspaceId=…&view=open&limit=40folders[]（文件夹计数）+ 40 条顶层条目（会话 / 项目）+ next；版本没动回 304
↓
客户端只拼页文件夹行用服务端计数；项目行 = 项目条目 + 现有 project-placement 读；不再按全表分组
↓
窗口化渲染（约 2 屏的行）行组件 memo；sessionLine 等只在挂载的行里算；滚到底取下一页
读 O(页)算 O(可见)/帧DOM O(可见)

2A · 新读：服务端给"顶层条目"，列表长相不变

规则逐条照搬客户端今天的 sessionProjectListing / sessionFolderListing，用一份共享夹具 contracts/session-listing.fixtures.json 钉住两边。Trash、按标签筛 / 分组的平列表不进这个读，照旧走 GET /sessions 分页。

  • 1文件夹行：行数（项目算一行）、等你的数、运行中 / 后台任务两种动静，由服务端按 folder_id 数出来，判定复用侧栏 workspace 行的 workspaceSessionCounts，三处不会说两样话。
  • 2项目行：一条项目条目代替它在本 workspace 收走的所有成员；位置取成员里最大的 listedAt，Pinned 跟协调者。第二行要的"谁在等你、跨 workspace 会话数"照旧来自现有的 GET /sessions/project-placement。
  • 3会话行：不在本 workspace 现存文件夹里、也没被项目行收走的会话；协调者在别处的成员照旧是自己的行，带项目标记。行内容与今天的列表行同一个 DTO。
  • 4分页：顺序与今天一致（Pinned 在前，再按 COALESCE(listed_at, created_at) DESC）；滚到底取下一页。流在线时只在 sessions.list_changed 或 60 s 兜底时重读已加载的页。

3C · 只画看得见的行，每帧只算挂载的行

文件夹行、分组标题、会话行、项目行展平成一条带类型的列表，交给窗口化渲染器；视口上下各留约一屏。行的第二行、图标动静、菜单都挪进行组件，只在挂载时算。

D1 · A 的形状

A1 服务端按顶层条目分页推荐首读、首屏只跟一页有关；规则搬到服务端，由共享夹具保证两边一致。
A2 精简索引 + 按需取整行分组仍在客户端，规则不搬；但索引仍是 O(N)（1348 行约 200–400 KB），要维护两层缓存。

D2 · 原生端

只做 Web推荐iOS / macOS / Android 本来就懒渲染，整读只在启动时一次，之后增量常驻；新读是加出来的，以后随时接。
三端一起读法与行为三端一致，本期工作量约翻三倍。

D3 · 虚拟化实现

@tanstack/react-virtual推荐无样式、约 5 KB，动态行高用 measureElement；与在用的 react-query 同一家。
CSS content-visibility: auto零依赖，省布局和绘制；但 React 仍为每一行建元素，渲染代价不降。
