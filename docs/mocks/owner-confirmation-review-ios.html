任务确认卡：补上「按下后会发生什么」和审查方的意见

截图那一单：执行会话 14:55 声明完成，派活的会话还在审，卡片已经在叫你。你 15:00:49 按下确认，1 秒后下游任务开跑，以一条没审完、也没进 main 的分支为基线。卡片上能看到的只有验收标准和执行者自己的话。下面四台手机按时间顺序画同一单：现状、第一步（只加 Orbit 算出来的事实）、审查中、审查完成。第二排是还没拍板的那一处对照，以及其余几种状态。

需要补的数据（按推进顺序）：
  1. If you confirm 只读服务端已有的事实：确认后会被放行的下游任务（autoRunWhenReady，并且其余依赖都已满足）、运行会话的 branchMerged / changedFiles，以及任务是否在项目里、项目怎么落地。这些数据加进 GET /tasks/:id/owner-confirmation 这个读接口，三端都从这里读。
  2. 报告改取声明完成（task_request_confirmation）那一轮的最后一条消息，而不是「停下来」那一轮的最后一条。
  3. 审查方：任务属于项目时，默认是项目的协调会话；不属于项目时，是建这个任务的会话；你在 app 里自己建的任务没有审查方。声明完成时，Orbit 向审查方发一条要求回复的会话请求，复用正在做的 expectReply。请求的几种结局（已回复 / 超时 / 对方已结束）正好对应审查栏的几种状态。审查期间这张卡不计入 needs-you，回复或超时之后再计。
  4. 审查内容沿用服务端已有的「项目是否完成」请求的结构（DoneRequest：judgment，加逐条核查和证据引用），按任务拆成 已核实 / 没核实 / 要你判断 / 遗留 这四类条目，并绑定在 requestId 和提交上。审查方能写条目和一句结论，但写不了按钮，也写不了开头那一行。
  5. 还没拍板的：开头用 A 还是 B（推荐 B）；超时时长（先用 30 分钟）；像这一单这样「机器能验、审查方能审」的任务，要不要直接由审查方结案，你只负责合入 main。
