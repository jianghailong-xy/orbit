会话工具栏：读不到 runner 时自己恢复 · iOS / macOS

工具栏上的模型名、用量条（还有 / 菜单里 runner 的命令和技能）都来自会话打开时那一次 GET /runners（ConsoleModel.loadContext）。这次改动不改任何界面，元素、文案、布局都和现在一样，变的只是什么时候再读一次。所以下面画的是同一个会话随时间的样子：cd-aivps 上的 Claude 会话，配额 7 天窗口 30%。「现在」按现有代码画，「改后」按本会话分支上的改动画（还没发版）。灰色字母标现在的问题，橙色数字标改动；对话内容只是示意。

① 现在：打开时读失败一次，就一直降级，直到退出会话再进来
现在14:42 打开会话，GET /runners 失败

A 模型名退化成原始 id claude-opus-5-5：友好名「Opus 5.5」只在 runner 上报的模型目录里。B 没有用量条：配额也在同一次读取里。/ 菜单也少了 runner 的命令和技能（图里看不到）。失败被 try? 吞掉，不重试，也没有提示。

现在锁屏 / 切到别的 App，再回来

C 回到前台会重连，并重读审批、排队消息、后台任务、项目的问题和确认卡，唯独不重读 runner，所以还是原始 id、没有条。网络断开又恢复、流断开重连，也都一样。

现在退回列表再点进来（或杀掉 App 重开）

只有重新打开这个会话，才会再跑一次 loadContext，工具栏这才恢复：Opus 5.5，用量条 30%。这就是之前让你「杀掉重开」验证的原因：其实退回列表再点进来就够了。

② 改后：打开时先重试；还读不到，下一次重连再读，不用退出会话；会话开着时每 60 秒再读一次
改后14:42 打开会话，第一次失败，0.3 秒后重试成功

1 打开时的读取最多试 3 次，间隔 0.3 秒、0.6 秒，和对话记录首屏加载（seedTailPage）一样。一次性的网络抖动在 1 秒内就恢复，多数时候根本看不到降级。新建会话的草稿用的是同一个读取，也一样重试。

过程三次都失败（比如打开时正好断网）

2 三次都失败时，先和现在一样降级。读失败不清空已有的数据，这条和现在一样，新加的重读也照这个规矩：从列表打开时带过来的模型目录如果在，模型名照常是「Opus 5.5」，只少用量条。Codex 重置额度照旧，读不到 runner 时不可用。

改后回到前台 / 网络恢复 / 流断开重连

3 每次重连都顺带重读一次 runner，模型名、用量条、/ 菜单一起恢复。不用退出会话，更不用杀 App。重连本来就会触发，这里只是在已有的那组重读里多加一项。

改后第二天 8:05 打开手机，回到这个会话

4 用量条以前停在会话打开那一刻（锁屏一夜回来还是 30%），现在回到前台马上刷新，这里是 41%。会话开在屏幕上时，每 60 秒也刷一次，和 web 一样：跑着的任务用掉多少，条就跟着动。

说明

  • 改了什么（一个文件，iOS / macOS 共用）

  • 1ConsoleModel.fetchRunners()：打开时的 GET /runners 最多 3 次（间隔 0.3 秒、0.6 秒）。会话的 loadContext 和新会话草稿的 prepareDraft 都走它，模型默认值、努力程度这些跟着 runner 算的东西在同一轮里就算对。
  • 2失败不清空：失败时只把 Codex 重置额度的准入置空（读不到就不让花，和 loadContext 原来一样），屏幕上已有的模型目录、配额都留着。
  • 3ConsoleModel.refreshRunner()：接进 run() 里重连时已有的那组重读（审批、排队消息、后台任务……）。读到就更新模型目录、配额和 / 菜单；runner 不在列表里就清掉，和打开时的处理一样。
  • 4runnerPollTask：会话开在屏幕上时每 60 秒调一次 refreshRunner()，和 web 的 60 秒刷新一样。跟着会话的流一起开、一起停：退出会话、切到别的会话就停。新会话草稿没有流，不刷。
  • 5测试：新加 ConsoleRunnerRefreshWiringTests 3 个用例，改前失败、改后通过；OrbitKit 全量 3452 个，失败的 12 个就是 main 上已知的那 12 个 copy-parity。新代码原样抽出来对 OrbitKit 做了 Swift 5 / 6 类型检查；完整的 App 编译要走 CI，还没跑。

  • 不变的

  • ·工具栏的元素、文案、布局；Context 环（来自会话事件，本来就不受影响）；Plan usage 详情。
  • ·web、Android 不动：web 本来就每 60 秒重新拉一次，失败重试一次；macOS 用同一个 ConsoleModel，网络恢复、流断开时同样重读。
  • ·手机上要等发版才生效，客户端只从 v* tag 发布。

  • 这次解决不了的

  • !确定性的失败。如果你杀掉重开后仍是原始 id、没有用量条，说明不是网络抖动，而是每次都会失败：某个 runner 行解码不了，或者会话的 runner id 对不上。重试多少次都一样，还得按原计划在服务器上抓一次原始响应，和客户端解码逐字段对比。

  • 已定（10 月 9 日）

  • ①不加「加载失败」提示。能自己恢复以后，降级通常不到一秒，最多到下一次重连或下一分钟的刷新，提示多半一闪而过。
  • ②会话开着时每 60 秒刷新一次用量。已加，见左边 4。
