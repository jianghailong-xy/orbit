9 · 待办即决定：会话行、置顶条、卡片三处都先说要你做什么

一条异常待办走到你面前时，三处展示位都由服务端的同一份读模型驱动：会话行、置顶条、卡片。卡片第一行是服务端给的 requiredAction（要谁做什么），门由服务端的 primaryAction 领头、每一扇下面一行说它的后果（ACTION_CONSEQUENCES），会话行与置顶条上是服务端算的短句 need（Escalated to you · Checks failed）。三端只渲染，不翻译、不自己拼（契约 §4.8、§7.5、§7.6）。英文是上线文案，中文是说明。

交出时必须写一句话（空说明、超 2000 字各自 400），它留在行上，第一行就引用它；推送标题是 Now yours — the coordinator handed it over。协调会话处理中要你拍板的事不用这扇门——它用 ask_owner 问，待办仍留着。
  • 1三处一个来源：requiredAction / primaryAction / need 都在服务端算（project-open-item.ts，维度按门表读），三端只渲染。会话行、置顶条、卡片因此不会对同一件事说两句不同的话——这正是 2026-10-02 那次「Escalated to you / Waiting for approval / 卡上写着别的」的修法。
  • 2门一定领得动：卡上的门来自门表（open-item-doors.ts）里这一格真正持有的那些，primaryAction 是其中第一个能按的；每一扇下面那句后果与它同源（ACTION_CONSEQUENCES，web 与 OrbitKit 由 parity 测试对住）。Review 只在目标候选真的在时出现。
  • 3「有人在办」也要先说：一旦挂上修复任务（handledBy 非空、且有一条还没到 DONE/CANCELLED），第一行就换成 A repair task is already handling this item …。重跑本身不改第一行——它只让旁边多一枚 Handling，门照常都在；处理中就是处理中，不显示成 HANDLED（H1–H5）。
