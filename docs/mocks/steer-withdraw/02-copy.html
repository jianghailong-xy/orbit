消息下面那一行的文案（Delivering… 合不合适）

已定（2026-10-16）：按推荐落地，Web、iOS / macOS、Android 三份词表一起改。结论：Delivering… 不合适。这时消息已经到了 Claude 那里，只是在等它做完手上这一步再读；「-ing…」说的却是「还在路上」，一停几分钟就像卡住了，旁边再放 Withdraw 也会读成「取消投递」。大家熟悉的是聊天软件的回执：发送中 → 已送达（未读）→ 已读，这一行照这个顺序改，三处要动，其余不变。每一格都是真实页面截的（右下角是你那条消息的气泡），「建议」是把新文案写进同一个页面。

消息走到哪现在建议为什么

正在撤回新增的状态 — 新增链接消失，不能重复点。
模型读到了已经进了这一轮，这一轮的回复会照顾到它 改在聊天软件里 Sent（已发出）比 Delivered（已送达）还早，原来 Sending → Delivering → Sent 是倒着走的。你真正关心的是「它看到没有」，所以用 Read；in this turn 保留：这条没有自己的回复，回复在这一轮里。

不知道读没读引擎还没回显就退出了 改不确定的不是「送没送到」（已经送到了），而是「读没读」。语气保持中性，不催你重发：它可能已经照做了，重发会做两遍。
撤回时来不及窗口右上角的提示 — 新增和 Read in this turn 用同一个词。原稿 Claude had already read this message. 改成现在时，也更短。

撤回相关的其他文案

  • Withdraw，不用 Cancel：排队消息的 Cancel 是「还在 Orbit 手里，取消发送」；这条已经交给 Claude，是「拿回来」，和你说的「撤回」一个意思。动作的结果一样：文字回到输入框。
  • 方案 B 留的那一行：You withdrew a message（同微信「你撤回了一条消息」）。
  • 撤回失败：Couldn't withdraw，下面一行写原因，例如 The runner didn't respond.。
  • 服务器的拒绝原因（API、CLI、MCP 会原样看到）：现在是 this message is being written into the running turn and can no longer be withdrawn，改成按引擎说：Claude has already read this message, so it can no longer be withdrawn. / Codex already has this message and can't give it back.
