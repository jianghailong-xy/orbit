Runner 更新：看得见、能延后、能中断

按 macOS「软件更新」的思路：更新是一个看得见的对象，有明确的阶段；凡是因为它而停住的工作，都说出原因，并且就地给出「Later」和「Update Now」。

· 服务端其实已经知道：心跳里有 heartbeat_draining=true，self_update.reason 写着 “deferred for 1h5m51s … until the 8 turn(s) in flight end”。

· 可是排队原因 queuedReason 只认 5 种（离线、runner 满、run 满、batch 满、git 操作），没有「在更新」，于是落到 null，界面说「马上就会被领走」。

· 「Update Runner Now」只是让它早点去查，查到有 turn 在跑还是继续等，实际上帮不上忙。

⑧ 数据、协议，以及待你拍板的几件事

数据和协议（只加字段，旧 runner 照常工作）

哪里改什么
排队原因 SQLWHEN r.heartbeat_draining THEN 'runner_updating'，放在 runner_offline 之后；queuedActive = 这台 runner 在跑的 turn 数
shared RunnerSelfUpdate加 phase（available / draining / restarting / postponed）、targetVersion、drainingSince、postponedUntil；由 runner 填写，旧 runner 不发，客户端就沿用今天的文案
API（只有 owner 能调，记审计）POST /runners/:id/self-update/postpone {until}
POST /runners/:id/self-update/now {interruptTurns:true}
和现在的 selfUpdateRequestedAt 一样，放在心跳回包里带给 runner
runnerpostpone：清掉 drainingForUpdate，在 until 之前不重新计时；now：走正常停机（session 保持可 resume），然后安装、重启
apiserver重新领取被打断的 session 时，补一个 resume turn，附带一行 Orbit 说明

落地顺序（按代价从低到高）

  1. 新增 runner_updating 排队原因，加上三端文案和排队消息的 foot row 灰字。不改 runner，最快见效。
  2. runner 上报 phase 等字段，runner 页面加 Update 卡片。
  3. Later（延后）端到端。
  4. Update Now，以及被打断 turn 的自动 resume（先实测）。
  5. 提示条和推送。
另一个 bug，单独开 task：runner 排空期间，有个 session 实际在跑，数据库里却还是 PENDING。它会让新的排队原因把这个 session 也错标成「Runner updating」。

待定 · 要你拍板

问题AB
D1 Later 有哪些选项1 小时 / 今晚 02:00 / 明早 09:00推荐只给一个「1 小时」
D2 延后有没有上限不封顶，但每次最多延到明天，到点会再问一次推荐标记为「必须」的版本不允许延后
D3 什么时候出提示条和推送只在有你的东西在等它的时候推荐只要 runner 进入排空就提示
D4 被 Update Now 打断的 turn自动 resume，并附一句说明推荐停在原处，等你自己去点继续
D5 安静时段设置先不做，D1 的「今晚」已经覆盖推荐每台 runner 设一个时间窗，窗口内不等空闲直接装

· 为什么不做「只放行这一个 session」：那样要改 runner 的领取协议，而且每放行一次更新就再往后推一次。它的效果和 Later 差不多，成本却高得多。

· 为什么不给排空加自动超时：超时后自动恢复领活的话，忙碌的 runner 就永远装不上更新了。当初加排空，就是为了让 0.1.248 的心跳修复能装上。该不该推迟，交给人来决定。
