Scheduled runs as a group under their workspace

Today a scheduled run opens an ordinary session in its workspace, but every list filters it out (run_source <> 'SCHEDULE'), so it is reachable only from Scheduled and from the notification. Proposal: each workspace that has runs gets one Scheduled runs group. It is a folder-style page that reuses the session list, the row and the session page unchanged. The only new thing is the filter: runSource=SCHEDULE instead of ≠.

Why it is like this

  • The owner ruled on 2026-11-14 (docs/scheduled-tasks-design.md) that run sessions stay out of the session list, so that a daily schedule does not add a session to its workspace every day.
  • Server: schedule-run-sessions.ts opens the session with the schedule's workspaceId, runSource = SCHEDULE, openedBy = SCHEDULE.
  • Every list query filters it out: SessionsService.list, listOpenSince, search, workspaceSessionCounts, listForOrchestration, folder counts, realtime session.created, workspace-usage.ts.
  • Cost seen today: a run that is waiting on an approval is hard to find from the workspace you work in.

Marks

  1. The drawer row appears only for a workspace with at least one run session that is not in the Trash. It is indented and smaller than a workspace and shows no count. The orange dot is the same "waiting on you" signal a session row carries.
  2. Folder-style header: back arrow, title, the workspace under it, and the same Open / Completed / Trash scope menu.
  3. Rows use the ordinary session row. The title is the schedule's name. The second line starts with the run's result (Waiting on you / Changed / Failed), then "run of Nov 18" or the run's note.
  4. The strip drops "not in your session list" and gains "Open schedule". The breadcrumb names the workspace group.

What does not change

  • The workspace's own list (Open, Completed, search, the drawer's count) still leaves runs out. You see them in their group, not mixed into Today.
  • openedBy = SCHEDULE stays, so a run never becomes the workspace default.
  • Scheduled (left drawer) and its history stay the main home of schedules.

My recommendation is B: it is pure reuse (a folder whose members are chosen by runSource) and works the same on every client. A is better only if you want runs visible without opening the workspace. The orange dot in Waiting on you already covers that case.

For you to decide

  1. Placement: A (drawer row under the workspace) or B (row in the workspace's list). Recommended: B.
  2. This reverses part of the 11-14 ruling "nothing about them appears in a workspace's session list". OK to amend the design doc to "runs appear only in their workspace's Scheduled runs group"?
  3. Search: should session search find run transcripts? Recommended: yes, labelled "Scheduled run". Agents' session_list stays as it is.
  4. Clients: web first, then iOS / Android in the same change? Recommended: all three, since B is the existing folder UI on each.
