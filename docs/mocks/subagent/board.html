SubAgent · 父会话把一段活交给最合适的 Provider，过程内嵌在消息流里

父会话的模型调用 delegate；Orbit 在同一台 runner、同一个 worktree 里起一个子引擎进程（可以是另一种引擎、另一把 key），按难度和 Optimize For 从所有已启用的 Provider 里选模型。子 Agent 直接改文件、不提交；可以前台等，也可以后台跑；可以并行，冲突由父 Agent 自己避开。

已定 · 2026-11-11三项 owner 均按推荐拍板

A. Cost 模式怎么算订阅账号

1 · 有余量的订阅先用，再用按量计费的 key推荐
订阅多用一次不多花钱；订阅之间按额度余量排，key 之间按 models.dev 价格排
2 · 订阅按同档 API 价折算，和 key 一起比价
看起来公平，但订阅额度闲置，实际花更多钱

B. 默认开还是关

1 · 默认开，Optimize For = Cost推荐
配合 A-1，多数 SubAgent 跑在已付费的订阅上；花费在块头和报告里都看得见
2 · 默认关，按 Agent 打开
L3 编排的做法；更保守，但多数人不会去开

C. 一轮结束时还有后台 SubAgent

1 · 会话保持 Running，结束时唤醒父会话推荐
和 bg_run 一致；停放推迟到它们结束
2 · 一轮结束就停掉
简单，但「后台」只在一轮之内有效
分期先把最难的「同 cwd 子进程 + 内嵌 + 生命周期」单独做对，再加路由

P1 能派、能看

delegate（前台 / 后台 / 续跑）· explore / general · 读定义文件 · 同 cwd 子进程 · 三端内嵌块 · subagent_run · 花费计入父会话 · 生命周期 · 审批。执行者 = 父会话的引擎和模型

P2 路由（影子）

按模型的档位表 · 候选池 · Optimize For · 额度换候选。只记决策，不改执行者，跑两天对比

P3 路由生效

跨 Provider / 引擎执行 · SubAgents 设置 · Providers 页 Tier 列

P4 报告
