协调会话活着、项目的 coordinator_enabled 却是 false 时，升级给你的异常该不该亮

现状（你截图那个项目 FineWeb × Common Crawl → RocksDB 语料库）：项目里 3 条 project_open_item 是 assignee=OWNER、assignee_reason=NO_COORDINATOR，也就是「没人会替你动，它是你的」—— 而列表行、标题栏、needs-you 条三处全暗（服务端的计数读写死只数 coordinatorEnabled=true 的项目）， 只有卡片孤零零画在会话里（①③ 里那两张）。下面 ②④ 是改后的样子，两处一起改： 计数与画卡用同一判据（只要这个会话仍是某个项目的协调会话，它的 owner item 就算在它头上）， 且这一行不再说泛称「Waiting for approval」，而是说那一条自己的话 —— 和横幅、卡片同一批词。

落下的规则（三端同一份）：服务端 sessionWaitingKind 只在「数到的全是同一种、且这种有自己的词」时给出 kind ——OWNER_CONFIRMATION 或 OWNER_ITEM；行/标题栏读到 OWNER_ITEM 就说最久等待那条 item 自己的词 （Escalated to you / Paused / Approve merge to main / Question from coordinator）。 三种情况仍回到泛称「Waiting for approval」：混着 blocked tool call 或 proposal 的行、数到两种 kind 的行、 以及这一版认不出的 kind（旧控制面）。coordinatorEnabled 从此不参与这件事——它是「协调者能不能行动」 （能不能把 item 投递给它），不是「卡片画在哪」；卡片画在绑定的那个会话里，客户端读的就是绑定。
