已有账号开通托管 runner 的入口

背景：生产上线时（任务 34w2jFjODmvhRLHEaXgjA，2026-11-14）发现，只有「没有 runner、也没有 workspace」的账号能在界面上看到「Set up a managed runner」。已有账号（包括 owner 自己的）只能在浏览器控制台里调 POST /api/managed-runner/ensure。服务端本来就允许任何符合资格的账号开通（canEnsure = 开关开 & 环境可用 & 账号未停用 & 符合资格，不看有没有 runner），缺的只是客户端的入口。本板只是设计，不改产品代码。

① 今天：入口只给「一台机器都没有」的账号

端今天在哪里显示托管 runner条件（代码）已有账号看到什么
Web默认落地页 ManagedRunnerLanding；托管 workspace 的输入框上方 ManagedRunnerNoticeApp.tsx DefaultLanding：useManagedRunner(listed && !first && runnerList.length === 0) —— 有 runner 或有 workspace 就根本不读托管状态什么都没有。Settings → Machines 只有自己的机器和「Register a machine」
iPhone / MacMachines & models 列表上方的 ManagedRunnerBannerManagedRunnerLogic.onboarding(display, runnerCount:)：runnerCount == 0 ? display : nil什么都没有
Android新会话的欢迎卡片 WelcomeCard.kt新账号的首个草稿什么都没有；Machines & models 页没有托管内容
共同点：判断「要不要显示」用的是本地的 runner 数量，而不是服务端给的 actions.canEnsure。结果：服务端说「可以开通」，界面却不让按。

② 建议：入口跟着服务端的 display.ensure 走，放在「机器列表」里，三端同一条规则

  1. 没有托管映射、服务端允许开通（kind = setup，ensure = true）：机器列表最上方多一行 Managed runner · Set up，不论账号有几台机器。
  2. 按 Set up：确认框说清楚会多出一台 runner 和一个 workspace → POST /managed-runner/ensure。应答（REQUESTED）已经带 runnerId 和 workspaceId。
  3. 有映射之后：这一行消失，托管 runner 就是机器列表里的一台普通机器，只是它的状态用共享显示的标题（Preparing / Asleep / Failed…），机器页顶部放 ManagedRunnerNotice（Retry、Open Machines & models 都在这里）。
  4. 服务端不给（不符合资格、环境不可用、账号已停用）或功能关闭：已有账号不显示任何托管内容，和今天一样。
候选位置结论
Settings → Machines（机器列表）建议托管 runner 开通后本来就是一台机器，入口和它的状态在同一个地方；任何时候都能找到
Register a machine 页作为第二个入口：页首一句「Or let Orbit run one for you」链接到同一行（见 D1 的 B）
runner 选择器 / 新建 workspace不建议：开通会自己带一个默认 workspace，放在「新建 workspace」里反而多出一个空 workspace 的歧义；选择器只在新建时出现，找不到
