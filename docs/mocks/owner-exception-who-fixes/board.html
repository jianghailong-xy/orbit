业主的例外卡：按「谁来修？」组织，而不是按机制排门

对象：项目里 升级到你（owner）手里的例外待办，以 INTEGRATION_CONFLICT 为例（web ProjectProgressStatus.tsx 的 EscalatedItemCard； Apple ApprovalCards.swift 的 owner item card；Android ExceptionCardView.kt）。今天的卡按机制摆：一列四扇门（修 / 停 / 看 / 结）同列排开、原始 ref 和 SHA、9 个文件全列、两个对不上的钟； 而且从不说它怎么结束——其实它会自己结束：往任务分支推一次就开一代新的落地（docs/project-integration-line-contract.md §2.1），落地成功就由 resolveIntegrationItemsOnLanding（project-open-item.ts ~L1227）把它关掉。「Mark as handled」只用于「工作从别的路到了线上」。

两个情形贯穿全板：(a) 协调者不可达（coordinatorUnreachable：消息送不进去——这里用「它的工作区 mac-mini 被停用」），(b) 协调者可达（2 小时没人动，钟把它交给了你）。 数据：示例项目 Checkout v2、任务 Retry failed webhook deliveries、9 个冲突文件、在协调者手里 2h 56m 后升级、读卡时共等了 3h 1m（真实条目的形状，名字是示例——仓库公开）。 红色编号 = 今天的问题；绿色编号 = 提议的改动。产品文案全是英文（CLAUDE.md §5）。
「今天」按 main 现状画（含 ff4ffab74/c2420ff05：不可达时标题已是「can’t take messages」、必做句不再提「ask the coordinator」；d2bc7fc4f：Ask again 与 Chat about this 读同一个 readCoordinatorReach）。所以提议第 1 点在 (a) 已经落地，本板在它之上做第 2–5 点。

① 今天 · web · (a) 协调者不可达

① 今天 · web · (b) 协调者可达

  1. 1两个钟各说各的。(b) 标题「no one acted on this for 2h 56m」，脚注「waiting 3h 1m · came to the owner at 2h 56m」——同一个 2h 56m 出现两次，第三个数 3h 1m 又是另一回事。读者要自己做减法才知道「到我手里 5 分钟」。
  2. 2一列门，按机制排。修（Open task session）、看（Open landing）、停（Cancel task）、结（Mark as handled）在同一列、同一种「按钮 + 一句后果」的形状里；只有重量在区分它们。卡没回答 owner 第一个问题：这事该谁修？
  3. 3(a) 少了真正的第一步。协调者收不到消息时 Ask again 不画（readCoordinatorReach 的 askable 为假，d2bc7fc4f 起与 Chat 同一个答案），必做句也已不提它，于是卡上的主门只剩「自己修」。但服务端早有路：COORDINATOR_UNAVAILABLE 指向 POST :id/coordinator/rebind（projects.controller.ts ~L896），项目页的协调者卡上也已经有 Enable mac-mini / Change workspace…。例外卡一个都没给。
  4. 4原始事实。refs/heads/project/<id> at <sha> 和 9 个路径全量平铺，占了卡的一半高度，却不是做决定要用的东西。
  5. 5没说怎么结束。只有事实块里一行「After a fix: push to the task branch — Orbit re-integrates and re-checks on its own」，没说事项会自己关；于是 owner 修完还会再按一次 Mark as handled——那是给「从别的路落地」用的门。
  6. 6灰掉的 Chat about this。(a) 一个按不了的按钮 + 一句「can’t take a message right now」，与标题「can’t take messages」说同一件事第二遍。

② 提议 · web

同一张 .project-open-item-card.is-owner，同样的琥珀色、同样的按钮三种重量；只换顺序与分组：标题 → 是什么 → 谁来修 → 怎么结束 → 细节（折叠）→ 分隔线 → 收尾。

② 提议 · web · (b) 协调者可达

② 提议 · web · Details 展开 （(a)(b) 相同）

  1. 1标题 = 此刻的原因（已部分落地），只有一个钟。(a) 的「the coordinator can’t take messages」是 main 上已有的（ff4ffab74），不改；剩下的是 (b)：「no one acted on this for 2h 56m」→「the coordinator didn’t get to it」，去掉标题里的数字；以及读数改成实时（交过来之后协调者结束了，标题就改说 ended——今天 ESCALATED 只在不可达时换句）。钟只剩右上角一个「waiting 3h 1m」；「2h 56m 后交给你」进 Details。脚注整行删掉（「Owner: you」标题已说）。
  2. 2「Who fixes it?」两行：协调者 / 你。(a) 第一行先说为什么它来不了（ProjectCoordinatorCard 的同一句 refusal），主按钮是把它请回来——Enable mac-mini（同一张协调者卡的 fix 标签），旁边 Change workspace…（= rebind）。(b) 第一行是 Ask the coordinator again。第二行永远是「You · Fix it myself」，即今天的 Open task session，换成说人话的名字。
  3. 3一行说它怎么结束（绿色，不是按钮）：Closes by itself once this work lands — push a fix to the task branch and you’re done. 只画在有任务分支的集成类事项上（CONFLICT / CHECK_FAILED / ERROR），取代事实块里的「After a fix」行。
  4. 4事实折叠。标题下一行「Merge conflict · 任务名 → 项目名」；其余收进 Details · 9 files：文件最多 5 个 + 「4 more」、目标分支（项目名 + 短 ref，mono 小字）、到你手里的时刻、Open landing（看，不是做）。
  5. 5分隔线后的收尾组「Already settled?」：Mark as handled（后果改为 The work landed another way. Your reason goes on the record.）与 Cancel task（红色 link，确认对话框不变）。它们是结束这条事项的方式，不是修它的方式。
  6. 6Chat about this：(a) 不再是灰按钮——第一行的状态句已经说了「can’t take messages」；(b) 降为 Ask again 旁边的 link「or Chat about this first」，因为它是「带一句话再交回」的另一种问法（见待定 D2）。

③ iPhone（393 pt）· 今天 vs 提议

iPhone 的门是「按钮在上、后果在下」（doorRow 的 iOS 分支）；今天 Apple 不画 Cancel task（控制台没有这扇门），Chat about this 是常亮的 bordered 按钮（走 composer，不先判断能否送达）。提议沿用同一套按钮样式：主 = borderedProminent，次 = bordered，其余 = plain secondary。

④ Mac（会话面板）· 今天 vs 提议

同一份 SwiftUI；Mac 上 doorRow 把后果放在按钮右边，所以今天的一列门在 Mac 上更像一张表。提议里「Who fixes it?」的两行在 Mac 上是「谁 | 状态 + 按钮」两栏，和 web 一致。

⑤ Android · 今天 vs 提议

Android 今天画 Cancel task（带确认对话框），按钮 48dp 高（Material Button / OutlinedButton / TextButton 三种重量）。提议沿用这三种，只改顺序和分组；「Fix it myself」= OutlinedButton。

⑥ 其它原因下，标题与「谁来修」第一行怎么读

标题和第一行都由同一个实时读数决定（readCoordinatorReach + 协调者状态的 refusal detail + assigneeReason），不再由「它是怎么到你手里的」决定。按钮标签全部复用已有的：协调者卡的 fix 标签、CHANGE_COPY.button、「Start a new coordinator」。
