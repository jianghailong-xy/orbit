「开工被拒」应当看得见：会话页说清为什么没跑，项目页说清缺的是什么

24 小时里的真实一例（项目 34bZ3i4AvgJaaoaw5E9tH，会话 2PLgNAQaH00wZ56CN8J03M）： 两个 07:45 派发的任务共用一条前置「把 OpenCode 加进 InstallEngine」，它 07:45:28 落地在 main 上， 于是派发按 P4 依赖闭包把起跑基线钉到项目的集成线 refs/heads/project/…； 而这条线从未被创建（项目三次落地作业全部 CHECK_FAILED，工作其实都并进了 main）， runner 的 git fetch 拿到 fatal: couldn't find remote ref， 会话停在 sourceState=REFUSED 空转 —— 而两个客户端都不读这一列， 于是你看到的是一句永远不变的 Starting。三格：今天 / 我建议的会话页 / 我建议的项目页。

根因那一半（①，不在这张图上）：P4 的基线没有 P5 的护栏。 source-selector.ts:247 的 P4 直接钉 codebase.integrationRef； 只有 P5（:269）有 integrationLineHasLanding ? integrationRef : upstreamRef 的两种写法。 契约 §4.1 的 v1.1 说明（project-source-contract.md:199）已经把这个道理讲全： 项目分支要等第一条落地回执才被创建，在那之前它与 upstream 逐字节是同一棵树 —— P4 与 P5 读的是同一条线（D5 说二者结构互斥，不是两条），这句话对 P4 同样成立。 所以修法是：P4 在 integrationLineHasLanding === false 时取 upstreamRef 的 tip， requiredContains 不变（本例里前置的 decda058 就在 main 上，取 main 完全满足）。 这是契约变更（§4.1 的 P4 行 + v1.2 记录 + source-selector.spec.ts 的负向用例），按 SR17 先改文档再改代码。
