Claude Code 跑在 OpenAI key 上：由 Orbit 自己的网关翻译协议

设计见 docs/claude-engine-openai-gateway-design.md。① 今天和新方案对照 · ② 组件和数据 · ③ 一个回合的时序 · ④ 安全、额度和故障 · ⑤ 待定 · 要你拍板，和落地顺序。界面文案仍是英文。

① 今天 vs 新方案

今天，想在 Claude Code 里用 GPT 的人得自己架 LiteLLM 之类的代理，再把地址和 key 填进 Orbit；OpenAI key 在 Orbit 里只能跑 Codex 和 OpenCode。新方案里，添加 OpenAI key 就是全部配置，翻译由 API server 完成，key 不再下发到 runner。

今天

用户自己部署 LiteLLM / claude-code-router维护进程、端口、模型映射、haiku 槽位、上下文窗口
↓
在 Orbit 里加一把「Anthropic 方言」的自定义 keybaseUrl 指向自己的代理，模型手填 GPT id
↓
runner 拿到 key 和地址，Claude Code 直连代理agent 跑的命令读得到 key；代理挂了会话直接 FAILED
↓
报错、额度、用量 Orbit 都看不见429 / 额度用尽是代理自己的措辞，auto-retry 认不出
要自己运维代理key 下发到 runner额度和用量不可见OpenAI key 选不了 Claude Code

新方案

在 Infrastructure 页添加 OpenAI key（和今天一样）key 的 engine 列表变成 Codex · Claude Code · OpenCode，默认仍是 Codex
↓
新建会话：选 Claude Code + GPT 模型派发时铸一个会话 token orbit-gwk-…，地址指向 /api/gw/anthropic
↓
runner 只拿到 Orbit token，拿不到 keyClaude Code 照常发 Anthropic Messages 请求
↓
API server 网关：验 token → 翻译 → 用 key 调 OpenAI → 流式翻译回来报错按 Anthropic 格式返回，auto-retry、额度、计费照常
零配置key 留在服务端复用 Codex 网关的选 key / 限速 / 计费无状态，多 API server 可用

④ 安全、额度和故障

key 的边界比今天任何一种 key 会话都紧；新风险是服务端要按 key 行的地址发请求。报错一律换成 Anthropic 的格式，让 CLI 自己的重试和 Orbit 的 auto-retry 照常工作。

key 和 token
  • key 只在 API server 解密，只用于上游请求；不进 runner 环境、会话 env 和日志。今天 Claude Code 跑的命令读得到 key（wiki 34dgAezaocJUDulv5Kc40），新路径读不到。
  • token 只认 (会话, key, 用户)，只能访问网关的两个路径；库里只存哈希。
  • 吊销：会话结束、key 删除 / 停用 / 轮换、账号停用。最坏情况是被偷的 token 在会话结束或 7 天内花这把 key。
  • 列进 tenant-isolation-runner-cases.ts，和 gw/codex 并排。
新风险：服务端出站请求（SSRF）

今天 key 的 baseUrl 只有 runner 会去连；新路径里 API server 自己连。一把指向内网地址的 key 会让服务器替人访问内网。

建议（D3）：先只放行 api.openai.com，加上管理员在环境变量里列的主机；不跟随重定向。

每个回合是一条经过 API server 的长连接：只转发、不缓冲，每条流最多留一个事件；P2 用 20 个并发会话量内存和连接数。

报错怎么翻
OpenAI 回网关回给 Claude CodeOrbit 另外做什么
401401 authentication_error，说是哪把 key标 key INVALID，和 gw/codex 一样
429 rate_limit_exceeded先在网关里等（rateLimitWait 的上限），还不行回 429 rate_limit_errorCLI 自己重试
429 insufficient_quota429，用 Orbit 额度处理认得的措辞（P2 对着 quota-limit-retry 定）记 key 用尽到重置时间（spentUntil）
5xx / 过载529 overloaded_errorauto-retry 认得「529 … overloaded_error」，会重发
403 / 模型不可用403 permission_error / 404 not_found_error提示里说 key 和模型名
context_length_exceeded400「prompt is too long: …」CLI 自己压缩

⑤ 待定 · 要你拍板

每项给了建议。D1、D3、D4 决定架构和风险，其余可以先按建议走。

D1 谁来翻译

A：API server 里自己写的翻译模块 · B：Orbit 运维一个 LiteLLM 容器，网关仍管 token、key 和计费

建议 A：Compose、Kubernetes、自托管都不多一个容器；报错、额度、haiku 映射都在自己代码里。LiteLLM 的映射当测试参照。

D2 上游用哪个 API

A：Responses · B：Chat Completions

建议 A：OpenAI 现行 API；加密推理能跨回合带着；Codex 网关已经在读它。

D3 哪些 key 能走网关

A：主机是 api.openai.com，加管理员列出的主机 · B：所有 OpenAI 方言的 key，拦掉内网地址

建议 A：先堵住 SSRF；有人要 Azure 等兼容主机再放到 B。

D4 ChatGPT 登录（Codex 账号池）能不能跑 Claude Code

A：不提供 · B：以后做成可选

建议 A：ChatGPT 的 Codex 后端不是公开 API；多用户托管服务上，封号风险落在你身上。

D5 Claude Code 的网页搜索（Anthropic 服务端工具）

A：首发提示「这个模型不可用」，P3 再映射到 OpenAI 的 web_search · B：P1 就映射

建议 A：它是单项最大的翻译工作，其余都不依赖它。

D6 怎么上线

A：部署开关，默认关，P3 质量对比过了再开 · B：P1 就开

建议 A：确认好用之前，engine 列表里不出现它。

D7 OpenAI key 的默认 engine

A：仍是 codex · B：改成 claude

建议 A：不选 Claude Code 的人什么都不变。

D8 这类会话的费用显示

A：用网关按 openai-prices 算的 · B：用 CLI 自己报的

建议 A：CLI 不知道 GPT 的价格，它的数是猜的。

落地（按依赖排，后一期依赖前一期）
P0 摸底

录 runner 自带版本的 claude 发给假 Anthropic 端点的一切：路径、头、effort 字段、haiku 请求、count_tokens、超长措辞；照录制写翻译模块；脚本里对 OpenAI 跑通。

完成：录制的 10 回合会话（并行工具、子 agent、跨回合推理、一次压缩）经翻译模块对 OpenAI 跑完；设计文档 §8 的问题都有录制的答案。

P1 接线

路由、token 表和迁移、派发环境、兼容表（开关后）、契约 §2.1 / §4.2、租户隔离用例。

完成：开关开时，真 runner 上 OpenAI key + Claude Code 的会话跑通；开关关时，所有现有会话的派发环境和 engines 逐字段不变。

P2 生产行为

报错和额度映射、限速等待、key 标记、用量计费、count_tokens、haiku 映射、负载。

完成：④ 表每一行都有用真 CLI 经网关打假上游的测试；20 个并发会话内存在预算内。

P3 质量和发布

同一组任务分别跑 codex + GPT 和 claude + GPT；网页搜索映射（D5）；文案、文档、连接表单那一行。

完成：你看对比结果，决定开不开开关。
