数据、证据绑定、保留期

  1. 执行会话 file_upload ./shots → 一个文件夹包加 8 张截图；file_upload report.json --as test-report → 测试摘要。
  2. task_evidence_submit：{kind: "FILE", ref: 包 id}，日志照旧引用工具调用。
  3. 服务器解析：文件是你的、在本任务的会话里上传 → 写入 sha256 → 进证据摘要。引用别的任务的文件直接拒绝。
  4. 投递给协调者：列出每个文件的名字、大小，和现成的 file_fetch 调用。
  5. 协调者按需 file_fetch，看图，判 Confirm done 或退回。
  6. 保留期跟着变：被确认的这一版留到任务删除；之前被退回的版本 30 天后过期。

已定、待定、落地

11-02 已定（「按建议」）
  1. 自托管默认存本地卷，Postgres 只放元数据；S3 兼容存储可选。
  2. 保留期：被取代的证据 30 天，探针和临时输出 14 天。
  3. 先显式上传（file_upload），提交闸门兜底（M3）。
  4. 闸门先拦再问，不自动上传（M3）。
  5. 设计稿批准先做提示（M4）。
落地（按代价排）
  1. 存储层 + 旧附件迁移服务端
    用户看不出变化，先上线，看迁移和备份。
  2. agent 接口runner + 服务端
    file_upload/fetch/list 和指引。
  3. 证据 FILE 引用 + 判定者取文件服务端 + runner
  4. 证据卡片Web → Apple → Android
  5. 测试报告摘要服务端 + 三端
  6. 保留清理、用量、备份同步服务端 + compose

1–3 做完，agent 就不必往仓库放证据；4 让你在 Orbit 里直接看图。

待定 · 要你拍板

1. 存储对象怎么来

A（推荐）· 升级现有附件链接继续是 orbit-attachment:，加 sha256 和存储后端。
B · 另建一套新表、新链接、新路由。
推荐 A：三端已经会渲染这个链接，runner 已经会上传和改写，分享链接和租户隔离测试都已覆盖；B 要把这些全部再做一遍。

2. 判定者怎么拿文件

A（推荐）· 按需取投递消息里列出文件和现成的 file_fetch 调用。
B · 投递时全部预取放进判定者的 uploads 目录。
推荐 A：p90 的证据有 142 个文件，判定通常只看几张；B 每次投递都要搬全部字节。

3. 到期后什么时候删字节

A（推荐）· 先打墓碑，宽限后再删宽限 7 天，且不早于 Postgres 备份的保留期。
B · 到期立即删
推荐 A：恢复备份后，元数据还能找到字节；误判过期也有挽回的时间。

4. 单文件上限

A（推荐）· 保持 25 MiB上传改成流式写盘，以后调大只改配置。
B · 现在就提到 100 MiB 以上并做分片上传。
推荐 A：HEAD 里没有文件超过 25 MiB，最大的 trace 包已经按摘要处理；分片等真有需要再做。

后面几步建在同一个存储上：M3 提交闸门提示 file_upload；M4 每版设计稿是一个文件夹包；M5 CI 用只能写文件的 token 上传；M6 被排除路径里的新文件转成 Orbit Files（顺带解决 git add -A 返回 1）；M7 把 docs/evidence 导入。
