已装机的机器：每个账号的 runner 用自己的名字、跑自己的 ~/.orbit/bin/orbit

设计见 docs/hostd-per-account-runners-design.md。① 今天和新方案对照 · ② 一台机器上的文件和进程 · ③ 注册和升级的时序 · ④ 已装过机的机器怎么迁移 · ⑤ 待定、验收标准和落地

① 今天 vs 新方案（只说执行过 orbit host setup 的机器；没装机的机器不变）

今天，装机后所有账号的实例都按 uid 命名，跑同一份 root 的 /usr/local/bin/orbit，由 hostd 统一升级。新方案里，实例按用户名命名，跑账号自己的副本，自己升级自己；hostd 只负责免 sudo 的启停。

今天

管理员执行一次 sudo orbit host setup装 hostd 和模板 orbit-runner@.service（User=%i）
↓
实例名是 uid：orbit-runner@1000.service看单元名认不出是谁的 runner
↓
所有实例跑同一份 /usr/local/bin/orbit账号自己 ~/.orbit/bin 里的副本用不上
↓
runner 写不了这个文件 → 请 hostd 升级hostd 下载、校验、替换，再逐个重启所有实例
↓
root 自己的 runner 先换了文件时hostd 回 updated:false，账号的实例停在旧版本，直到有人手动重启
实例名是数字所有账号共用一份二进制升级要绕 hostd可能卡在旧版本

新方案

管理员执行一次 sudo orbit host setup（不变）模板改成 User=%I，ExecStart 指向账号自己的二进制
↓
实例名就是用户名：orbit-runner@alice.service用 systemd 自己的转义：test-user → test\x2duser，可还原，不会撞名
↓
每个实例跑账号自己的 ~/.orbit/bin/orbitExecStart=/bin/sh -c 'exec "$HOME/.orbit/bin/orbit" run'
↓
runner 自己升级自己的副本和没装机的机器走同一条路：不经过 hostd，不需要 root
↓
hostd 只管启停，外加它自己那份 /usr/local/bin/orbitroot 仍然只执行 root 自己的文件
一眼认出是谁的 runner和没装机的机器同一种布局升级不经过 root不会卡在旧版本

② 一台机器上的文件和进程

root 的东西只剩 hostd 和它跑的那份二进制；每个账号的 runner、凭据和二进制都在自己的家目录里。新 改动，不变 保持，去掉 删除。

一台执行过 orbit host setup 的 Linux 机器

注册之后账号不再需要 root。hostd 只看文件在不在，从不执行、读取或写入账号家目录里的东西。

④ 已经装过机的机器怎么迁移

旧的 orbit-runner@1000 在新模板下也能跑：User=1000 被 systemd 当成 uid（已实测纯数字 User=）。所以迁移前后都不会断，迁移只是把名字和二进制换过来。

迁移前
  • orbit-runner@1000.service
  • 跑 /usr/local/bin/orbit run
  • 升级靠 hostd
→
管理员：换二进制，重跑一次 setup
  • sudo install -o 0 -g 0 -m 0755 <新版> /usr/local/bin/orbit
  • sudo /usr/local/bin/orbit host setup --server <url>
  • setup 重写模板；逐个处理 orbit-runner@<数字>（待定 3 选 A）：账号已有副本 → 先 drain 再迁到 @<用户名>；没有副本 → 列出来，附上该账号要跑的那一条命令
→
迁移后
  • orbit-runner@alice.service
  • 跑 /home/alice/.orbit/bin/orbit run
  • runner 自己升级
没装过机的机器

什么都不用做：本来就是 orbit-runner-<用户> 跑账号自己的副本。

生产机（今晚刚装机）

它唯一一个账号的 @<uid> 迁到 @<用户名>，跑它 ~/.orbit/bin 里已有的那份；root 的 runner 不动。这一步要你确认后才做。

回滚

旧版 hostd 不认识 @<用户名>：管理员先 systemctl disable --now 这些实例，再用旧版本重跑 setup（写回旧模板），然后按旧方式启用 @<uid>。

⑤ 待定 · 要你拍板，建议的验收标准，落地

待定 1：模板怎么指向各账号自己的二进制

A：模板里用 shell：exec "$HOME/.orbit/bin/orbit" run。systemd 按 passwd 设 $HOME；一份模板管所有账号，exec 之后主进程就是账号的二进制。

B：hostd 给每个实例写一个 drop-in，写绝对路径。systemctl cat 一眼看到路径，但 hostd 要多管一批文件。

C：机器级二进制当启动器，缺副本时先装再 exec。每次启动都要执行 root 的那份，它就得继续对所有账号可执行。

推荐 A：最少的东西，最直接。

待定 2：hostd 的 update 动作留不留

A：留着，只管 hostd 自己那份。runner 升级完通知一次，hostd 校验后换掉 /usr/local/bin/orbit，不重启任何实例。

B：删掉。机器级二进制由管理员 sudo /usr/local/bin/orbit upgrade 升级，或由跑它的 root runner 顺带升级。

推荐 A：hostd 不用人管也保持最新。

待定 3：已装过机的机器怎么迁移

A：重跑 setup 时一起迁：有副本的账号逐个迁（先 drain），没副本的列出来并给出命令。

B：setup 不碰实例，每个账号下次 orbit register 时自己迁；那之前，它的 uid 实例跑新模板，没副本就起不来。

推荐 A：管理员一条命令迁完，不会有人掉线。

待定 4：root 自己的 runner

A：保持旧单元不动。它若跑 /usr/local/bin/orbit，自己升级时顺带把 hostd 那份也换新；两边都是 root 的文件。

B：也改成跑 /root/.orbit/bin/orbit，和没装机的机器一致。要重启 root 的 runner，在留着 update（待定 2 选 A）时没有额外好处。

推荐 A。

建议的验收标准（你来改）
  1. 已装机的机器上，两个账号（一个名字带 -，一个带 .）免 root 注册；runner 是 orbit-runner@<转义名>.service，各以自己的身份跑自己 ~/.orbit/bin/orbit。
  2. 已装过机的机器重跑 setup：有副本的 orbit-runner@<uid> 都迁到 @<用户名>，任何时候没有一个账号同时有两个 runner；没迁的账号连同要跑的命令被列出来。
  3. 发布新版本：每个 runner 免 root 升级自己的副本；hostd 升级自己那份、不重启实例；root 从不执行下载物，也不执行账号能改的文件。
  4. 已装机的机器上跑 install.sh：装进当前账号的 ~/.orbit/bin，不需要 sudo，从不写 /usr/local/bin/orbit。
  5. scripts/hostd-e2e.sh、scripts/install-sh-e2e.sh 和 runner-go 全部测试通过。
  6. 生产机：账号的 runner 是 orbit-runner@<用户名>，跑它自己的副本；root 的 runner 不变。
落地（按依赖排）
  • P1runner-go：模板、转义实例名、hostd 各动作、缺副本时拒绝、迁走旧单元
  • P2runner-go：register 放好账号的副本；update 只管 hostd 那份；能写的安装不再委托 hostd
  • P3install.sh：已装机的机器也装进账号家目录，去掉机器级分支；e2e 场景
  • P4hostd-e2e（名字、各自的 exe、迁移、升级）和 self-hosting 文档
  • P5发版，然后迁生产机（你确认后）
  • 1为什么当初选 uid：orbit 自己的转义有损，alice.b 和 alice_b 都变成 orbit-runner-alice_b。systemd 自己的转义可逆，换成它就不会撞名，也就不需要 uid 了。
  • 2为什么不能直接写用户名：%I 还原时把 - 当成 /，test-user 会变成 test/user。实例名必须先经过 systemd-escape。
  • 3为什么不用 %h：系统单元里的 %h 是 root 的家目录，不是 User= 那个账号的。$HOME 由 systemd 按 passwd 设置（实测 User=daemon 得到 /usr/sbin；家目录是 /nonexistent 的账号没有 $HOME，hostd 拒绝它）。
  • 4为什么 hostd 还要一份 root 的二进制：hostd 以 root 运行，root 不执行任何账号能改的文件，所以它跑的那份仍然要过 checkMachineBinary。
