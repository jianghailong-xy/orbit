有依赖的批次：按层排，每行写清在等谁

一批任务之间有依赖时，确认页把任务按层分组：第几层 = 它在本批里最深的前置 + 1， 和 Web 依赖图的分层是同一个算法（buildBatchGraph），所以两端看到的先后顺序一致。 层与层之间用左侧细线串起来表示先后；同一层的任务互不依赖，可以并行；每行写全它在等哪几条。 B、C 用的是一批示例任务（菱形依赖：1 → 2、3 → 4，第 1 条还等一条已有任务）。

规则

  1. 分层：第几层 = 它在本批里最深的前置 + 1；在本批里没有前置的都在第 1 层。同 Web 的 buildBatchGraph（服务端保证引用只能指向更早的条目，所以不会有环）。
  2. 编号：按层从上往下编，前置的编号永远比等它的小；任务页标题「Task 4 of 4」用同一个编号。
  3. 每行写全前置：「Waits on 2 3」。只等本批以外的写「Waits on a task outside」。
  4. 并行：同层的任务互不依赖，层标题写「N in parallel」。
  5. 没有依赖：本批内部一条依赖都没有 → 不分层，就是 ② 的普通列表。
  6. 大批次：只画服务端给的前 12 条，末尾「+N more」；后果数字始终按整批算。
  7. 代码：分层算法从 Web 的 batchGraph.ts 搬到 OrbitKit（替掉 batchTreeRows），iOS 视图按层分组渲染；不需要改服务端（除非要做第 5 种）。

顺带发现

  • 服务端预览还返回 scheduled（定时，到点自己跑）和 awaitingProjectStart（等项目开始才跑）两个数，iOS 和 Web 都没显示。
  • 一批任务如果全落在这两类里（比如往还没开始的项目里建任务），iOS 的后果卡一行都没有，Web 只写「0 start running within the minute」，看上去像什么都不会发生。
  • 建议后果卡补上这两类，图标用时钟 / 旗子之类，文案另定。
  • 形状那句话：只要是两层，两端都写「N in parallel after 1」（N 取最宽那层）。这只对「1 条之后并行 N 条」成立；像第 5 张卡「3 条之后接 1 条」，代码会写成「3 in parallel after 1」，说反了。板子上画的是改过后的「2 levels, up to 3 in parallel」：两层且第 1 层只有 1 条时才用 after 1 的说法。
