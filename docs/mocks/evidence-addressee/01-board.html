② 原则一：标准由服务器绑定，agent 不再抄

任务按哪个标准判定，完全由任务行决定。服务器提交时本来就快照了这份标准（criterionRevision），agent 抄的那份是只会出错的冗余输入。

今天信封 4 个必填字段

{ claim: "…", criterion: { key: "5qKy…", text: "Assistant prose…" }, checks: [ … ], gaps: [ … ] } → 服务器拿 agent 的引用 ⇄ 当前标准 比对

引用错 = 判不了，但仍被接受、静默落地。

改后agent 只交它做了什么

{ claim: "…", checks: [ … ], gaps: [ … ] } 服务器在提交事务里写入： standard = 任务声明的验收项 ?? 任务自己的 acceptanceCriteria → 判定时比对 快照 ⇄ 当前标准

"引用错了"在结构上不存在。标准被改写后旧证据仍判不了（按内容绑定的语义不变）。旧 runner 发来的 criterion 迁移期接受并忽略。

⑤ 原则四："没验证"不等于"通过"

同一个项目暴露的另一类问题，与死锁无关，由你决定是否同期做。

今天

· D 的条款要求"copy parity with Swift and web"，但 D 只依赖服务端任务 A2。Swift 一致性测试因对方文案还不存在而 skip，结果仍是绿的。

· 协调者把它当"已接受的缺口"确认了。

· W 自己写明没做"审批回答 422 时的 Retry / Send as written"，这是项目决策 1A、3A 的要求。

改后

· 拆任务指引：验收条款只能写依赖链内能证明的内容；跨任务一致性交给汇总验证任务。

· gap 结构化：{text, criterionClause?, followUpTaskId?}。命中条款却没有后续任务 id 的 gap，判定入口拒绝 CONFIRM。

· 仓库约定：一致性测试在对方文件缺失时失败，而不是 skip。
