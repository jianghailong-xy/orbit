项目栏：从“一行一个会话”改成“一行一个任务”，再加一个“改动”页

右侧项目栏（及手机的底部弹窗）现在按会话列：同一任务的重跑、同步合并、平台的判定会话各占一行，按“昨天 / 2–7 天前”分组，看不出谁在等你、谁已在 main、改了什么。
方案 A：一行一个任务，按状态分组，每行带改动量；重跑与判定收进任务行。方案 B：栏顶加“任务 | 改动”两个标签，“改动”像 Codex 的审查面板，列项目分支对 main 的文件差异。 图里数据是样例（“Move search to the new index”）；界面文字为将上线的英文，标注为中文。

待定 · 要你拍板

1. 先做哪个

  • 先 A 后 B推荐：A 基本只改前端（会话本来就记着属于哪个任务，每个会话的改动统计也有）；B 要新增一个“项目分支对 main 的 diff”接口，工作量中等。
  • A、B 一起：一次到位，但 B 的接口会拖慢 A 上线。

2. 平台的判定会话（Judgment）怎么放

  • 收进任务行推荐：在 “3 runs ▾” 里显示“2 judgments by Orbit”，展开可点开。
  • 完全不显示：最干净，但想追查“为什么被退回”时要去任务页找。

3. Changes 页默认范围

  • Project branch vs main推荐：整个项目到底改了什么，未合入的单独标出。
  • Last landing：只看最近一次合入的改动，适合跟进中途。

落地（按代价排）

  • Web A：项目栏的数据从“项目的会话”改成“项目的任务 + 各自的会话”；去掉前缀、按状态分组、每行改动量（取各任务最新运行会话的分支统计）、多次运行收起。手机弹窗同一块内容。
  • 服务端 B：新增“项目分支相对 main 的文件差异”接口（文件列表 + 每文件加减 + 由哪些任务改动 + 是否已在 main），以及按文件取 diff。
  • Web B：Changes 标签、范围与任务过滤、文件列表、复用现有 diff 抽屉。
  • iOS / Android：跟进 A、B 的同一布局（各一个任务，先 iOS 再 Android）。
