每一项都给了推荐。你回「按推荐」，我就按推荐写进设计文档、建任务；哪项想改，直接说编号。

#问题方案 A方案 B推荐
D1放开到哪里私聊和群都放开。同事第一次找机器人，多半是私聊。只放开群，同事私聊照旧被拒。A
D2怎么确认对方「有权限」每条消息由 Orbit 自己再向飞书核实一次：发送者在不在应用的可用范围里。要多申请一个只读权限，接口名和权限名在真实租户上核实。查不到就当作不在范围里处理（见③C 第一句）。只要飞书把消息发来了就受理。但如果飞书把可用范围以外的人在群里的 @ 也发过来，就等于群里任何人都能用。A
D3别人开的会话用什么设置一组默认设置：workspace、模式、上限。connect 过的群用它自己的设置。每个人单独一套设置。太重，也违背「不用逐一授权」的初衷。A
D4默认权限模式Auto，和你 11-18 对群确认页的要求一致。Default：每条命令都要你批。人一多，你的私聊会被审批卡刷屏。A
D5默认上限每人同时 1 个、每天 10 个；所有人合计同时 3 个、每天 50 个。数字都能改。只设合计上限。一个人就能把一天的额度用完。A

风险与对策

  • 可用范围在飞书后台改，不经过 Orbit。有人把它设成「所有员工」，全公司都能让你机器上的 agent 干活。对策：
    • 放开后，卡片和 Groups 卡上都写明后果；
    • 别人开的会话只在一个独立 workspace 里跑；
    • 有两层上限；
    • 群可以单独关掉；
    • 一键切回「Only you」。
  • 审批只给你。别人的会话里，危险动作还是要你点头（Auto 模式下由 agent 判断哪些要问）。
  • 回传只有正文。对方拿不到工具输出、文件和 Orbit 链接。这和今天的群一样。
  • 跨账号隔离不变。一个账号的应用只作用于这个账号。外部群照旧不服务。

落地（按代价排）

  1. 飞书卡片（S）：你私聊里的审批卡加一行「Started by <name> in <group>」。这一项单独做也有用：今天群里发起的会话也受益。
  2. Web（M）：「Who can use the bot」卡片，以及 Groups 卡里「Uses the settings above」的那些行。
  3. 服务端（L），包括：
    • feishu_app 加访问策略的字段，迁移号取 0800 以上，默认 Only you；
    • 别人私聊、没接入的群，改成按策略开会话；
    • 核实发送者（D2）；
    • 每人和合计的上限计数；
    • 单独关掉群；
    • 英文回复；
    • 所有者通道（PAT 403）；
    • 普查，以及覆盖幂等、跨账号、超限零写入的 pg spec。
  4. 真实租户核实（要你来做）：
    • 可用范围以外的人在群里 @，飞书会不会把消息发过来；
    • D2 的接口在你的租户上能不能用。
