已拍板：产品支持远端通道 · runner 走 https://orbitd.io · 所有账号都给 · 10.66.0.3 上的活由 workstation runner 会话来做。下面是 ① 今天 和 ② 建议的新结构。

隔离提醒（你已接受）：所有账号的容器和 10.66.0.3 共用内核。这台机器上还有 Nextcloud 数据、5 块 14.6 T 盘上的 NFS/SMB 共享，以及带你引擎登录态的 root runner。内核/容器运行时一旦被突破，这些都暴露；防火墙只挡网络路径，挡不住这条。

③ 一个账号的 runner 怎么起来（时序）

  1. 账号登录 → prod 的 manager 按 profile 申请：GET http://10.66.0.3:<port>/v1/info（检查 instanceId、镜像、主机容量）
  2. PUT /v1/volumes/mr-data-<uuid> → PUT /v1/credentials/<uuid> → POST /v1/containers（防火墙 status.json 必须是 enforced，否则 503 等待）
  3. 容器在 10.66.0.3 上启动，读 bootstrap 卷里的凭据，用 https://orbitd.io 注册、用 wss://c1.link.orbitd.io 建 link
  4. READY → 接会话；空闲 1 小时 → manager 让它睡，容器删掉、卷保留，算力释放
  5. prod 发版后：协调者在 workstation 上开会话跑 remote-host upgrade <sha>（D3），新代际的容器用新镜像

落地（按依赖顺序，每步依赖上一步）

  1. 通道：私网地址监听 + allowPeers，配置校验和单测
  2. apiserver：remote profile、私网通道 URL、https serverUrl 规则、D2 的镜像模式，单测
  3. 通道主机套件 + /upgrade + 文档，在 HPC 上做两台主机的实验室验证
  4. 生产上线（要你点头）：workstation 会话在 .3 上 install → token 和 profile 拷到 prod → ORBIT_MANAGED_RUNNERS_ENABLED=true → 重建 apiserver → 第一个账号的 runner 到 READY 并跑通一个会话。回滚 = 开关改回 false 再重建（卷保留）

D1–D4 · 已定：全按推荐（A）

D1 通道传输 HTTP + token 走 wg1，只监听 10.66.0.3，allowPeers 只放 10.66.0.1。WireGuard 本身加密并认证对端。已选 再加一层 TLS（固定自签证书）。能防一个被攻破的 wg1 对端伪造 10.66.0.1，代价是多一张证书要轮换。
D2 镜像归属 通道主机负责镜像。prod 的 profile.json 写 "image": "channel"，apiserver 用通道报告的镜像 ID，继续校验 instanceId。一次升级只改一个文件。已选 保持两边都写死镜像 ID。每次 .3 升级后要把新 ID 拷到 prod 并重建 apiserver；漏一次，所有新 runner 都起不来。
D3 通道主机怎么升级 每次 prod 发版后，协调者在 workstation runner 上开会话跑 remote-host upgrade <sha>，用刚部署的提交。已选 通道主机定时跟随 prod（读 /dl/version.json，变了就构建）。不用人管，但构建会在不确定的时间压到这台机器上。
D4 10.66.0.3 给多少算力 默认推导：主机减去四分之一 = 6 核 / 约 46 GiB；每个 runner 2 核 / 4 GiB → 同时醒着 3 个，最多 8 个容器；睡着的不占算力。已选 写死一个更小的池：4 核 / 16 GiB（同时醒 2 个），给 Nextcloud 和 root runner 多留余量。

⑤ 多台 Docker 机器一起提供算力

数据模型已经有一半：每个托管 runner 的记录都存着它所在的位置（cluster_key + namespace = 通道 instanceId），容量池也是按位置一行。卷是本机 Docker 卷，所以 runner 跟着卷走，建在哪台就留在哪台。
