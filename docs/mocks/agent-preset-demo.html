Agent × Workspace → Session

把 Agent 这个词还给它该指的东西：一个跨机器、无路径、可复用的预设。Workspace 说"在哪"，Agent 说"怎么干"，Session 是这一次真的跑起来。

核心流程：选 Workspace，再选 Agent

左侧层级不变（Runner ▸ Workspace ▸ Session）。Agent 是新的一枚 pill —— 选中它会填充 Mode / Model / Effort，而不是锁死它们。

关键取舍：预设填充，不是预设锁死。 选了 Reviewer，三枚 pill 变虚线紫框表示"继承自 Agent"；你改其中一枚，它变实线蓝框 仅本次会话，Agent 本身不变。改不了的预设是笼子，不是预设。
还没定的：已有的 @mention 现在指 workspace（在哪跑）。加了 Agent 之后 @reviewer 更像在指 Agent。建议保留 @ 指 workspace，Agent 只走 pill —— 否则一个符号两个含义，正是我们刚花力气拆开的那种毛病。

Agent 库 —— 账号级，不挂在任何一台机器下

这是它和 Workspace 最大的区别，所以在侧栏里它不在 Runners 分组内。同一个 Reviewer 在你三台机器的任何一个检出上都成立。

为什么工具白名单可以放在 Agent 上，却不能放在 Workspace 上。之前的结论是"工具名是运行时相关的，而 provider 是 per-session 绑定，目录层不知道会用哪个运行时，写下去校验不了"。Agent 钉了模型 ⇒ 钉了运行时 ⇒ 工具名此刻是可知、可校验的。这一刀正好把那个反对意见解掉了。

Agent 编辑器

注意这里没有路径、没有机器、没有 git 设置 —— 那些是 Workspace 的。一个字段只属于一个实体，这是整个拆分的检验标准。

仓库 ~/orbit/CLAUDE.md
这个代码库怎么工作、约定是什么。
随仓库走，进版本库，换谁来都适用。
Agent Reviewer
我这次要你怎么工作。
跟人走，跨机器，换仓库照样成立。
这两者不重复，是正交的。之前我说"DB 里的 per-directory system prompt 在重复盘上的 CLAUDE.md"——那个批评对目录级的人设成立，对角色级的不成立。CLAUDE.md 回答"这个代码库需要什么"，Agent 回答"我要你以什么方式工作"。9 行里只有 1 行设了 systemPrompt，恰恰因为挂错了地方。
迁移：现存 workspace 里设过 systemPrompt 的（只有 wikids 一个）自动升成一个同名 Agent；其余全部落到 Default。任何人不做任何事，行为不变。

为什么值得做：你的名字里已经写满了缺失的维度

真实数据。今天一个实体同时背着"哪个项目""哪台机器""什么角色"，只能靠名字后缀编码。

名字回到只说一件事：orbit 就叫 orbit，在哪台机器由 @runner 说，用什么角色由 Agent 说。5 个 workspace × 4 个 agent = 20 种组合，写 9 行配置。
老实说代价。这是加一个实体，不是省一个。多一次选择（虽然有 Default 兜底）、多一张表、多一层继承要在三端渲染"这个值从哪来"。只有当你真的会复用角色时它才回本 —— 如果你永远只用 Default，这一层就是纯负担。所以我建议：先只做 Agent 库 + 组合器 pill，不动任务指派、不动 @mention、不做共享/市场，用两周看你自己建不建第二个 Agent。建了再往下走。
