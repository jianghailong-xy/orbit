Runner 上报 CPU / 内存 / 硬盘 —— 设计图

现在 runner 只报一样东西：每个工作区目录所在那块盘还剩多少，客户端从里面挑最紧的一块画成 Capacity 里的 Disk 条。CPU、内存一个数都没有，也没有历史。

HPC 今天 12:03 的真实状态：24 核 load 27.9；14 GB 内存只剩 2 GB 可用，swap 用了 22 / 43 GB；开机 7.5 天内核因内存不足杀了 33 次进程，昨天 16:30 那次把 runner 一起停掉了（服务是 OOMPolicy=stop），3 分钟后才回来；/ 897 / 915 GB。这些在 Orbit 里一个都看不到，只能 ssh 上去查。

改后 · Web

只加三块，不改现有布局：机器卡片头上三根小条；机器页主栏最上面 Resources（现在的数 + 曲线）和 Using It Now（谁在用）；侧栏 Capacity 的 Disk 一行展开成 Disks（每块盘一行）。下面三张都是真实页面，把新的部分插进去截的。

  1. 1CPU / Mem / Disk 三根条，每台机器对齐在同一列，扫一眼就能比。≥ 90% 变琥珀；内存 24 小时内有 OOM 记录就是红色；Disk 取 Orbit 会写的盘里最满的一块，低于 Keep Free 时琥珀（和今天的磁盘提醒同一条规则）。
  2. 2第三行提醒多一种：Out of memory 4× in 24 h，红色，排在磁盘前面。
  3. 3离线的机器：CPU、内存是「此刻」的数，离线就写 —；盘留最后一次读数（灰）——关着机盘不会自己变空。
  1. 4Needs Attention 新卡 Out of memory（红）：几点、几次、runner 有没有因此掉线、现在用了多少。按钮 Lower Max Concurrent 跳到 Capacity 的输入框（和 Set a Reserve… 跳到 Keep Free 一样）。
  2. 5Resources：每个指标一行，左边是现在的数和一句话，右边是曲线。内存行带 swap 虚线和 OOM 红三角；磁盘行画 Keep Free 虚线（纵轴 95–100%，标在右上角）；斜线阴影是 runner 离线（昨天 16:30–16:33）。
  3. 61h / 24h / 7d：分别 1 分钟、5 分钟、30 分钟一个点。
  4. 7Using It Now：现在每个会话占多少（会话的引擎 + 它跑的命令 + 它的后台任务），点开进会话；最后一行是 Orbit 以外的进程（模拟器、Docker…），写出最大的三个进程名。机器不忙时这一块可以默认收起。
  5. 8Capacity 只留两个设置：Max Concurrent、Keep Free。
  6. 9Disks：Orbit 会写的每块盘一行，写明上面放了什么（Worktrees / Repos / Home / Temp / 哪个工作区）；Keep Free 的位置在条上画一道竖线。/data（NFS，87%）Orbit 不写，就不列。

改后 · iPhone / Mac

iPhone 和 Mac 是同一套 SwiftUI（Mac 在右侧详情栏里，图更宽）。机器行加三根条；机器页加一节 Resources，点进去是 Resources 页：大图、每块盘、谁在用。曲线用系统自带的 Swift Charts（iOS 17 / macOS 14 都有）。

改后 · Android

结构和 iPhone 一样：Settings → Runners 的每台机器加三根条；机器页加 Resources 一节；点进去是 Resources 页。曲线用 Compose Canvas 自己画（App 里没有图表库，也不需要引）。

三端一起的规则

什么时候变色、什么时候进 Needs Attention、文案怎么写，三端只有一份：

  • 判断写在 runnerAttention.ts，Swift 的 RunnerAttention、Kotlin 的 RunnerPage 各镜像一份，三边都对着 runnerAttention.cases.json 跑测试——今天的磁盘提醒就是这么做的。
  • 英文文案进 runnerCopy.ts，Swift / Kotlin 的对照测试直接读它。
  • 刷新沿用现在的节奏：列表和机器页每 15 s 拉 GET /runners；曲线只在 Resources 打开时拉，60 s 一次。

数据从哪来

runner 每 5 秒读一次本机，攒成「每分钟一条」，跟着现有的 30 秒心跳送上去；服务端存「此刻」和「每分钟」两份；三端照旧轮询。不新开连接，不加 runner 依赖（runner 是纯 Go 标准库、CGO_ENABLED=0）。

Runner 每 5 s 读，每分钟汇总

  • CPU：/proc/stat 两次之差；load：/proc/loadavg
  • 内存：MemTotal − MemAvailable；swap
  • OOM：/proc/vmstat 的 oom_kill 增量
  • 盘：Worktrees、Repos、Home、Temp、各工作区目录各 statfs 一次，按设备去重
  • 谁在用（每 30 s）：每个会话的进程组 + 它的后台任务，/proc/<pid>/stat 求和
心跳多一个字段 resources：此刻的数 + 没送出去的分钟汇总（断线时最多攒 60 分钟，回来一次补齐）+ 各会话用量。约 1–2 KB。

提醒规则（三端同一份）

Out of memory（红）：24 小时内有 OOM 杀进程。按钮 Lower Max Concurrent。

Memory 9x% used（琥珀）：5 分钟平均 ≥ 90%，且没有 OOM。

Disk 99% full（已有）：低于 Keep Free；没设时剩不到 10%。改为看 Disks 里每一块盘。

CPU：不进 Needs Attention，5 分钟平均 ≥ 90% 时条变琥珀（见待定 ③）。

成本：runner 每 5 s 读几个 /proc 文件；每 30 s 扫一遍进程（HPC 上约 4,000 个，几十毫秒）。服务端每次心跳不多语句，分钟表一天每台 1,440 行。

待定 · 要你拍板

1历史曲线存不存、存多久

「监控」的另一半是回头看：昨天 16:30 runner 为什么停了、HPC 是不是每天下午都满。

A（推荐）· 服务端按分钟存 7 天

  • 新表 runner_resource_minute，每台每分钟 1 行，7 天约 1 万行；每小时清一次。
  • 三端有 1h / 24h / 7d 曲线、悬停 / 拖动读数。

B · 只存「此刻」

  • 不加表，只在 runner 那一行多一个 JSON；三端只有数字和条，没有曲线。
  • 最便宜；但出了事以后，看不到当时的样子。

2「谁在用」这次做不做

CPU 100% 时，下一个问题一定是「谁」。runner 本来就把每个会话放在自己的进程组里管着（停会话时整组杀），多算一次 CPU 和内存就有了。

A（推荐）· 这次一起做，只看此刻

  • Using It Now：每个会话几核、几 GB，点开进会话；Orbit 以外的进程合成一行，写最大的三个名字。
  • 不存历史（存历史要按会话建表，量大，以后再说）。

B · 先只做整机

  • 这期只有 CPU / 内存 / 盘，Using It Now 留到下一期。

3提醒和拦截做到哪

今天磁盘有拦截（低于 Keep Free 就不再自动派任务）。内存、CPU 要不要也拦？HPC 一整天 load 27.9 / 24 核、内存 86% 加 22 GB swap——按阈值拦，它大半天都派不了活。

A（推荐）· 只提醒，不加新拦截

  • 内存（OOM、5 分钟 ≥ 90%）和磁盘进 Needs Attention；CPU 只变色。
  • 调节手段还是 Max Concurrent，提醒卡上直接给按钮。先看一周真实数据，再定要不要拦、拦在哪。

B · 加内存拦截，CPU 也提醒

  • 像 Keep Free 一样：内存 5 分钟平均 ≥ X%，或刚发生 OOM 的 30 分钟内，不往这台自动派新任务。
  • CPU 连续 30 分钟 ≥ 95% 进 Needs Attention。

4Keep Free 也看 Worktrees 那块盘（这次顺带发现的）

现在的拦截只比「工作区目录所在的盘」，可开了 worktree 的会话写在 runner 自己的 ~/.orbit/worktrees。工作区在大盘、home 在小盘的机器（比如工作区放 /mnt/data，home 在 /）：小盘满了照样派，派过去的会话再写满它。

A（推荐）· 两块都看，取更紧的

  • 开了 worktree 的工作区，用「工作区目录的盘」和「Worktrees 的盘」里剩得更少的那块比 Keep Free。
  • runner 自己清理旧 worktree 时量的本来就是 Worktrees 那块盘，两边说法一致。

B · 不动

  • 只是在 Disks 里看得到 Worktrees 那块盘，拦截规则照旧。
