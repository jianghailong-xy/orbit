截图那一屏：协调者 08:10 连问了两件事，你 08:29 六秒之内两个都选了推荐项。之后对话里的两张卡只剩 Answered 和你选的那一行，点开详情也只多一句「by you · delivered…」。问题原文、三个选项和各自的说明、推荐项，服务端其实都存着（问题和你的回答记在同一行上），只是读接口只返回还开着的问题；卡片现在靠的是答题那一刻在内存里记下的一行字。

其余几种结局

同一张卡、同一个详情页，只有回答那一行和底栏不同。用的还是截图那两问。

待定 · 要你拍板：对话里的卡要不要把选项也列出来

详情页两种都一样，选项和说明全在。区别只在不点开时看到多少。下面按截图那样两问挨着画，右边标高度。

推荐 A
  • 对话里的卡是记录。回看时要的是「这张问的是什么、我怎么答的」，A 一眼就够；当时还有哪些选择，点开就有，原样都在。截图这个项目两天里问了你 19 次，18 次选的是推荐项，其余选项回看时很少用得上。
  • 和其它回执一样：标准变更、证据、任务确认都只写结论，点开看全文。
  • 两问挨着来（截图就是这样）时：截图里对话区能看到的高度约 408 pt，A 两张卡 358 pt 放得下；B 440 pt，一屏放不下两张旧卡。
B 的好处
  • 不点开就能看到当时还能怎么选，像投票结果那样。如果你常回头核对「当时还有哪几条路」，B 更省一次点击。
  • 代价：选项一多，卡就长；选项名太长要截断，说明也只能留在详情里。

落地（按代价排）

  1. iOS / macOS：卡片和详情页按上面改只改客户端
    收起态加问题开头两行和你的回答；详情页原样回放问题和选项，底栏写谁答的、几点答的、转没转给协调者。字和 Web 共用一份（两端有测试盯着不许走样）。只做这一步的话，数据还是答题那一刻记在本机内存里的：这台设备、这次打开期间看得到，重启或换设备照样消失。
  2. 服务端：读接口返回已结束的问题服务端 + 两端换数据源
    GET /projects/:id/open-items 多返回一组已回答、已撤回的问题（最近 50 条，按条数封顶，不按天），每条带问题、选项、推荐项、你的选择和文字、回答时间、投递去向、撤回理由。数据库里都有，不用迁移。客户端把卡画在回答的时刻：重启、换设备都还在，在 Web 上答的手机上也看得到。
  3. Web 对话里也画这张卡Web
    今天 Web 上答完，卡片随读接口刷新当场消失。有了第 2 步的数据，同一张卡、同一套字画在对话里。项目页不变，那里只列还要你答的。
  4. 可选 · 转给协调者的那条消息，不再画成你的气泡服务端 + 两端
    服务端在这条消息旁边记一份结构化数据（异常交付、项目启动那几种消息已经这么做了），客户端画成一行灰色胶囊「Sent to the coordinator · 08:29」，样式沿用合并回执那一行。可以单独做，也可以不做。
  5. 顺带 · 选项名里的「（推荐）」一句话
    截图里两问的选项名都是协调者自己写了「（推荐）」，和 Recommended 标签重复，回答那一行读起来像你答了「推荐」。在 ask_owner 的说明里加一句「推荐项用 recommendedOption 标，不要写进选项名」即可，界面不改。

建议 1–3 一起做，一个任务、一次落地；4 和 5 你说要再做。
