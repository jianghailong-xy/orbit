# Wiki 读 memory：写入是线索，不是证据（2026-11-04 方案草案）

> owner 11-04 问：`wiki_note` 能不能和 Claude、Codex 的 memory 机制关联，记一条 memory 时，wiki 根据它从 session 和代码里 ingest，而不是只记录？历史 memory 会不会导入？
>
> owner 11-04 定：§10 全部按推荐，不确定的按数据测量（§6）。本文是方案，还没有任何实现。文中的数都是 2026-11-04 在 orbitd.io 上的只读聚合，只取计数，查询见 §11。

## 0. 一页结论

1. **关联，但 memory 只当线索。** 一次 memory 写入里有三样东西：agent 判断这条重要（信号）、一句话（声明）、写在哪个 session 的哪一刻（指针）。信号和指针直接用；声明只当待查的问题，永远不当证据。
2. **不建新流水线。** 写入本来就是 session 事件流里的工具调用，维护作业也已经读过 97% 写过 memory 的 session。只改三处：另成一份只放声明和相关证据的案卷，抽取之后另跑一遍只核对声明（抽取本身不动），核对按证据定信任。
3. **agent 的行为不变。** 不加钩子，不发 runner，不加指令。Claude 照常写 memory，服务端自己看得到。
4. **信任要看第一手证据。** 现在 67% 的生效条目只有 agent 自己的话或 memory 作出处，其中大多数是 `auto`（§1.3）。按 M1 的抽查（§6.1 的判定），以后只有 memory 出处的 op 不再得 `auto`，来自声明的条目没有工具结果或 owner 的原话时也一样，都最多 Unreviewed。否则“从 session 找证据”只会找到 agent 把同一句话又说了一遍。
5. **只有 Claude 自动关联。** Codex 的 memory 是空闲后后台生成的摘要，默认关闭，里面没有“工作中的 agent 判断这条重要”这个信号。其余引擎用 `wiki_note`。
6. **`wiki_note` 变小。** Claude 平时不用调。它只用于没有 memory 的引擎、纠错和 owner 明说“记到 wiki”，走同一条路。
7. **历史 memory 会导入，但不再照抄。** 10 月以来从未导入的写入（1,006 个 session）和 9 月已导入的 note（958 个能找回 session）都回到原 session 核对，从新到旧分批跑。找不回 session 的最多 Unreviewed（§5）。
8. **代码先当锚点。** 声明里的路径和 session 改过的文件作为锚点候选。读代码判断真伪放在核对这一步，而且先在回放里量值不值（§3.5）。
9. **不确定的按数据定。** 先按证据类别抽查条目的对错，再回放对比，都不写 wiki 表（§6）。重点看证据规则站不站得住，以及模型会不会顺着声明说。

## 2. 三条规则

**R1：声明不是证据。** memory 和 `wiki_note` 的正文只能提出问题。它们不进 `sources`，核对器也看不到。这保留了现有的规则：二手内容不能回流成出处。

**R2：只有 memory 撑不起 `auto`。** Automatic 下，`supported` 要变成 `auto`，核对器读到的不能只有 note。范围按 M1 定（§6.1 的判定）：

| op 的出处 | 判 `supported` 得到 |
| --- | --- |
| 只有 `note` | 最多 Unreviewed，`verification_evidence` 记 `second_hand`，计入回退统计 |
| 来自声明（`promptedBy`），没有第一手出处 | 最多 Unreviewed，由“声明上线”任务接上 |
| 其它 | `auto`，和现在一样：agent 回复、thinking、任务文本都算 |

- 第一手：§6.1 表里的“观察到的”和“owner 的话”。分类函数是 `wikiEvidenceClass`（`src/shared/src/wiki.ts`），写文件类工具和 wiki 读取不算观察到的。
- decision、convention 不要求 owner 的话：owner 的话这类错误率也是 13.3%，和只有 agent 的话一样，没有数据支持这个要求。
- 最多 Unreviewed 的条目照样可搜可读，只是不再显得验证过。
- 旧条目不动。

**R3：一条流水线。** memory 写入、`wiki_note`、历史 note 最后都是案卷里的声明。没有第二套抽取、队列和表。

## 3. 设计

### 3.1 什么算一次写入

在构建案卷时识别（`timeline()`），现在这里遇到 memory 路径就返回 null。

- **工具：** `Write`、`Edit`、`MultiEdit`，没有报错。
- **路径：** `/projects/<slug>/memory/<file>.md`，不含 `MEMORY.md`。比现在的 `MEMORY_PATH` 严，后者也会匹配仓库里的 `memory/x.md`。
- **正文：** `Write` 取 `content` 并去掉 frontmatter；`Edit` 取 `new_string` 里 `old_string` 没有的部分。`loadDossierRecords` 现在不取这两个字段，要加，上限 4,000 字符。
- **跳过：** frontmatter 写 `type: user`；正文大部分是链接（hub、索引）；新增不足 20 字符。都计入 `report.claims.skipped`。
- **上限：** 每个案卷 6 条，每条 600 字符。`feedback` 优先，其次新的。超出计入 `overCap`。
- **继续剔除：** 读 memory 的调用、提到 memory 的句子、Bash 和脚本对 memory 的改动。

### 3.2 案卷

**抽取的案卷不变。** 第一次回放把声明放进抽取案卷，没过门槛；第二次 A 的抽取不动，另跑一遍只核对声明（下称 S），全过（§6.2），上线的是后者。声明有自己的一份案卷（`buildDossier(..., { claims: true })`），只给 S 用，下面说的都是这一份。

- **声明行：** 新说话人 `claim`，编号 `C1`、`C2`，放在写入时刻的时间线位置。`wikiMaintainLines` 只认 `L<n>`，`sourcesOf` 也要跳过这种行，所以模型引了 `C1` 也成不了出处。
- **必留：** 先放声明，再放任务开场和 owner 的话。
- **证据窗：** 声明里的代码词（路径、标识符、反引号片段）在时间线里命中的工具行和 owner 行加分。窗口向前看，因为证据在写入之前。结果中间命中的那一行也放进这一行，现在只放结果的首尾行。前测里 93% 的写入有八成以上代码词在此前的工具记录或用户消息中出现过（§11）。
- **预算：** 总量仍是 8k。owner 的话最多占 35%，其余按声明轮流放证据窗。S 案卷平均 4041 token，A 5603（§6.2）。
- **确定性：** 同样的记录产生同样的文本。A 的案卷和提示逐字节不变，现有 golden fixture 不用动。
- **留出：** `sha256(sessionId)` 落在 10% 的 session 没有这份案卷，不跑 S（§6）。
- **排除 wiki 读取：** `wiki_search`、`wiki_get` 的结果不进案卷，否则 wiki 内容可以绕一圈回来当证据。判定在 `wikiCallReadsWiki`（`src/shared/src/wiki.ts`）：各引擎的工具名，加上工具调用和后台任务的命令里跑的 `orbit wiki search`、`orbit wiki get`。

### 3.3 抽取和只核对声明的一遍

A 的案卷、提示和调用次数都不变。有声明的 session 在 A 之后另跑一遍 S（`wikiMaintainCheckClaims`，提示在 `wikiMaintainClaimsPrompt`，step `claims`），逐条回答：

- `shown`：工具行或 owner 行说明的正是这件事，`shownBy` 写这些行。
- `narrowed`：这些行只说明了一部分，只留这部分。
- `contradicted`：这些行说明的相反。
- `absent`：这些行既没说明也没反驳。只有 agent、think 这类行重复这条声明也算。
- `not_durable`：进度、某个任务的事实，或者看代码一分钟就知道。

每条 `shown` 或 `narrowed` 写一条条目，不写别的条目。

- **解析：** `notes` 从回答里逐个读，读不出算 `unanswered`，不为它重试。模型给不出回答也算 `unanswered`，运行和 A 的 op 不受影响。
- **引用：** 引用 C 行丢弃。条目自动加上 `shownBy` 里最多两条第一手的行，重复声明原文的工具行不加（§3.4）。
- **顺序：** A 的 op 先记下、先核对完，再轮到 S。这样 S 的 op 的相似条目里有 A 刚写的，核对时已经生效，重复就走现有的 `duplicate`（把出处加到 A 的条目上）。两边走同一个自检和熔断。回放没量过两边同时写，所以 `report.claims.duplicates` 单独报。
- **追溯：** op 记 `promptedBy`（事件 id 和文件名）。它是服务端字段，agent 传了仍被拒，不算出处，用于 §3.4 的封顶、度量和追溯。
- **报告：** `report.claims = { claudeSessions, seen, skipped, overCap, heldOut, shown, narrowed, contradicted, absent, notDurable, unanswered, entries, duplicates }`，只算本次运行有变化的案卷。`entries` 是 S 记下的 op 数，`duplicates` 是 S 的 op 被判 `duplicate` 的条数。S 的 op 计入 `report.ops`，`report.entries` 只算 A。
- **告警：** 连续 3 次运行都读过至少 20 个 Claude session 而 `seen` 为 0，通知 owner 一次（§8）。

第二次回放的读数：写入 173 次，跳过 2，进案卷 171。S 写过 memory 的 session 每个多 1.44 次抽取调用和 1.03 次核对调用。

### 3.4 核对

- **读的东西不变：** 条目加被引记录。声明不在其中，核对器不知道条目来自 memory。
- **证据多一档：** `verification_evidence` 增加 `second_hand`，表示核对器读到的原文全部来自 note。`supported` 落到 Unreviewed，并且计入回退统计，因为模型确实读了文本。`unreadable` 的行为不变。改动在 `wikiVerdictEffect`（`src/shared/src/wiki.ts`）和它的调用处。
- **来自声明的 op：** 带 `promptedBy` 的 op 没有第一手出处时，证据记 `second_hand`，`supported` 最多 Unreviewed。第一手用证据规则的 `wikiEvidenceClass` 和 `WIKI_FIRST_HAND_EVIDENCE`，不另算一份，还要读得到原文。另有两条：
  - 工具结果里的 memory 原文（比如读一份存下来的工具结果文件）过得了过滤。`observed` 的出处，交给核对器的原文和声明连续重复 60 个字符以上，就不算这条声明的第一手。owner 的话不受影响。第二次回放按案卷行量到 96 条第一手条目里 2 到 6 条受影响，C 组 1 条外来声明也是这样被“证实”的。这里比的是核对器读到的整条记录，范围比案卷行大，受影响的条数可能更多，上线后看 §6.4 的信任分布。
  - `project_send`、`task_comment`、`session_send` 这类工具的输入是 agent 写的字，`wikiEvidenceClass` 算 `agent_words`，名单是第二次回放开跑前定的 14 个。第二次回放里只靠这类工具行的第一手条目是 5/96。这只影响 `promptedBy` 的判定，不带 `promptedBy` 的 op 不受影响。
- **边界：** note 旁边有别的带原文的出处就不算 `second_hand`，不论那条是什么类别。旁边的出处没有原文（空 thinking，库里读不到原文的 commit）时仍算，因为结论读到的不是那条。
- **污染：** 从记录抽的 op 按记录所在 session 判定污染，这是现成的。note 按 frontmatter 的 `originSessionId` 找到的 session 判定：这个值是引擎的 session id，查 `session.runtime_session_id`，只查本 owner，一个 id 对应多个 session 时任一污染就算。没写或找不到的按未污染，note 反正封顶。

### 3.5 代码

| 层 | 做法 | 状态 |
| --- | --- | --- |
| 锚点候选 | 声明里的路径，加 session 在写入之前改过的文件 | 现有的快照校验和复验直接可用 |
| 判断真伪 | 核对时读锚点文件在 `origin/main` 的内容，只取命中条目代码词的行和上下文，最多 2k 字符 | 先在回放里量（G4） |

读代码不放进抽取：案卷变长会降低召回率。我试过量 memory 的路径过期率，没量成：1,024 个被引路径有 155 个不在 main 上，但抽查 60 个缺失路径，只有 11 个在 git 历史里出现过，其余多是缩写、临时脚本和构建产物。所以这一层的价值目前未知。

### 3.6 时机

写入时刻什么都不做。turn 结束产生 `session_settled` 事实（`src/apiserver/src/wiki/wiki-maintenance.ts:239`），到期规则不变：积压 20 个 session，或最老事实超过 24 小时。

- **证据更全：** agent 写完可能很快改掉这条。
- **代码才到位：** 61% 的写入之后还有合并回执，中位 0.5 小时。等一等，锚点才能对上 main。
- **没人在等：** 现在读 wiki 的 session 很少。以后读多了，可以让写过 memory 的 session 优先，这一期不做。

代价是新知识最多晚约一天。没开维护的 space 不处理。

### 3.7 一个例子

memory 里有一条：`release.sh next` 会直接打 tag。owner 当时只说了 “cut a beta version”。知识在 agent 的轨迹里：它读 skill 文档，以为 `next` 只解析版本号；跑完后工具结果第一行是 `tagging v0.1.2-beta.104 … pushed`；随后它在 thinking 里写下 “isn't a dry run”。

| | 导入作业 | 本方案 |
| --- | --- | --- |
| 读什么 | 这一句 | 这一句，加该 session 的案卷 |
| 出处 | note | 工具结果那一行 |
| 字段 | 只能从这句话里抽 | `trigger.commands`、`symptom`、`cause` 从工具结果和 thinking 填 |
| 锚点 | note 提到才有 | session 读过的 `.claude/skills/release/release.sh` |
| 信任 | 核对器读 note，判 supported，也最多 Unreviewed（此前得 `auto`） | 引了工具结果才是 `auto`；只引 agent 的话就是 Unreviewed |

## 4. `wiki_note`

| 项 | 内容 |
| --- | --- |
| 形态 | MCP 工具 `wiki_note`，CLI `orbit wiki note` |
| 参数 | `text`（必填，最多 2,000 字符）、`paths?`、`corrects?`（条目 id） |
| 路由 | `POST /api/runner/wiki/notes`，必须带 session；验证和判断 session 仍被拒 |
| 存储 | `wiki_note` 表加可空的 `session_id`，不挂外键。`paths` 追加到正文，脱敏和按内容去重沿用现有逻辑 |
| 进案卷 | `loadDossierRecords` 读本 session 的 note，和 memory 写入一样变成声明 |
| `corrects` | 立刻提交一个现有的 challenge，正文同时作为声明 |
| 限额 | 每个 session 15 条，探针文本拒收，不占 Review 名额 |
| 回答 | `{ noted, noteId, created, readBy: "the next maintenance run", challenged? }` |

存表而不是只靠工具调用记录，是因为 CLI 调用在事件流里只是一次 Bash。

**实现时定下的（任务 `34rozWZl2qENSjLHzt5PQ`，协调者可改）：**

- **留出不管 note。** §3.2 的留出是为了量 memory，`wiki_note` 的回答又说了会有运行读它。所以留出的 session 只留出 memory 写入，它的 note 照常核对。这种 op 的 `promptedBy` 是 `{ noteId, file: "wiki_note" }`，M8 分得开。
- **`seen` 只算 memory 写入。** note 单独记在 `report.claims.notes`，否则几条 note 就能盖住 §8 的写入量告警。
- **记 note 的调用不进任何案卷，也不算 `observed`。** 否则工具调用记录和 `orbit wiki note` 的 Bash 记录都会把声明原话变成它自己的第一手出处。第二次回放定下的 14 个工具名单没动，这是单独的判定（`wikiCallWritesNote`）。
- **note 没有跳过规则，排序算 feedback，受每份 6 条的上限。** 所以一个 session 记满 15 条时，最多 6 条进案卷，其余计入 `overCap`。
- **`readBy` 按实情回答。** space 没开维护、正文来自别处时不说“下次维护”。
- **同样的正文归先写的一方。** 后写的 session 回答 `created: false`，它的案卷里读不到这条。

**回填怎么跑**

- **入口：** 维护作业加一种输入：给定 session 列表和每个 session 的 note id，而不是游标页。自检、断路器、提议、核对、锚点都复用。跳过移动游标、写文档和排 articles（`src/apiserver/src/wiki/wiki-articles-jobs.ts:70`），不单独再排：回填结束后，下一次记下 op 的日常运行会排 articles，那一次覆盖回填写的条目。
- **只跑核对声明那一遍，不再跑原来的抽取（协调者 2026-11-05 定）：** 这些 session 大多已经被日常维护抽取过。再跑一遍只会多出一批主要靠 agent 自己的话的 `auto` 条目，这正是这个项目要减少的。第二次回放的读数（§6.2，回放数字，不是回填实测）：每个写过 memory 的 session，A 是 1.56 次抽取调用加 3.32 次核对调用（332 条 / 100），S 是 1.44 次加 1.03 次（103 条 / 100），只跑 S 少 66% 的调用。代价是从没抽取过的旧 session 这次也不抽取。
- **不写 `wiki_dossier`（同一决定）：** 不写 hash、sources，也不写位置。hash 的含义是“抽取已经读过这份案卷”，`dossierPage` 据此判 `unchanged`。回填没跑抽取，如果更新 hash，一个有新记录、事实还在游标之后的 session，下一次日常运行就会被判 `unchanged`，新记录不抽取。没有这一行的 session 也不新建。
- **回填过的 session 之后又有新记录：** 日常运行照常读它，抽取，再核对一次声明。重复的声明走 `duplicate`，不会多一条生效条目。
- **声明：** 带 note id 的 session，声明就是这些 note 的正文，不含 frontmatter，规则和上限与写入相同，放在 session 最后一次写这个文件的位置，没写过就放在最后。这时不再读它事件流里的写入：更早的版本不回填，见上表。不带 note id 的 session 读它的写入。留出组不变：落在 10% 里的 session 点名了也不跑 S，它的旧 note 条目收尾时降级。
- **不倒回游标：** 倒回会让整个 space 进入追赶，文档停更，新 session 排在后面。页位还会被没有 memory 的 session 占掉。
- **节奏：** 每批 20 个 session，一次一个作业，和日常维护交替，从新到旧。交替由代码保证：回填不论成败，结束时都请求这个 space 的下一轮，还到期就立刻建日常作业，下一批回填要等它结束。
- **触发：** 容器里的一次性 CLI `src/apiserver/src/wiki/wiki-backfill.cli.ts`，先例是附件迁移的 CLI（`src/apiserver/src/files/attachment-migration.cli.ts`）。不加 HTTP 路由，省掉登录和租户用例：这件事只为一个 space 跑一次，能跑这条命令的人本来就能读数据库。要求写明原因，一次最多 20 个 session，还有没结束的维护作业时拒绝。没有 UI。

  ```text
  node src/apiserver/dist/wiki/wiki-backfill.cli.js run --space <id> --reason <why> --session <id>[:<noteId>,<noteId>] ...
  node src/apiserver/dist/wiki/wiki-backfill.cli.js downgrade --space <id> [--apply --reason <why>]
  ```

- **不影响日常：** 回填的运行行 `due` 为 NULL，不计入当天次数、catch-up 的连败和 memory 写入量告警。失败只写在自己的运行行上，不计入游标的连败数，也不通知。只允许 Automatic space：duplicate 判定和证据封顶都在核对这一步。
- **旧条目：** 把当前版本引用这条 note 的生效条目加进 op 的 `similar[]`，只对 maintenance 身份生效。核对判 duplicate 时，现有逻辑把新出处追加到旧条目上，内容和信任不变。
- **收尾：** 全部跑完后，CLI 的 `downgrade` 把仍没有第一手证据的旧 note 条目从 `auto` 降为 Unreviewed，走 `applyOp` 的一条内部指令，不产生新 revision。判定用证据规则的同一函数（`promptedEvidenceOf`）。默认只报告不执行，`--apply` 才写，这时要写明原因。每 50 条一个事务，并写一行 `activity` 记原因和 id：没有 revision，这是唯一的记录。结果打印成报告，重复执行没有变化。

- **止损：** 前 100 个 session 是试点，门槛 G1、G2 不过就停。

其它 space 不需要回填：新开维护从 `lookbackDays`（默认 14 天）读起，声明随案卷自动带上。

## 8. 风险

- **模型附和。** 最大风险，由 G2 把关。核对器看不到声明，这是第二道防线。
- **Claude 改机制。** 2.1.318 里已有后台提取代码（`extractMemories`、`autoDream`），近 7 天没有 `memory_saved` 事件。一旦启用，写入会离开主事件流，工具调用这条路静默归零。对写入量告警；退路是读 `memory_saved` 里的路径，再让 runner 读文件。
- **漏网。** 一个账号 7 天变更的 100 个文件里，27 个没有 Write、Edit 记录（6 个经 Bash，21 个没找到，其中 13 个没有 `modified` 戳），多半是脚本整理，没有逐个确认。
- **网页内容混入。** 污染只认 WebFetch、WebSearch 这几个工具名（`src/apiserver/src/wiki/wiki.service.ts:4352`），Bash 里的 `curl` 不算。本方案不改，但任何自动推送上线前都要先修。
- **隐私。** memory 正文原本就在事件流里。新变化是它进入 System model 的提示。案卷不落库，先过脱敏器，`user` 类跳过。
- **`auto` 明显变少。** 这是预期结果。标签会更诚实，但界面上的 Unreviewed 会变多。
- **算力。** articles 占近 14 天 orbit space 模型请求的 81%（31,345 次），抽取只有 1,368 次。这个比例是否正常还没查。
