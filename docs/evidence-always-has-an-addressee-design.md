## 0. 一页结论

证据是一个问题："这份工作是否达到了**这个任务**的标准？" 只要它还没有答案，就必须同时满足三点：**有人能答、那个人被告知、谁在等谁是明确的**。今天的设计在三处破了这条约束，本文分别给出修法，而不是给这一个 case 打补丁：

1. **标准由服务器绑定，不再让 agent 抄。** 一个任务按哪个标准判定，完全由任务自身决定（声明的 `criterionKey`，否则任务自己的 `acceptanceCriteria`）。服务器在提交时已经快照了这份标准（`criterionRevision`），信封里的 `criterion {key, text}` 是一份只会出错的冗余输入。去掉它，"引用错了标准"这个错误就从结构上消失了。
2. **判不了的版本，交给能让它变得可判的人。** 提交后标准变化（被改写、被删除、任务移项目），唯一能推进的动作是"重交"，唯一能做这件事的是任务的 run。今天只有"移项目"这一条路径会通知 run（`moved-task-evidence.ts`），其余路径静默落到 owner 卡片上，而 owner 卡片上没有能按的按钮。把这套通知推广到所有"判不了"的原因。
3. **加一条可检查的不变量和一个兜底巡检。** 每个未结束的待处理项，都必须能说出"现在轮到谁、他是否被告知"。巡检找出说不出来的项（孤儿），交给协调者（没有协调者时交给 owner）。不加计时卡片，遵守 2026-10-08 和 2026-11-08 的 owner 决定。
4. **"没验证"不等于"通过"。** 证据的 gap 如果命中任务自己的验收条款，确认时必须有去处（退回，或一个带 id 的后续任务）。任务的验收条款不能依赖它依赖链之外的工作。

**worker 为什么会填错：平台让它这么填。** 任务执行提示词（`task-execution-prompt.ts:146`）写的是 `criterion ({key, text}, copied from the acceptance criteria project_get returns)`。任务描述又第一句就要求先读 `project_get`。对一个没有声明 `criterionKey` 的项目任务，这句话恰好把 worker 引到错误的标准上。D 和 W 是两次独立的运行，犯了同一个错，说明这不是模型偶发的失误。

**为什么谁都没被叫醒：**
- 提交者（唯一能重交的人）只在同步回执里拿到一个布尔值。
- 协调者（有裁决权的人）被过滤掉了，因为它判不了。
- owner（被问的人）推进不了：卡片要求"让提交者对照当前标准重交"，owner 无从下手。
- 2026-11-08 的"取走才计时"规则下，从未投递的版本没有计时，也就不会升级。这条规则本身是对的（见 §5），问题在于这一版根本没有该投递的对象。

## 2. 原则一：标准由服务器绑定（解决"引用错了"）

### 2.1 现状的形状

一个任务的标准今天有两条线（`task-evidence-envelope.ts` `liveCriterionText` 的注释写得很清楚）：
- 声明了 `criterionKey`：标准是那个项目验收项的当前原文。
- 没声明：标准是任务自己的 `acceptanceCriteria`，与是否归入项目无关。

两条线都只由任务行决定。提交时服务器已经把这份标准快照进 `task_completion_evidence.criterion` 和 `criterionRevision`（`completionDigest(criterion)`）。信封里的 `criterion {key, text}` 是让 agent 再抄一遍，然后由服务器比对它抄得对不对。

### 2.2 改法

- 信封去掉 `criterion`。服务器在提交事务里把"此刻这个任务的标准"（key + 原文）写进证据记录，作为这一版的标准快照。
- 判定入口的"标准还在吗"改为比较**快照**与**当前标准**，不再比较 agent 的引用与当前标准。语义不变：标准被改写后，旧证据仍然判不了（这正是 `criteria-seal-design.md` 要的"按内容绑定"），只是比较的两边都来自服务器。
- 兼容：已发布的 runner 和 CLI 仍会发 `criterion`。迁移期**接受并忽略**它，不因它拒绝提交。见 D1。
- 提示词第 3 步删掉 `criterion` 字段，改为把这个任务的标准原文直接写在提示里，作为"你的证据要证明的是这段话"。agent 照样要读标准，只是不用再抄。

### 2.3 删掉之后哪些错误不复存在

| 今天的拒绝原因（`movedRefusal`） | 改后 |
|---|---|
| 证据没引用任何标准 | 不存在，服务器总会写快照 |
| 引用的 key 不是任务声明的那个 | 不存在 |
| 没声明的任务引用了项目验收项（本次） | 不存在 |
| 提交后项目验收项被改写 | 仍存在，属于原则二 |
| 声明的验收项被删除 | 仍存在，属于原则二 |
| 任务没有任何标准（无声明、`acceptanceCriteria` 为空） | 改为**提交时同步拒绝**（4xx），调用者就是能修的人 |

**规则：** 提交时就能判断的错误，当场拒绝，交给调用者；只有提交之后才可能发生的变化，才进入异步路由。

## 3. 原则二：判不了的版本交给能改它的人（解决"没人被叫醒"）

### 3.1 判不了的原因，以及谁能推进

| 原因 | 能推进的动作 | 能做这件事的人 |
|---|---|---|
| 标准在提交后被改写 / 被删除 | 对照新标准重交，或改声明后重交 | 任务的 run |
| 任务被移到别的项目（已实现） | 同上 | 任务的 run |
| 裁决会话参与过这份工作（`decidingSessionDisqualification`） | 换一个独立会话裁决 | 协调者开 judgment session，或 owner |
| 协调者暂时不可用 | 等它回来 | 平台（排队，2026-11-08 规则） |

前三行今天只有第二行会通知 run。

### 3.2 改法

把 `moved-task-evidence.ts` 已有的两条消息推广成一个公共入口：**某个版本变得判不了时，一律走它。**
- 告诉任务的 live run：`resubmitMessage`，`steerIfLive: true`。消息里写清楚这一版为什么判不了，以及新标准的原文。
- 告诉 Automatic 项目的协调者：`arrivalMessage` 的同类知会，说明"已让 run 重交"或"没有 live run"。
- 没有 live run（run 已结束）时：协调者收到的知会就是一个待办，由它决定 `task_start` 重跑还是改标准。没有协调者的项目，才落到 owner 卡片上，并且卡片上的动作必须是 owner 能按的（例如 Restart the task）。见 D2。
- 触发点有三个：标准改写（`replaceAcceptanceDefinitions` 提交后）、声明的验收项被删除、任务移项目（已有）。一个 key 规则：`(evidenceId, standardDigest)`，同一版对同一份新标准只通知一次。

### 3.3 owner 卡片的动作从判定条件推导

今天的待判定读已经和判定入口共用判断条件，但卡片上只显示 `requiredAction` 文本，没有对应按钮。改为：卡片只出现收件人自己能完成的动作；`requiredAction` 指向别人（run、协调者）时，这张卡就不该出现在 owner 面前，而应改为 §3.2 的通知。

## 4. 原则三：每个待处理项都有当前处理人（兜底）

原则一、二修的是已知路径。新的路径以后还会出现，所以需要一条可以机械检查的不变量：

> 每个未结束的待处理项，都能读出 `(addressee, notifiedAt)`：轮到谁、什么时候告诉他的。读不出来的就是孤儿。

需要覆盖的待处理项：

| 待处理项 | 正常的 addressee |
|---|---|
| 未判的最新证据 | 协调者（Automatic）/ owner / 派发会话；判不了时是 run |
| 异常待办 | 协调者，没有时是 owner（契约 §4.6） |
| 运行中的任务 run | run 自己；长时间无进度、无后台任务、无 wake 时视为无人 |
| 等待依赖的任务 | 依赖任务的 addressee |

**巡检**：周期性扫描未结束的项目任务，找出孤儿，给协调者发一条消息（没有协调者时交给 owner），key 规则同 §3.2，同一个孤儿只报一次。不计时，不出倒计时卡。这和 2026-10-08、2026-11-08 的 owner 决定一致：由协调者负责推进，有问题再问 owner。

本次的两个现象都会被它抓到：D 的 rev 1（addressee 是 run，但 run 没被告知），以及"W 中途停了"一类的 run 无进度（如果属实）。

## 5. 与 2026-11-08 "取走才计时"的关系

不冲突。那份设计约束的是**有** addressee 的项：协调者暂时不可用时排队，取走才计时。本文处理的是**没有** addressee 的项，它们根本没进过任何队列，计时规则无从适用。本文不改任何计时规则。

## 6. 原则四："没验证"不等于"通过"

这一节与本次死锁无关，是同一个项目暴露的另一类问题，一并写进来供 owner 决定是否同期做。

**现象：**
- D 的验收标准写着 "copy parity with Swift and web"。D 的分支早于 M 落地，Swift 一致性测试因对方文案不存在而 **skip**；Web 一致性只在 W 未提交的文件上验证过。协调者把这两条作为"已接受的缺口"确认了。
- W rev 1 自己写明没做"审批回答 422 时的 Retry / Send as written"，这正是项目决策 1A、3A 要求的。

**根因：**
- D 只依赖 A2，但它的验收条款要求与 M、W 的产出一致。**验收条款引用了依赖链之外的工作**，所以在 D 交付时它不可能被证明。
- gap 是自由文本，确认时没有约束：命中验收条款的 gap 可以被直接接受。
- 测试在对方缺席时 skip，结果仍是绿的。

**改法：**
- 协调者拆任务时的指引（项目协调者提示词）加一条：验收条款只能写依赖链内能证明的内容；跨任务的一致性属于汇总验证任务（本项目的 X1/X3）。
- gap 结构化为 `{text, criterionClause?: string, followUpTaskId?: string}`。判定入口拒绝这样的 CONFIRM：存在标了 `criterionClause` 的 gap 却没有 `followUpTaskId`。判定者核实 gap 是否如实标注，这仍是判断题，但"命中条款还被直接接受"变成了显式动作。见 D4。
- 仓库约定（不属于平台）：跨客户端一致性测试在对方文件缺失时失败，而不是 skip。见 D5。
