# Orbit 0.1.261

## Summary

The stable release after `v0.1.260`, with everything merged since that tag. It supersedes the `0.1.261-beta.N`
prereleases tagged from `main` on the way to it, starting with `v0.1.261-beta.1`, and carries everything in them.
Their notes are beside this file. A runner, Mac or Android install on one of them moves to 0.1.261. These are
the changes an operator will notice first:

- **SubAgents.** A session can hand a self-contained piece of work to a child agent with the `delegate` tool. The
  child runs in the session's working directory, or on another workspace of the same repository, chosen by name
  or by runner capability. Orbit routes it by tier and the agent's Optimize For setting across the enabled
  providers, Codex and Claude account pools included, and moves it on a limit or a sign-in failure. Its work
  shows as an Agent block in the parent's conversation on every client.
- **Scheduled tasks.** A schedule starts agent runs on a timetable. Web, macOS, iOS and Android have a Scheduled
  page with a timeline and a run panel, and schedule cards appear in conversations and in Waiting on you. Runs
  count against a weekly budget. A CHECK_ONLY check reads the checkout without writing to it.
- **Translation.** With Settings › Translation on, the owner's messages are translated into the agent's
  language before the engine reads them. Replies, question cards, approvals and suggestions come back
  translated, in about 30 languages, and Show both languages draws each reply block in both. The prompt
  optimizer, on by default, offers a rewritten draft before a message is sent.
- **Coordinator handoff.** From its context gauge, a project's coordinator can Compact or Start a new
  coordinator. The outgoing coordinator writes a handoff note, and its successor opens with the note and takes
  over its waits.
- **Session Settings.** Every session has a Settings page on every client. It holds the session's own
  environment variables, laid over the workspace's, with Restart to reload a live engine. It also has
  notification overrides and a mute, the session's labels and public link, and its usage.
- **Runner self-update.** A busy runner takes an automatic update at night instead of during the working day. A
  drain that runs past five minutes interrupts the turns still running, and they resume on the updated runner.

Also in this release:

- **Phones.** The needs-you card floats over the page at a notification's size and can be swiped away. On iOS,
  an approval that arrives with the app open shows in that card. A conversation's navigation bar shows only its
  own needs-you, and something newly waiting on you is announced once, as a toast. Android also gets push
  notifications for crossing requests, coordinator confirmations and schedule alerts.
- **Machines.** A new machine's setup card asks for one folder name in the machine's home; on the web it also
  creates the workspace. Managed runners are in Machines & models on every client, and the managed runner image
  bundles every supported engine. A machine's "N of M running" counts sessions a background job holds.
  Fix with an agent is offered under a failed Update engines report.
- **Merges and the main checkout.** A merge runs beside the session's turn instead of waiting for it, and a
  branch that landed some other way drops its stale "Merge conflict". The main checkout gains Discard, and its
  Commit has no message box.
- **Messages.** A queued message says what holds it (`Queued · runner full`, `run full` or `batch full`), and
  macOS and iOS file a send where the server placed it. iPhone photo uploads work again. A turn that carries only
  Orbit's blocks is drawn as a From Orbit line, not as the owner's bubble.
- **Sharing.** Guests see a shared session's images and attach their own. The invite field suggests people
  invited before.
- **Accounts.** Switching an idle session to another account frees the old one. A refused account removal
  names the sessions still using the account. Removing one secret no longer holds up delivering another.
- **Owner cards.** An escalated item says when the coordinator can't take messages, and offers only the actions
  it can carry out. An agent can ask the owner to create a wiki. A request to take a task out of its project
  reaches the owner, and a pending request offers Chat about this.
- **Recovery.** Refusals and failures carry a stable code and a recovery action. A retried `project_create` or
  `session_create` returns the first receipt instead of filing twice.
- **Smaller changes.**
  - New sessions start on the workspace's last model.
  - Create and start leads the single-task create card.
  - The recap card has a single ×.
  - iOS session-list section titles scroll away with their rows.
  - On iOS 26 the drawer's waiting count is the toolbar item's badge.
  - macOS and iOS say "Shared" on a shared pool.

These notes also correct the 0.1.260 notes, which left out five database migrations and a dependency security fix
(see Upgrade impact and Security fixes).

## Upgrade impact

- **Runners update themselves.** `0.1.261` orders above `0.1.260` and above every `0.1.261-beta.N`, so runners
  self-update from `/dl` as usual, including any on a beta.
  - **Which rules apply.** The update to 0.1.261 follows the rules of the runner it replaces. A busy 0.1.260
    runner drains after an hour of deferral and waits for its turns to finish. A runner on a 0.1.261 beta
    already follows 0.1.261's rules.
  - **0.1.261's rules.** A runner that goes idle still updates at once. A busy runner's automatic update waits
    six hours for it to go idle. If it never does, the runner drains at the first check between 02:00 and 06:00
    local time after that, which can be the next night: about 26 hours after the release. A release the owner
    postponed with Later keeps its plain deferral and ignores that window.
  - **Drain limit.** Once a drain has lasted five minutes, the runner takes the update as Update Now does: it
    interrupts the turns still running, and they resume on the updated runner. The runner log says when the
    interruption came from the drain limit.
  - **What waits for the runner.** These need the machine's runner on 0.1.261: the `delegate` tool, Discard on
    the main checkout (capability `main-checkout-discard/v1`; the apiserver refuses a discard for an older
    runner), a merge beside a running turn, the idle account switch, and the one-folder setup step
    (`create-workdir/v2`). Until a machine's runner updates, its setup card keeps the `~/orbit-repos/` prefix.
- **SubAgents.** These are on in every workspace by default, with at most 4 running at once (1–16). The
  SubAgents group of an agent's settings holds both, with Optimize For (Cost by default) and blocked providers.
  - The runner offers top-level sessions a `delegate` tool, so a session gets it once its runner has updated.
    Claude Code loads it up front.
  - A SubAgent never gets `delegate` itself, and its permission mode is never wider than its parent's. A
    read-only SubAgent routed to Codex, such as the built-in `explore` type, runs in Codex's read-only sandbox.
  - The child runs on the provider and model routed by tier across the enabled providers. When an account hits
    its limit or fails to sign in, it moves to the next candidate, at most twice; a model the caller named is
    never moved.
  - A run on another workspace needs that workspace's runner updated too. It works in a temporary worktree of
    that workspace's HEAD and returns text only. `provider_list` with `workspace` says what can run there, and
    a named model that cannot is refused at once with `SUBAGENT_TARGET_CANNOT_RUN`.
  - Each model's tier is in the Providers page's Tier column. A custom endpoint's model has none until the owner
    sets one, and routing skips it until then.
- **Scheduled tasks.** A schedule's runs start sessions recorded as scheduled (`session.run_source` is
  `SCHEDULE`). A CHECK_ONLY check runs each engine in its nearest mode that does not write: Claude Code asks
  before shell commands, and Codex runs in its read-only sandbox
  ([engine modes](../docs/scheduled-tasks-engine-modes.md)). 0.1.260 cannot read a scheduled session; see
  Rollback.
- **Translation and the prompt optimizer.** Translation stays off until the owner turns it on. While a message is
  being translated it is held, and a failed translation offers Retry or Send as written. The prompt optimizer is
  on by default, and only an explicit off in Settings turns it off. Both use the server's existing
  `DEEPSEEK_API_KEY`, and a server without one offers no optimized prompt.
- **Twenty-two database migrations** since `v0.1.260`, applied by the apiserver on boot. All are additive: they
  create tables, types and indexes, add nullable or defaulted columns, widen checks and add one enum value, and
  every new foreign key cascades or sets null. `0670` and `0860` fill columns they add; no migration rewrites a
  column that existed before.
  - **SubAgents:**
    - `0524_subagent_run`: the `subagent_run` table and two `workspace` columns.
    - `0526_model_provider_model_tiers`: `model_provider.model_tiers`.
    - `0527_subagent_run_wake`: three `subagent_run` columns and a partial index.
    - `0528_approval_subagent_run`: a nullable `approval.subagent_run_id`.
    - `0642_subagent_run_remote`: five nullable `subagent_run` columns, an index and the
      `subagent_relay_event` table.
    - `0800_pool_login_token_subagent_credential`: two nullable `pool_login_token` columns.
  - **Sessions:**
    - `0645_create_request_receipt`: the table of create receipts, one per request id.
    - `0670_session_opened_by`: `session.opened_by`, `TEXT NOT NULL DEFAULT 'PERSON'`. One `UPDATE` sets it for
      every existing session from what opened it, and its check is added `NOT VALID`, then validated.
    - `0700_session_settings`: six `session` columns and three checks on them. These are `env`, a JSON object,
      with `env_changed_at` and `env_applied_at`; `notify_turn_finished` and `notify_needs_you`, each null, `on`
      or `off`; and `notifications_muted`, default false.
  - **Translation:**
    - `0532_conversation_turn_translation`: three nullable `conversation_turn` columns and
      `conversation_turn_translation_chk`. The check is added `NOT VALID`, retrying on a 2 s lock timeout, then
      validated.
    - `0550_approval_translation`: a nullable `approval.translation`.
  - **Scheduled tasks:**
    - `0790_schedules`: the schedule tables and their types, `SCHEDULE` added to the `session_run_source` enum,
      and a nullable `session.schedule_run_id`.
    - `0830_schedule_run_start`: two nullable `schedule_run` columns and an index, and `SCHEDULE` added to
      `session.opened_by`'s check.
    - `0840_schedule_attention`: four nullable `owner_request` columns and an index, and its kind check widened
      by four `SCHEDULE_*` kinds.
    - `0860_schedule_check_only_asks`: a nullable `schedule_run.access_level`, filled for runs that have
      started, and `workspace_permission_rule.from_schedule_run`, `NOT NULL DEFAULT false`.
  - **Owner requests and handoffs:**
    - `0531_owner_request_wiki_create`: two nullable `owner_request` columns, `WIKI_CREATE` added to its kind
      check, and a partial unique index.
    - `0810_coordinator_handoff`: the `coordinator_handoff` table. Its directory also holds a `down.sql`, which
      nothing runs.
  - **Runners and machines:**
    - `0770_main_checkout_discard`: `main_checkout_request`'s action check widened to `discard`.
    - `0780_runner_presence_background_job_sessions`: `runner_presence.background_job_session_ids`,
      `UUID[] NOT NULL DEFAULT '{}'`.
    - `0870_managed_runner_image_roll`: a nullable `managed_runner.image_roll_to`.
    - `0880_attachment_guest_uploader`: a nullable `attachment.uploaded_by_guest_id`.
    - `0910_account_remove_sessions`: `runner.codex_account_remove_sessions`, `UUID[]` with an empty default,
      added with `ADD COLUMN IF NOT EXISTS`.

  Eleven are numbered below `0760_runner_attention_fixes`, the newest migration a 0.1.260 database has: `0524`,
  `0526`, `0527`, `0528`, `0531`, `0532`, `0550`, `0642`, `0645`, `0670` and `0700`. `prisma migrate deploy`, the
  apiserver's boot step, applies every migration the database has not recorded whatever its number, and the
  Prisma 7.10.0 this release pins does so. A database that ran beta.14 or beta.15 recorded `0910`'s column under
  its first name, `0870_account_remove_sessions`. There, `0910` finds the column and changes nothing.
- **Correction to the 0.1.260 notes.** 0.1.260 applied five more migrations than its notes listed, beside
  `0705_runner_engine_update_dismissals`, `0740_session_merge_after_turn` and `0760_runner_attention_fixes`:
  - `0660_terminal_credential`: new `terminal_login` and `terminal_credential` tables.
  - `0661_approval_decided_by_terminal`: the approval check widened to a `TERMINAL` credential.
  - `0662_turn_sender_client`: two nullable `conversation_turn` columns.
  - `0663_approval_decided_terminal_machine`: a nullable `approval.decided_terminal_machine_name`, and the
    approval and activity checks widened to `TERMINAL`.
  - `0730_session_work_subdir`: a nullable `session.work_subdir`.

  All five are additive: they create tables, add nullable columns and widen checks, and none rewrites existing
  rows. Some deployments upgrade from `v0.1.2-beta.246` (package 0.1.256), the release before `v0.1.260`,
  straight to 0.1.261. They apply thirty-seven migrations on boot:
  - the six in the [0.1.257 notes](0.1.257.md);
  - `0720_runner_presence_resources`;
  - the three the 0.1.260 notes name;
  - these five;
  - 0.1.261's twenty-two.
- **Session settings.** A session's own variables are laid over the workspace's when its engine starts. They win
  over the workspace's, a provider's injected variables still win over both, and `ORBIT_*` never comes from
  them. Restart, or Restart after this turn, reloads a live engine with them. Per-session notification
  overrides and the mute apply to every push transport (APNs, FCM, Feishu).
- **Main checkout and merges.** Commit no longer asks for a message: every commit is sent with a default message
  naming the chosen files ("Add a.ts and b.ts"). Discard asks for confirmation first and saves the whole
  checkout to `orbit/rescue-*`; a Discard that fails part way names that branch. A merge no longer waits for the
  session's turn: it runs beside it, and a commit waits for changes to stop.
- **API.** These changes are additive, and a client that does not read the new fields works as before:
  - `PATCH /sessions/:id/settings` writes a session's settings, owner-only. `POST /sessions/:id/restart` queues
    the reload, and an ended engine is refused 409 `ENGINE_NOT_RUNNING`. Both refuse a terminal credential.
  - `GET /sessions/:id` adds `settings`, `usage` and `engineVersion`.
  - `GET /sessions/:id/subagents` lists a session's SubAgent runs, each with its engine, read-only flag,
    changed files and description.
  - Schedules:
    - `/schedules`: the list, drafts, one schedule and its runs, pause, resume, run, undo and delete;
    - `POST /schedule-runs/:id/stop`;
    - `/schedule-requests`, with allow and decline.
  - Coordinator handoff: `POST /projects/:id/coordinator/handoff`, with `skip`, `cancel` and `retry`, and
    `GET /projects/:id/coordinator/pending-waits`.
  - `POST /wiki/spaces` is owner-only and refuses a second wiki for the same repository.
  - `POST /workspaces` takes `newFolder` with `runnerId`, held to the same rules as `POST /sessions`'
    `newWorkspace`.
  - `GET /sessions/:id/guests/suggestions` suggests people the owner invited before.
  - Refusals and failures from tasks, projects, sessions and spawns carry a stable code, a recovery action and
    whether the call may have written. `project_create` and `session_create` keep a receipt per request id.
  - Workspaces take `subagentsEnabled` and `subagentsMaxRunning`. A runner's own workspace door refuses them with
    400 `HUMAN_ONLY_WORKSPACE_FIELD`, as it does the model-routing fields.
  - `GET /projects/:id/handoffs` adds `toProject.coordinatorSessionId` and `fromProject.coordinatorSessionId` to
    each row. Each is null when that project has no coordinator or its coordinator is in Trash.
  - A machine's main-checkout view reports `discardSupported`.
- **Deployment.** No configuration changes are required. Pin the deployment to the tag `v0.1.261`, and deploy the
  server before the clients update, because the 0.1.261 clients call routes a 0.1.260 server does not have.
  - The upgrade skill now builds the `/dl` runner from the newest `v*` tag behind the deployed commit, not from
    the deployed tree. A deploy of `v0.1.261` serves the 0.1.261 runner, and a deploy from `main` between
    releases keeps serving the last release's runner
    ([release process](../docs/release-process.md#runner-binaries-come-from-the-release-tag)).
  - With a registry, the two-stage upgrade also builds and pushes `orbit-managed-runner` when its inputs changed,
    for deployments that run managed runners on Kubernetes.
  - With `ORBIT_MANAGED_RUNNERS_ENABLED` on, every signed-in account gets its managed runner. A hosted runner
    left on an earlier image rolls onto the profile's image once it is idle.
- **Clients.** macOS ships on the stable channel, and Macs on the beta channel move from their 0.1.261 beta to
  it. iOS ships marketing version `0.1.261` to TestFlight. Installed Android apps are offered `0.1.261`, those
  on a beta included. These builds carry the native changes merged since `v0.1.260`.

## Security fixes

None in this release. Nothing merged since `v0.1.260` fixes a security issue in a published release, and no
dependency lockfile changed beyond the root package's own version. The managed runner image now installs the
engine CLIs at pinned versions. The new session settings, restart and SubAgent routes refuse terminal
credentials from the start, as their siblings do. A read-only SubAgent cannot write. Codex's read-only sandbox
refuses its writes, and Orbit refuses its escalations, its file changes and any third-party MCP tool call that
reaches it.

**Correction to the 0.1.257–0.1.260 notes**, which each said "None". `v0.1.260` is the first published release
with the DeepSeek Harness MCP client fix. It moves `@modelcontextprotocol/client` and `@modelcontextprotocol/core`
from 2.0.0 to 2.4.0 in the two DSH lockfiles: `src/runner-go/dsh-install`, which runners install DSH from, and
`scripts/deepseek-harness-p0`. It fixes two advisories, reported as Dependabot alerts #75–#78:

- [GHSA-6qxp-vccf-f47h](https://github.com/advisories/GHSA-6qxp-vccf-f47h) (CVE-2026-104850, high): the SDK's
  OAuth client could send its credentials to an authorization server that a remote MCP server advertised.
- [GHSA-6prh-2h8m-c8cw](https://github.com/advisories/GHSA-6prh-2h8m-c8cw) (CVE-2026-111769, moderate): its
  HTTP transport re-sent custom headers and request bodies across cross-origin redirects.

Neither path was reachable through Orbit. Its DSH sessions configure no OAuth, and they run MCP servers over
stdio only: an HTTP entry is refused before the process starts. A machine that installed DSH before `v0.1.260`
keeps its old tree, because a published `engines/dsh/0.2.0-rc.2` directory is not reinstalled when the lockfile
changes; fresh installs take the patched one. See
[dependency security](../docs/dependency-security.md#mcp-client-in-the-deepseek-dsh-lockfiles-2026-11-13).

## Known limitations

- Android still labels a shared pool `SHARED`, where the web, macOS and iOS say "Shared".
- Android has no Reduce Motion fallback for the needs-you card's motion.
- On iOS 26 the drawer's waiting count is the system's toolbar badge, which VoiceOver reads as the bare number
  ("2") rather than "2 waiting on you".
- A SubAgent cannot ask the owner anything. AskUserQuestion and plan approval inside it are refused, and it is
  told to put the question in its result.
- While a runner scans its checkouts after a secret is removed, it refuses merges and pushes, because the
  secret-taint record fails closed. A slow scan therefore delays publishing.
- These limits from earlier notes still hold:
  - A failed model-list probe on a signed-out Claude is logged, but its cause is not known
    ([0.1.257](0.1.257.md)).
  - The machine page's resource history lives on an UNLOGGED table and empties on a database crash, and
    macOS CPU is averaged by `ps` ([0.1.258](0.1.258.md)).
  - The note on unattached reply files covers only links outside the session's directories
    ([0.1.259](0.1.259.md)).

The tag is `v0.1.261`. Its full source SHA is that tag's commit, which the account owner confirms before the
tag is created. The release workflow publishes:

- `Orbit-v0.1.261-arm64.dmg` and its Sparkle payload `Orbit-v0.1.261-arm64.zip`;
- `orbit-android-0.1.261.apk`, its `.sha256`, and `android-update.json`;
- a TestFlight build of `0.1.261`;
- the runner reference binaries;
- `SHA256SUMS`, a CycloneDX SBOM, SLSA provenance and `release-manifest.json`, with a GitHub artifact attestation
  ([supply chain](../docs/supply-chain.md)).

`/dl/version.json` names `0.1.261` once the server built from the tag runs.
`node scripts/release-identity.mjs check-tag v0.1.261` checks that every surface derives from the package version
and that these notes carry every section. The release workflow's `identity` job runs the same check before it
builds anything.

The tag is cut only once a dispatch of `ci.yml` on the release commit has reported all six of `main`'s required
checks green on that commit: JavaScript, Go runner, Swift core, Dependency review, Container images and
PostgreSQL specs. A dispatch of `client.yml` must also have built macOS and iOS. Record those run URLs and the
asset digests in the Release once the release run finishes.

## Rollback

The rollback target is the latest published stable release,
[`v0.1.260`](https://github.com/jianghailong-xy/orbit/releases/tag/v0.1.260) (source
`9328d738028b849b01df992ebba1c32b6935fd6e`). It is the one target: a deployment, runner or client that also ran a
0.1.261 beta goes back to `v0.1.260` too. Record the image IDs and the source SHA you are running before
upgrading.

The migrations are additive, and every new foreign key cascades or sets null, so the 0.1.260 application starts
against the upgraded schema. Some data that 0.1.261 writes breaks 0.1.260, though. Clear it before you roll the
application back:

1. **Sessions a schedule started.** 0.1.260's Prisma client does not know the `SCHEDULE` value that `0790` added
   to `session_run_source`. Reading such a session fails with `Value 'SCHEDULE' not found in enum
   'SessionRunSource'`, and so does any list that includes one, such as the owner's session list. Pause or delete
   every schedule and let its runs end. Then relabel the sessions it started:
   `UPDATE "session" SET "run_source" = 'MANUAL' WHERE "run_source" = 'SCHEDULE';`. They keep their
   `schedule_run_id`, and after a later return to 0.1.261 they read as ordinary sessions.
2. **Messages held for their translation.** When a session ends, 0.1.260 marks every unanswered message
   answered. `conversation_turn_translation_chk` refuses that for a message held while it is translated, or after
   its translation failed. The completion then rolls back and the runner retries it every 2 s, so the session
   never finishes; 0.1.261 leaves held messages alone. Turn Translation off, then use Send as written or withdraw
   on each held message, until `SELECT count(*) FROM "conversation_turn" WHERE "status" = 'HELD'` returns 0.
3. **Work 0.1.260 has no handler for.**
   - Let any pending main-checkout Discard finish, running SubAgents end and any coordinator handoff complete.
   - Answer or withdraw owner requests of the kinds 0.1.260 does not know: `WIKI_CREATE` and the four
     `SCHEDULE_*` kinds. It still lists them, but cannot carry them out.

The rest of what 0.1.261 wrote stays in the database, and 0.1.260 ignores it. That covers session settings
(sessions start with the workspace's variables, and notifications follow the account's switches), schedules,
translations, handoff notes, create receipts and SubAgent runs.

Move runners back first, with the `/api/runner/release` pointer: they do not move back by themselves, and a
0.1.261 runner's `delegate` needs a 0.1.261 server. A runner back on 0.1.260 takes later automatic updates under
0.1.260's rules again.

Keep PostgreSQL and its archive running. Reinstall the 0.1.260 DMG or select its TestFlight build only after
confirming server compatibility. Android's `versionCode` only increases, so fix forward rather than downgrade
the APK. See [Release process](../docs/release-process.md#rollback-decision-and-procedure).
