# Orbit 0.1.261-beta.47

## Summary

This release brings macOS, iOS and Android in line with what the web already drew: a scheduled run's session is
a session of its workspace. A run opened from a schedule's history, from Waiting on you or from a notification
now goes through the ordinary session route, with its workspace selected and the session list showing its
Scheduled runs folder, and Back returns to that folder instead of the schedule. The Scheduled section's own
run-session layout, its "‹ schedule title" crumb, its "Run of Nov 13" title and its "Open · Codex agent · 4 min"
head line are gone; the header and the watch control are any session's. The run's strip, which says when it was
planned or which condition fired it and with what access, and its report after the end stay in the conversation.
There are no server, database, runner or web changes in this range.

- **A run's session is an ordinary session on macOS and iOS.** Opening a run from a schedule's history, a
  timeline row, Waiting on you or a notification calls the app's session route with the Scheduled runs folder
  (`route(to:inScheduledRuns:)`), rather than the Scheduled section's own panel: the session's workspace is
  selected, the sidebar lights that workspace, and the navigation stack carries the Scheduled runs folder under
  the session so Back opens it (`SessionFolderAddress.scheduledRuns(for:)`). A cold route learns its workspace and
  lifecycle from the session's own read and puts the folder beneath it without disturbing any navigation made
  while it loaded. The Scheduled section's run-session layout is removed: on the Mac its detail column again shows
  only a row's detail or a draft's create card, and the phone's Scheduled stack no longer carries a
  `navigationDestination` for a run's console. The transcript's first card keeps the run's planned time or fired
  condition and access, and its last keeps the report.
- **The same on Android.** Schedule history, timeline rows and Waiting on you open a run's session through the
  ordinary session reader (`openRun`). The route lands on the session's own workspace, then its Scheduled runs
  folder, then the session, so Back opens the folder; a workspace is taken from the session's own detail, since a
  schedule may have moved since the run. A timeline row whose run has a session opens that session, and a schedule
  with no run session still opens its detail sheet. `ScheduleRunStrip` and `ScheduleConversationInsert` lose the
  crumb, the "Run of …" title and the head line, and keep the firing and access line and the report.
- **No head line is drawn anywhere.** `runHeadText` and `runAgentName` are deleted from `ScheduleDisplay` on both
  OrbitKit and Android core, with their tests, so "Open · Codex agent · 4 min" no longer appears above a run's
  transcript; the session's own header draws its state, and its console draws the watch control.
- **Also.** The Apple change landed as two commits: c186119f19 removed `scheduled` and `s` from the schedule
  detail's `historySection`/`historyRow` while the record row's Undo still called `scheduled.undo(s.id, …)`, so
  OrbitApp did not compile on macOS or iOS, and af64083462 passes both through again. Without that second commit
  the release tree would not build; it changes no behaviour a user sees. The rest of the range is the test and
  fixture changes that follow the product change (the Apple wiring, entrance and display tests, the Android
  `ScheduleDisplayTest`, `SessionListPageShellTest`, `ConditionShotsTest`, `ScheduledDeviceTest` and the shell
  fixture). No user-facing change comes from those files.

## Upgrade impact

- **Database migrations: none.** `git diff v0.1.261-beta.46 origin/main -- src/apiserver/prisma/migrations/` is
  empty, so the apiserver applies nothing on boot and the schema is the one v0.1.261-beta.46 left.
- **Server:** no apiserver change in this range. The deploy is unchanged from the previous release.
- **Runner:** the runner served at `/dl` is built from this tag. It carries no runner change: no Go file under
  `src/runner-go/` differs from v0.1.261-beta.46, so a runner from the previous release behaves identically.
- **Configuration:** nothing must be set before or during the upgrade. No Compose file, deploy script or engine
  pin changes in this range.
- **Clients:** macOS beta users get the DMG on the beta channel, TestFlight gets marketing version 0.1.261 with
  the build number as the commit count, and Android gets `android-update.json` from this tag with `versionName`
  0.1.261-beta.47. The new behaviour is client-only, so no minimum server or runner version is set: a client from
  this tag against a server older than this commit works as before, and a client from an older release against
  this server simply keeps drawing a run's session its own way.

## Security fixes

None in this release. No commit in this range names a security fix, an advisory or a CVE, and no dependency is
added, removed, moved or bumped: `package.json` and `package-lock.json` differ from v0.1.261-beta.46 only in the
version lines the release commit writes.

## Known limitations

None known. Two behaviours in this range are by design: a run's session is opened through the ordinary session
route, so on the Mac it no longer fills the Scheduled section's right-hand column and the schedule's own head
crumb is not drawn (Back returns to the session's Scheduled runs folder instead), and Android still opens a
schedule's detail sheet for a run that has no session id. A client from an older release keeps the previous
layout until it updates.

## Artifacts and verification

The tag is v0.1.261-beta.47, and this file is in the release commit's tree. The release is prepared on origin/main
commit 5e723028a9117079d2b15781f7e1bf4781fc9889; the release commit adds the version lines in `package.json` and
`package-lock.json` and this file to that tree, and the tag names it. The release publishes the macOS DMG and
Sparkle appcast (beta channel), an iOS TestFlight build and the Android APK with its `.sha256` and
`android-update.json` on the same GitHub Release, all from this tag; the runner served at `/dl` is built from this
tag.

None of the four commits in this range records a test run, a CI run or a build result: c186119f19, af64083462,
207a7e6f99 and the merge 5e723028a9 each give only the change and its reason, so these notes credit no check to
them. What was verified was run directly at 5e723028a9, and is recorded here rather than in those messages:

- A Mac running Xcode 27.0 built OrbitApp for macOS with `swift build` and the iOS app for the simulator with
  `xcodebuild`, which reported BUILD SUCCEEDED.
- On the same Mac and tree, OrbitKit's `swift test` ran 5588 tests, 5 skipped, 0 failures.
- Android unit tests on the same tree have three failing tests: `LandingCheckShotsTest.baseline`,
  `ProjectDataTest.everyProjectCallHitsItsRoute` and
  `ProjectPageTest.theOwnersStartTakesTheDefaultRuleAndAPressSendsEverySetting`. All three fail identically on
  origin/main's own Android files without this release's Android changes, so they are known red and not caused by
  this release. Every other failure in a loaded full run passed when its class was re-run alone.

No screenshots of the new navigation are recorded as evidence with this release.

## Rollback

The previous tag is v0.1.261-beta.46, commit 471eefe4bc88db731dec0a04ab892c07c6fc8764 (its tag object is
0fcda020dcc6ada478cfde26ea35e1dcbfc37833), on origin. This range carries no database migration and no server or
runner change, so an application-only rollback to that tag is schema-safe: there is nothing to undo, no backup or
restore step is needed, and no data is affected. Rolling back restores the previous client behaviour — a run's
session opened over the Scheduled section with its crumb, its "Run of …" title and its head line, and on the Mac
in the section's right-hand column — for any client that also rolls back, since the change is client-only. See
[Release process](../docs/release-process.md#rollback-decision-and-procedure).
