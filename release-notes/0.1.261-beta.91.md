# Orbit 0.1.261-beta.91

## Summary

- **Runner: an agent can copy a whole directory into Documents once, in the background.** `documents_sync` (MCP) and `orbit documents sync` (CLI) start a runner-hosted job that walks a local directory, uploads what Documents does not already have the same, skips the rest, and optionally moves what the local directory no longer holds to Trash with `--delete`; `--wait` runs the same sync in the foreground. The call answers at once with the background job's id and returns the turn to the agent; `bg_output` shows its progress, `bg_kill` stops it (files already committed stay), and when it ends its normal wake tells the agent, with a summary line naming the destination, a link, how many files were uploaded, unchanged and deleted, the bytes and any failures. The local directory is checked before the job starts: it must be inside the session's checkout or uploads directory, it must not be inside the Documents mount, the destination is normalized as `documents_put` does, and `--delete` with `/` as destination is refused. `orbit drive sync` answers too, since `orbit drive` is the same command.

- **Web: each sync appears in the Documents page's upload tray.** A running sync draws as a row beside the owner's own uploads, in the bottom-right tray: "Checking files…" while it compares, then files done of total, bytes sent of total, the rate and an estimate of the time left. A finished one reads how many files it synced and how much it sent — or "Already up to date" with the count of files that were already the same when nothing needed sending — and how many `--delete` moved to Trash; a failure or a partially failed sync draws a Details dialog listing each path and its error, with a button to open the destination folder. A sync row has no Pause or Cancel — the agent owns the run. "Clear finished" hides ended syncs in this browser only. The tray refreshes on the control plane's `drive.sync` event, on focus, after a reconnect, and every 5 s while one runs and the page is visible.

- **Server: a new `document_sync` record, a list route and a realtime event carry that progress.** Migration 1560 adds the table; the runner opens one row when a sync starts and reports into it at most every two seconds; the owner reads the running syncs and those that ended in the last 24 hours from `GET /api/documents/syncs` (`/api/drive/syncs` too, like every Documents route), and the runner reports to `/api/runner/documents/syncs` (`/api/runner/drive/syncs`). A running row whose runner has sent nothing for two minutes reads as Stopped without being written as such, and opening a sync prunes the owner's rows that ended more than a day ago. A new `drive.sync` control event nudges only a stream that declared `hints=drive_syncs`.

- **Server: Documents is now behind an off-by-default switch, `ORBIT_DOCUMENTS_ENABLED`.** Only the value `true` turns it on; absent, empty, `false` and anything else leave it off, with one warning in the log for a value that is neither. Off, the server meets a client the way one without the drive would: every route of the owner's door and the runner's door (and their `/drive` aliases) answers `404 DOCUMENTS_DISABLED` before reading anything, a Documents file cannot be shared, `GET /api/auth/capabilities` says `documents.enabled: false`, and sessions are claimed with `documentsDisabled`. Nothing is deleted — what the drive holds is there again when the switch is turned back on.

- **Web: Documents is hidden while the server has it off.** The web reads `documents.enabled` from `/auth/capabilities`; absent or unreadable reads as on, so a server from before the switch keeps Documents. Off, the sidebar's Documents entry, its routes, the composer's Documents picker and Documents link cards in transcripts are gone, and no Documents API request is made.

- **Runner: a session claimed while the server has Documents off gets no drive tools.** The server says on each claim and reclaim whether it has Documents; the runner spawns the engine with `ORBIT_DOCUMENTS=off`, and there `orbit mcp` lists no Documents tools (`documents_put`, `documents_get`, `documents_list`, `documents_move`, `documents_delete`, `documents_sync`) and refuses them, `orbit drive` refuses, and the agent's instructions and guide leave the drive out. A `404 DOCUMENTS_DISABLED` answered mid-session reads the same. Only an explicit off turns it off, so a runner that predates the flag, and a server that predates the switch, keep what they had.

- **Apple: only the agent-tools guide changes.** The generated guide both apps read is regenerated to list `documents_sync`; no Apple screen changes in this release.

- **Android: no change in this release.**

## Upgrade impact

- **Migrations:** one new migration, `1560_document_sync`, and it is **additive**. It creates one new table, `document_sync` — the id; the owner and runner foreign keys (both `ON DELETE CASCADE`); the sync's source name, destination, status, file and byte counts, the failed list (at most 100 paths, with a count of them all), an optional error, and start, update and end timestamps — with two indexes (`owner_id, started_at DESC` for the tray's read, and `runner_id` for a runner's cascade) and checks on the status values, on `ended_at` being set exactly when the sync has ended, and on the counts being non-negative. No existing table, column, row, index, trigger or function is touched, nothing is renamed, and no older build reads the new table. It takes no locks on existing data and every statement is guarded so it runs twice safely. A host coming from beta.90 already has 1550 and 1551 applied; 1560 applies on the first boot of the new apiserver.
- **Configuration — one step for a deployment already using Documents:** `ORBIT_DOCUMENTS_ENABLED` is new and off unless it says `true`. `docker-compose.yml` passes `${ORBIT_DOCUMENTS_ENABLED:-false}`, and a fresh install writes `false`. Neither install nor upgrade writes `true` for you: a deployment that predates the switch has Documents **off** after this upgrade, with everything its drive holds kept on disk and in the database, until its `.env` says `ORBIT_DOCUMENTS_ENABLED=true` and the apiserver is recreated. Set it before or with the upgrade if the deployment uses Documents. (The upgrade's first version wrote `true` where the drive already held files; that was removed, because it turned Documents on for self-deployed users who had not asked for it.) Moving the line later is fine: nothing is deleted while off.
- **Server:** the first boot applies 1560. There is no backfill and no other database step.
- **Runners:** the runner served at `/dl` is built from this tag and carries `documents_sync`, `orbit documents sync` and the switch: a session claimed with `documentsDisabled` starts with `ORBIT_DOCUMENTS=off` and no Documents tools. Orbit Cloud runners get it from the `orbit-cloud-runner:0.1.261-beta.91` image, built from this tag. An older runner keeps working against the new server, and a new runner keeps working against a server from before the switch.
- **Clients:** web arrives with the deploy of this commit; macOS (beta channel DMG), iOS (TestFlight) and Android (APK) come from this tag. The Apple clients take only the regenerated agent-tools guide, and Android is unchanged. No one-time step on a Mac, iPhone or Android device.

## Security fixes

None in this release.

## Known limitations

- The Apple and Android clients do not read the Documents switch in this release. With Documents off, the web hides it and the runner's sessions have no Documents tools, but an Apple or Android app still draws its Documents entry and every request it makes answers `404 DOCUMENTS_DISABLED`.
- A sync is one-shot: nothing keeps watching the local directory. A later change is another sync, which only sends what is still missing.
- The sync's local directory must be inside the session's checkout or uploads directory and outside the Documents mount. A Plan-mode session is refused the same way `bg_run` is, and a session without the background job service gets `BG_TRANSPORT_UNAVAILABLE`; `--wait` runs the same sync in the foreground there.
- Ended syncs are listed for 24 hours and the tray is sent at most 50. A running sync whose runner stopped reporting for two minutes reads as Stopped without the row being written as one, and "Clear finished" hides ended syncs in that browser only.

## Rollback

Previous tag v0.1.261-beta.90 (`b013098a69`). Application-only rollback is **schema-safe**: 1560 only adds the `document_sync` table, which the previous release never reads, so it can stay; Prisma's startup migration does not undo applied migrations, and none needs undoing. The previous release knows no switch, so Documents is served as before, with everything the drive holds; the sync tool, its routes, the `drive.sync` event and the tray's sync rows are gone, and a rolled-back server serves no sync route.

Client rollback is to the last published builds, v0.1.261-beta.90's DMG, TestFlight build and `orbit-android-0.1.261-beta.90.apk`.
