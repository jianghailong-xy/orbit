# Orbit 0.1.261-beta.50

## Summary

This release reworks the **Scheduled page**: the separate *Needs you* group is gone, and a schedule that
failed stays on the day of its next run carrying a **Failed** tag on its own row, which clears once a run
of it is under way. The **project sessions button** on web and Android now spins while anything its page
shows is active, matching iOS. The composer's **prompt suggestion gets the whole line** on iPhone, iPad,
Mac, Android and phone web. An **owner request's resolution turn** is drawn as a divider on iOS/macOS and
Android, as web already does, and the web **Agents strip** drops its Running / Done headings. On the server
side, a **performance migration** indexes the rare facts five owner-scoped reads were scanning whole tables
to find.

- **Scheduled page, every client (web, macOS/iOS, Android).** The schedules list by day; a failing one keeps
  its place on the day of its next run and carries the Failed tag on its own row (owner 2026-11-19). While a
  run of it is under way — *Run now*, or its next slot — the tag is off and the drawer does not count it: a
  failure puts it back, and a run that did not fail clears it. Held schedules, which have no next run, are
  listed first under Paused, and a condition that cannot be read leads "Waiting for a condition". The copy
  contract (`contracts/schedule.contract.json`) drops `groups.NEEDS_YOU`.
- **Project sessions button spins while its page is active (web, Android).** As iOS already did (owner
  2026-11-17, board `docs/mocks/project-sessions-button-running`, option C): the glyph gives its place to
  the running spinner while a member or landing session works or has a background job, a landing job runs or
  waits, or a merge into main is being checked or landing. On web the title bar's member reads are polled
  like the page's, and the landing line and merge are read only while the page is shut; on Android the
  one-shot count read becomes reads that follow the account stream, polling the landing line and merge every
  4 s while one is active, and all of them pause while the sheet is open. TalkBack reads "Active".
- **Prompt suggestion gets the whole line (iOS/iPad/Mac, Android, phone web).** On an iPhone the translation
  tag and "Double-tap to use" left the guess 5–7 characters. While a suggestion is on offer the composer's
  translation tag gives way on iOS/iPad/Mac and Android, except when it warns that translation is
  unavailable, and the touch hint reads "Double-tap" (iOS, Android, phone web). Web's tag sits in the
  toolbar, so only its hint changes. Board: `docs/mocks/prompt-suggestion-room` (option B).
- **An owner request's resolution turn is a divider (iOS/macOS, Android).** Both drew the turn Orbit queues
  when an owner request ends as a user bubble carrying prose and JSON for the agent. They now draw it as
  web's divider, "Owner action resolved · turn started automatically". Web's head pattern also missed
  `WIKI_CREATE`'s "ended DONE." wording, which this fixes.
- **Web: the Agents strip drops its Running / Done headings.** The opened list keeps its order (running
  first, then ended, newest first); the status glyph on each row already tells them apart.
- **Server: indexes for the rare facts owner-scoped reads scanned whole tables for (migration 1130).** One
  owner holds 114k of production's 115k tasks (109k of them a paused pipeline's OPEN backlog), so an index
  that starts with `owner_id` or `status` is a full scan for that owner. Migration `1130_rare_predicate_indexes`
  adds three partial indexes — `task_fork_snapshot_idx` (`fork_runner_id` where `fork_sha` is not null),
  and `session_bg_jobs_live_idx` / `session_bg_shells_live_idx` using Prisma's own `<> '{}'` predicate — and
  five reads are narrowed: the runner's fork-snapshot read, the workspace background-job/shell tallies, the
  schedule read's start-when list (now stating `startWhenConditionId IS NOT NULL`), the sweep's
  independent-task scan (narrowing to the moving projects in the same statement), and wiki maintenance's
  project lookups (probed per project with `EXISTS`). The rows returned are unchanged.
- **Also.** Design boards and design docs are updated under `docs/mocks/` (`prompt-suggestion-room`,
  `project-sessions-button-running`) and `docs/` (`scheduled-tasks-design.md`,
  `condition-triggers-design.md`), and `docs/postgres-runtime-settings.md` §12 records the
  `maintenance_work_mem` review, kept at 64 MB.

## Upgrade impact

- **Database migration: one, additive.** `src/apiserver/prisma/migrations/1130_rare_predicate_indexes/migration.sql`
  is new: it creates three indexes (`task_fork_snapshot_idx`, `session_bg_jobs_live_idx`,
  `session_bg_shells_live_idx`) with `CREATE INDEX IF NOT EXISTS`. It writes no row and drops or changes
  nothing, so it is schema-safe in both directions. As with the other index migrations (0283, 0305, 0353,
  0361, 0417, 0420) the indexes are built inside the migration's transaction, not `CONCURRENTLY`, each one a
  single pass over a small table (`task` is 256 MB of heap, `session` 33 MB), holding a `SHARE` lock that
  long; every statement can run twice. The apiserver applies it on boot as usual; there is nothing to run by
  hand.
- **Server:** besides the migration, four reads change in `src/apiserver/src/` — `runner-api/runner-api.controller.ts`
  (comment only, reading through the new index), `schedules/schedule-reads.service.ts`, `tasks/tasks.service.ts`
  and `wiki/wiki-maintenance.ts`. Each returns the same rows; only the plan changes. Tagging does not deploy
  the server: these reach an instance only when it is upgraded from this source. An apiserver on the previous
  release behaves as it did.
- **Web:** the Scheduled page, the project sessions button, the prompt-suggestion hint and the Agents strip
  reach browser users only when the deployment's web is rebuilt from this source; the tag does not deploy
  the web app.
- **Runner:** no Go file under `src/runner-go/` differs from v0.1.261-beta.49, so a runner from the previous
  release behaves identically. The runner served at `/dl` is built from this tag.
- **Configuration:** nothing must be set on a server, and the release pipeline needs no new secret.
- **Clients:** macOS beta users get the DMG on the beta channel. TestFlight gets marketing version 0.1.261,
  with the build number as the commit count. Android gets `versionName` 0.1.261-beta.50 and
  `android-update.json` from this tag. Nothing the clients draw here needs a newer server: the Scheduled
  page, the project sessions button, the prompt suggestion, the owner-request divider and the Agents strip
  all draw data the clients already receive.

## Security fixes

None in this release. No commit in this range names a security fix, an advisory or a CVE. No dependency is
added, removed or bumped: `package.json` and `package-lock.json` are unchanged between the two tags, apart
from the version line this release commit writes. The migration adds indexes only; it grants no new access
and reads no new data.

## Known limitations

- **The macOS DMG container is not codesigned.** It is notarised and stapled, so Gatekeeper accepts the app,
  but `spctl` reports the `.dmg` itself as having no usable signature. This predates this release.

## Rollback

The previous tag is v0.1.261-beta.49, commit `6f40c3d7891c3964ecddd8eb2f3df553582354c7` (its tag object is
`da694bfa8b18e12f3b27feda262482eff468a2f1`). For clients, rolling back removes the new Scheduled page
behaviour, the spinning project sessions button on web and Android, the whole-line prompt suggestion, the
iOS/macOS and Android owner-request divider and the web Agents-strip change; they draw what they drew before.

An application-only rollback to beta.49 is schema-safe, because migration `1130_rare_predicate_indexes`
only adds indexes: it changes no column, row or constraint, so an older apiserver runs against a schema that
merely carries three extra indexes and is unharmed. No backup or restore step is needed. See
[Release process](../docs/release-process.md#rollback-decision-and-procedure).
