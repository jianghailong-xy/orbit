# Orbit 0.1.261-beta.12

## Summary

The work merged since [0.1.261-beta.11](0.1.261-beta.11.md), on the beta channel: GitHub-backed workspaces (docs/github-workspace-design.md), whose runner half is below.

- **Runners clone GitHub workspaces.** A runner now declares `clone-workdir/v1`
  (docs/github-workspace-design.md §6). For each workspace the control plane asks it to clone, the runner
  checks the folder the same way it checks one Orbit makes: inside the repos root, no `..`, symlinks
  resolved. A folder already holding a clone of the same repository is reported ready. Any other folder at
  that path fails with "`<path>` already exists on `<machine>`". The clone runs in a temporary directory
  inside the repos root and is renamed into place when it is whole. It keeps the full history. It fails
  after 30 minutes without progress. A restart removes the unfinished clone and starts it again. The
  heartbeat carries the clone's state, git's progress percentage and which credential cloned it
  (`machine` or `github-app`).
- **Orbit's GitHub credential.** The machine's own Git credential is tried first. If it has none, or GitHub
  refuses it, the runner asks `POST /runner/git-credential` for the GitHub App's token for that one
  repository and tries once more. The same applies to landing fetches and pushes in a checkout Orbit cloned,
  so managed runners can push work back to GitHub. The token is handed only to that one git command's
  credential helper, and only for that repository on github.com. It is never written to `.git/config` or the
  remote URL, never put in an engine's environment, and the command runs no hook. A session in such a
  checkout is told: "This checkout's GitHub credential is Orbit's: land your work to push it."
- **From GitHub on the web.** A machine's setup card offers From GitHub where the deployment has a GitHub App:
  connect GitHub, pick one of your repositories (most recently pushed first, private ones marked), keep its
  default branch or name another, and the folder it is cloned into. The conversation's first line shows the
  clone's progress, then the workspace it made with a link to the repository, or why the clone failed with
  Retry. Settings → GitHub lists the workspaces from GitHub and the credential each one's clone used. A GitHub
  workspace isolates its sessions in worktrees from the start, so their work lands back to the repository.

## Upgrade impact

- **Database migrations,** applied by the apiserver on boot: `0820_github_app_connection` (GitHub workspaces P0)
  creates `github_app_config`, `github_connection` and `github_oauth_flow`, and adds seven nullable clone columns
  and one CHECK to `workspace`; `0880_workspace_clone_credential` (P2) adds the nullable `workspace.clone_credential`
  and one CHECK. Nothing is backfilled.
- **Runners update themselves.** `0.1.261-beta.12` orders above `0.1.261-beta.11`. `runner-release.json`
  stages it at 40% of runners, and the rest stay on 0.1.261-beta.11 until the percentage is raised. Only a
  runner on this release can be picked for a workspace made From GitHub.
- **Configuration.** No changes required.

## Security fixes

None in this release.

## Known limitations

- An agent's own `git fetch` or `git push` in a GitHub workspace on a managed runner has no credential. Its
  work reaches GitHub through Orbit's landing.
- The known limitations of [0.1.261-beta.11](0.1.261-beta.11.md) still apply.

## Artifacts and verification

The release identity is `package.json` `0.1.261-beta.12` and tag `v0.1.261-beta.12`. The runner binaries on
`/dl` are built from this tag.

## Rollback

Set `"rollback": "0.1.261-beta.12"` in `runner-release.json` and deploy. Runners go back to 0.1.261-beta.11
at their next idle update check. The migrations only add tables and nullable columns, which older code ignores.
