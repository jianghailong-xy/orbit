# Orbit 0.1.261-beta.51

## Summary

This release carries a **failing landing baseline that keeps its own card once it is escalated to the
owner** (web, iOS/macOS, Android), a **background job's approval card that closes when its job ends**, a
**new session that defaults to a credential able to run on its machine** (web, iOS/macOS), **Android's
composer redrawn as iOS's card**, a tidier **"Sent to the agent in English" line on iPhone**, OpenCode key
and catalog fixes, and a scheduled run that may wait on its own background job.

- **Escalated baseline items keep the baseline card (web, iOS/macOS, Android).** A shared baseline item
  (`INTEGRATION_CHECK_FAILED` with `baseline`) that had been escalated, handed over, or left without a
  coordinator was drawn as the "Who fixes it?" card, which is shaped around one task's branch. It lost the
  heading "Baseline checks failing on <branch>", the line "The project branch with the latest main fails its
  checks without this task.", the Landings on hold / Upstream / Project tip / Combined baseline / Landing
  check facts, the "View held tasks" links and "Landings resume automatically when this open item is
  resolved." On web it also told the owner to push a fix to the task branch. A baseline item now never
  takes the "Who fixes it?" layout, whoever holds it, and web's escalated card is headed with the baseline
  title. Android already drew it this way since `f42d26ba05` (in v0.1.261-beta.49); this release brings web
  and iOS/macOS level with it and pins the escalated case with a test on each client (`9120d2b8b3`).
- **A job's approval card closes when its job ends (server).** A `bg_run` job that asked for approval and
  was then killed left its card PENDING until the turn ended, and a generating session counted every PENDING
  card, so the conversation read "Waiting for approval" with no card to press. The server now collects a
  job's cards in the same ingest that records the job's end and sends `APPROVAL_RESOLVED` for each, and the
  live-approval count and the session list count a job's card only while its job is still running
  (`0173cdeb0a`).
- **A new session defaults to a credential that can run on its machine (web, iOS/macOS).** When nobody
  picked one in the draft and what the workspace last ran on can't run on this machine (the runner's Claude
  region, a sign-in gone, a CLI missing), the draft lands on the same engine's first credential that runs,
  else the first other installed engine that has one, and the hero says why ("Using DeepSeek · Anthropic
  unavailable on jdcloud · Details"). With nothing usable the send is held and the hero offers another
  provider. An explicit pick is never moved (`6969aaab15`).
- **Android's composer as iOS draws it (Android).** One rounded card holds the attachments, the text and
  the toolbar: + and the permission mode on the left; the model with its effort, a context ring, Optimize
  and a round Send/Stop on the right. The context line becomes a ring that opens a bottom sheet with the old
  dialog's rows; a full row gives way as iOS does (Optimize folds to ✦, then the effort, then the name
  truncates). A failed upload drops its chip and says "Upload failed — <file>: <reason>" (`69da451119`).
- **"Sent to the agent in English · Hide original" on one line (iOS/macOS).** With both languages shown,
  the line under a message on a phone wrapped into two lines beside the time and sat out of line with it.
  It now ends the copy/time row on one line, flush with the bubble, and moves to a line of its own under the
  time only when the row has no room (`f94beb63cf`, `258c2803e2`).
- **OpenCode (runner, server).** An OpenCode 401 now reads as a provider auth failure, so the turn says
  "Failed to authenticate" and the clients offer the rejected-key card; the model catalog probe runs with a
  private, empty config as sessions do, so a provider defined only in the global `opencode.json` is no
  longer offered and then refused; and the runner pages drop "no provider key found" when the owner holds an
  Orbit key OpenCode can spend (`6ba3b1370e`).
- **A scheduled run waiting on its background job is not NO_REPORT (server).** A run whose session ended
  its turn to wait for a `bg_run` job was failed NO_REPORT about 30 s later and its eventual report refused;
  an idle session now counts as working while it has a running job or watch, or a turn still pending
  (`17bb9ace28`).

## Upgrade impact

- **Database migrations:** none.
- **Server:** the approval-card, OpenCode key and scheduled-run fixes are apiserver changes, so they take
  effect once the apiserver is deployed from this commit or later; the web client ships with the same deploy.
- **Runner:** the OpenCode auth and catalog fixes are runner changes; the runner served at `/dl` is built
  from this tag.
- **Configuration:** nothing to set before or during the upgrade.
- **Clients:** macOS beta users get the DMG on the beta channel, TestFlight gets marketing version 0.1.261
  with the build number as the commit count, and Android gets `android-update.json` from this tag with
  `versionName` 0.1.261-beta.51. The change reads only fields the server already sends.

## Security fixes

None in this release. No commit names a security fix, advisory or CVE, and no dependency is added,
removed or bumped: `package.json` and `package-lock.json` change only in the version line this release commit
writes.

## Known limitations

- **The macOS DMG container is not codesigned.** It is notarised and stapled, so Gatekeeper accepts the app,
  but `spctl` reports the `.dmg` itself as having no usable signature. This predates this release.

## Rollback

The previous tag is v0.1.261-beta.50, commit `a1282659a41fb8ffbb8994e286eb447551017b0a`. Rolling back puts
the escalated baseline item back on the "Who fixes it?" card on web and iOS/macOS (Android keeps the baseline
card, which beta.49 already drew), and a rolled-back apiserver again leaves a killed job's approval card
pending until the turn ends. It also takes back the new-session credential fallback, Android's
composer card, the one-line bilingual foot on iPhone, the OpenCode fixes and the scheduled-run wait. No migration is involved, so an application-only rollback is
schema-safe and no backup or restore step is needed. See
[Release process](../docs/release-process.md#rollback-decision-and-procedure).
