# Orbit 0.1.261-beta.51

## Summary

This release carries two fixes: a **failing landing baseline keeps its own card once it is escalated to
the owner**, on web, iOS/macOS and Android alike, and a **background job's approval card closes when its
job ends**, so a conversation no longer reads "Waiting for approval" with no card to press.

- **Escalated baseline items keep the baseline card (web, iOS/macOS, Android).** A shared baseline item
  (`INTEGRATION_CHECK_FAILED` with `baseline`) that had been escalated, handed over, or left without a
  coordinator was drawn as the "Who fixes it?" card, which is shaped around one task's branch. It lost the
  heading "Baseline checks failing on <branch>", the line "The project branch with the latest main fails its
  checks without this task.", the Landings on hold / Upstream / Project tip / Combined baseline / Landing
  check facts, the "View held tasks" links and "Landings resume automatically when this open item is
  resolved." On web it also told the owner to push a fix to the task branch. A baseline item now never
  takes the "Who fixes it?" layout, whoever holds it, and web's escalated card is headed with the baseline
  title. Android already drew it this way since `f42d26ba05` (in v0.1.261-beta.49); this release brings web
  and iOS/macOS level with it and pins the escalated case with a test on each client (`9120d2b8b3`).
- **A job's approval card closes when its job ends (server).** A `bg_run` job that asked for approval and
  was then killed left its card PENDING until the turn ended, and a generating session counted every PENDING
  card, so the conversation read "Waiting for approval" with no card to press. The server now collects a
  job's cards in the same ingest that records the job's end and sends `APPROVAL_RESOLVED` for each, and the
  live-approval count and the session list count a job's card only while its job is still running
  (`0173cdeb0a`).

## Upgrade impact

- **Database migrations:** none.
- **Server:** the approval-card fix is an apiserver change, so it takes effect once the apiserver is deployed
  from this commit or later; the web client ships with the same deploy.
- **Runner:** no runner change; the runner served at `/dl` is built from this tag as usual.
- **Configuration:** nothing to set before or during the upgrade.
- **Clients:** macOS beta users get the DMG on the beta channel, TestFlight gets marketing version 0.1.261
  with the build number as the commit count, and Android gets `android-update.json` from this tag with
  `versionName` 0.1.261-beta.51. The change reads only fields the server already sends.

## Security fixes

None in this release. Neither commit names a security fix, advisory or CVE, and no dependency is added,
removed or bumped: `package.json` and `package-lock.json` change only in the version line this release commit
writes.

## Known limitations

- **The macOS DMG container is not codesigned.** It is notarised and stapled, so Gatekeeper accepts the app,
  but `spctl` reports the `.dmg` itself as having no usable signature. This predates this release.

## Rollback

The previous tag is v0.1.261-beta.50, commit `a1282659a41fb8ffbb8994e286eb447551017b0a`. Rolling back puts
the escalated baseline item back on the "Who fixes it?" card on web and iOS/macOS (Android keeps the baseline
card, which beta.49 already drew), and a rolled-back apiserver again leaves a killed job's approval card
pending until the turn ends. No migration is involved, so an application-only rollback is
schema-safe and no backup or restore step is needed. See
[Release process](../docs/release-process.md#rollback-decision-and-procedure).
