# Orbit 0.1.261-beta.75

## Summary

**An Orbit Cloud runner can now be moved onto the current image by its owner, and every client says when it is running an older one.** The managed status carries an `update` field (`57666cc129`), and the machine page draws an Update card, a confirmation, an update dot on the machine row and a `Build <sha7> · <date>` line on web (`f9cfeb20e4`, `361bcafe78`), macOS and iOS through OrbitKit (`d0d79680d3`, `38f4cc3eb4`) and Android (`9c419f00f8`), replacing the "Kept up to date by Orbit" note. The card's sentences are the web's `managed*` copy on all three clients, held together by parity tests (`205d06295f`, `702cc14e83`, `baf48ca4e5`). `POST /api/managed-runner/update-now` is owner-only (`033053b42a`): an idle runner drains and wakes at once on the current image; a busy one is refused `409 MANAGED_RUNNER_BUSY` with the running turns and background-job count, unless `interruptTurns: true`, in which case one transaction records the request and a `managed_runner.update_now` activity, the manager asks the backend to stop the instance, and the next generation — made on the same volume and runner with no attempt spent — resumes the cut turn itself (`014313d901`). A turn cut that way is stored as the update's and is handed back opening with the update's note instead of "its runner restarted" (`1e231e35ef`). Docker now rolls an idle runner of a previous image onto the current one exactly as Kubernetes already did (`6d5f4faee1`), and demand no longer calls off an owner's Update Now on either the idle or the interrupt path (`014313d901`).

**A runner made before the `/home/orbit` volume layout no longer comes back on an empty home.** An image before `a944a7f362` keeps home in a `home` folder; a start of today's image now moves that home to the volume root, entries one durable rename at a time under the earlier home's own lock, rewrites the config's and marker's workDir and renames Claude Code's conversation folders to the names `--resume` reads from today's paths, so sign-ins, workspace files and transcripts follow (`20cd2c14bd`). `/var/lib/orbit/home` becomes a link to `/home/orbit`, so paths the earlier home recorded still resolve. A start stopped at any step finishes on the next; a home this image has already run in is kept, with a warning. A runner caught in the other order — restarted onto a newer image before the move landed, so an unused, signed-out home sits at the volume root — has that empty home set aside in one dated `.orbit-empty-home-<ts>` folder (never deleted) and the earlier home recovered, when the root home has no engine sign-in and no workspace folder under a non-hidden root path (`c20687b341`). Real-Docker runs cover both orders (`6c4d3b21f2`, `fe13b15bae`), and the design doc now says the home is moved rather than discarded (`61e41c82f7`).

**A scheduled run that finds a full runner waits instead of being retired after ten minutes.** A run whose session is queued behind a full runner, run tree or batch keeps that one session until its catch-up deadline and is then MISSED as `RUNNER_FULL`; the ten-minute `RUNNER_UNAVAILABLE` limit stays for sessions held by anything else and now counts from the last watch pass that saw the session held (`f4dfb21fc5`). A run whose first turn never reached the engine no longer counts toward the weekly budget, so a MISSED `RUNNER_UNAVAILABLE` run cannot make a later slot read `OVER_BUDGET`, and the refusal message reads the same count (`9764d0e23b`). `GET /sessions/:id/schedule-cards` now carries `runStatus` — every try with its start and whether it reached the engine, this session's try, when the run gave up, the next try, the schedule's next run and the capacity gate holding the current session — and the Scheduled runs folder leaves out ended tries whose first turn never reached the engine (`3bfbf7cbe1`). Web's session page for a run that did not get under way there draws the run card — Didn't run / Queued · runner full / Started on try N, with Run now, Cancel run, Open schedule and Open the run — instead of the error and the composer (`b2f571fb88`, `ab53bc4e88`).

**Android catches up on the two places beta.74 named as lagging.** A session queued behind a GitHub workspace's clone now names the repository and machine and draws git's percentage in both the full-height and the under-transcript card, its row reads "Cloning · N%", and the failed-clone sentence no longer points at the conversation's first line (`1b702bde10`, `c058ed2826`, `84583fc5fb`). The Apple apps hold a card where it was put instead of for a fixed 2.5 s, keep a scrolled-up reader's window through a resync or an exhausted reconnect catch-up, and save a translation folded into a stored reply so a relaunch draws it translated (`3de283eeb2`, `a8e481743a`, `5d8922a4c3`, `3dff985147`, `50f9b6aab1`). `docs/api-reference.md` is regenerated after the merges (`2a1146038f`, `50986f03a7`, `89f39eafff`, `90628d9d51`); the merged tree mounts 495 user routes.

## Upgrade impact

- **Database migrations:** four migration files are added between v0.1.261-beta.74 and this tag, and **all four are additive**:
  - `1210_managed_runner_image_outdated` adds two nullable columns to `managed_runner`, `image_outdated_since` (`TIMESTAMPTZ(3)`) and `current_image_sha` (`TEXT`), so a status read needs no backend.
  - `1290_managed_runner_update_now` adds three nullable columns to `managed_runner`: `update_requested_at`, `update_requested_by` and `update_completed_at`.
  - `1430_schedule_run_capacity_held_at` adds one nullable column to `schedule_run`, `capacity_held_at`.
  - `1431_managed_runner_update_interrupt` adds one `BOOLEAN NOT NULL DEFAULT false` column to `managed_runner`, `update_interrupt_turns` — a catalogue change with a constant default, so no row is rewritten.

  None has an UPDATE, DELETE or backfill; existing rows keep NULL (or `false`), and no other table is altered. The commits call these migrations 1090, 1100/1120 and 1430 in their messages — the files were renumbered as `main` moved, `1090` to `1210` (`73222798fd`), `1120` to `1290` (`d6f0aeb2de`) and the interrupt file from `1430` to `1431` after `main` took 1430 (`cabf8cd3d4`) — and the files in this tag's tree are the four named above. `1210` and `1290` sort below migrations a deployed server has already applied (`1262`…`1431`), so a boot applies them after those, in name order; every statement is a plain `ALTER TABLE … ADD COLUMN`, so the Prisma ledger is what keeps a file from being applied twice.
- **Ordering:** unchanged from beta.74. **Every replica must already run v0.1.261-beta.70 or later before this tag's apiserver boots migrations 1401+.** No commit in this range changes that, and none of the four new files needs a particular order around the rest.
- **Configuration:** no new environment variable or setting is required. The Docker channel now reads the image's `org.opencontainers.image.revision` label and reports it as `imageRevision` in `/v1/info`, and a Kubernetes profile may set an optional `runner.imageRevision`; with neither, the status carries no `update` and no client shows the card. **The managed-runner image must be rebuilt from `deploy/managed-runner/image` at this commit** for the home-move entrypoint and the `/var/lib/orbit/home` link to reach it (`deploy/managed-runner/host.sh` builds it locally, never pushed); Update Now rolls to whatever image the profile names, so a deployment still serving an image built before this tag offers no update.
- **Runner** (`src/runner-go`): unchanged in this range — no file under `src/runner-go` changes between the previous tag and this one. The supply-chain job still builds the runner binaries from this tag, and the runner served at `/dl` is built from this tag; a production deployment is what puts it there, so the runner at `/dl` shows this tag after the next production deploy.
- **Clients:**
  - *macOS:* the Orbit Cloud Update card, its busy confirmation and the row dot, the build version line, and the Apple reader fixes — on the beta channel.
  - *iOS:* the same OrbitKit card and fixes in a TestFlight build; marketing version 0.1.261, build number the commit count.
  - *Android:* the Orbit Cloud Update card, confirmation, row dot and build line, plus the clone progress and card centring, at `versionName` `0.1.261-beta.75` with the next `versionCode` and `android-update.json`.
  - *Web:* the Update card, the scheduled run card and tones, and the shared copy, with the next server/web deployment rather than from this tag's client artifacts.
  - The server-side additions — the status's `update` field, the `update-now` route and `runStatus` on `schedule-cards` — are additive: an older client keeps its existing reads and draws its existing page, and no minimum client version is enforced.
- **One-time step:** a runner on the pre-`/home/orbit` layout moves its home on the first start of an image built at or after this tag, and does nothing on later starts. No operator action beyond rebuilding the managed-runner image is needed.

## Security fixes

None in this release.

## Known limitations

The scheduled run's session card is drawn on web only. The shared copy and the server's `runStatus` exist for every client, but the Android and macOS/iOS apps still draw their previous page for a session whose run did not get under way there; there is no workaround beyond reading that session on web. On Kubernetes, which has no per-instance stop, a busy runner's Update Now waits for idle and the status says so (`update.waitsForIdle`); there is no Kubernetes managed-runner deployment today, so no user meets it.

## Rollback

The previous tag is v0.1.261-beta.74, commit `ec0176958fc7ce3ca5e7b813f373323285232ef1`. An application-only rollback to it is schema-safe: all four migrations in this range only add nullable columns (or one constant-default boolean that rewrites no row), beta.74 writes none of them and reads none of them, and its triggers and functions are the ones it shipped with. Rolling the managed-runner image back is safe for the database, but a runner whose home was already moved to the volume root stays moved: an image before `a944a7f362` looks for `home` in the old place and would come up on an empty home again, as `a4211f22e7` records. Roll the managed-runner image forward rather than back. A release before beta.70 cannot be the rollback target: 1401 refuses its terminal writes.

The client changes do not roll back with the code. Rolling macOS or Android back from this release means installing beta.74's build, which loses the Orbit Cloud Update card and the Android clone progress; an iOS device can also go back to a beta.74 TestFlight build.
