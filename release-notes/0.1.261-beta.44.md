# Orbit 0.1.261-beta.44

## Summary

This release puts the phone's composer footer under one thumb: on a compact-width iPhone the plan usage bar and the context ring become one tap target that opens one sheet, instead of two controls that were each hard to hit. iPad and macOS keep their two gauges with their numbers. On the server, a new coordinator is no longer sent every owner answer an earlier coordinator already read; only answers no coordinator has read still arrive as turns, and the rest reach a successor once, in its opening state digest. And a runner now reads an OpenCode key found in its environment as signed in, and every client words the OpenCode row's unknown sign-in plainly. It adds no database migration.

- **One tap target for the plan usage bar and the context ring (iOS).** On a compact-width iPhone the context gauge now draws the plan bar beside its ring in one button at least 32pt tall (the bar alone was tappable only on its 20x4pt stroke, and the ring is 16pt), and its sheet reads Context, then Plan usage, then the context actions, titled "Context and plan usage" as Android's dialog is. A 0.5pt separator-coloured capsule 26pt tall groups the bar and ring 3pt apart so they read as one control; it carries no fill, which no other footer control has. A gauge without the plan bar is unchanged, and iPad and macOS keep both gauges with their numbers. The sheet's Plan usage group draws one flat row array, as `ListRowShapeTests` requires of every list. Board: `docs/mocks/composer-usage-tap`.
- **A new coordinator is not replayed every owner answer an earlier one read (server).** A new coordinator — opened by a context hand-off, the owner's replace, a workspace switch or a recovery — was sent every answered question whose blocked task was still open, one turn each, even when an earlier coordinator had already read and acted on it (on 2026-11-18 a workspace switch replayed 29 answers; one had reached five coordinators in a row). R11 now delivers only answers no coordinator has read: an answer whose turn has `delivered_at` set is not delivered again. Answers given while nobody coordinated, or queued to a conversation that ended before taking them, still arrive once. What a successor needs of the read ones moves into its opening state digest: a new "Owner answers in force" section (answered in the last 14 days, or still blocking an unfinished task; newest first; size-capped). Every successor now opens with the digest, not only a handoff's; a project's first coordinator is unchanged. A redelivered answer names the tasks it still blocks, and the asker's own message stays byte-identical. Contract revision 40.
- **OpenCode's sign-in reads its environment keys (runner, all clients).** The runner's `opencode auth list` probe returned "unknown" whenever the output contained "0 credentials", which it always does above a key OpenCode found in its environment, so a working env key never read as signed in. It now sums both sections' totals: any key reads as signed in; none is still unknown (OpenCode's free models need no key, and config-file keys are not listed), now reported as `openCodeNoKey`. The machine settings row no longer says "the CLI wouldn't say", which read as if the version were in doubt: it says "sign-in unknown", or "no provider key found" when the runner reports none, on web, macOS/iOS and Android. The new sign-in reading needs a runner from this tag.
- **Also.** `db-write-inventory.ts` gains the line for `skipInFlightLandingCheck`, whose writes the inventory was missing. The rest of the range is test and design material: `blocking-request-replies.pg.spec.ts` (its case (h) rewritten over three generations), a new no-handoff successor case in `coordinator-handoff.pg.spec.ts`, `coordinator-digest.spec.ts`, `PlanUsageSheetTests.swift`, the composer usage boards under `docs/mocks/composer-usage-tap/`, and the hand-off design and integration-line contract documents. No user-facing change comes from those files.

## Upgrade impact

- **Database migrations: none.** The diff of `src/apiserver/prisma/migrations/` between v0.1.261-beta.43 and this release is empty: no migration is added, changed or removed. The newest migrations remain 1070_owner_card_translation and 1080_owner_card_translation_more from v0.1.261-beta.41, both additive (nullable JSONB columns and one new table), which an apiserver already at that tag applied on boot; there is no manual step in this release.
- **Server:** the coordinator answer delivery is an apiserver change (`src/apiserver/src/projects/coordinator-digest.ts`, `coordinator-opening.ts`, `project-open-item.service.ts` and `projects.service.ts`, with its specs), so the apiserver must be deployed from this commit or later for it. The web client ships with the same deploy; its only change is the OpenCode row's "sign-in unknown" / "no provider key found" wording.
- **Runner:** the OpenCode sign-in probe changes (`src/runner-go/doctor.go`), so a runner reads an OpenCode env key as signed in only once it is updated to this tag; an older runner keeps working and keeps reporting such a key as unknown. The runner served at `/dl` is built from this tag. No commit names an engine version change and no minimum runner version is set.
- **Configuration:** no variable, compose file or deploy script changes in this range; nothing must be set before or during the upgrade.
- **Clients:** the composer change is iPhone-only. macOS beta users get the DMG on the beta channel (its only visible change is the OpenCode row's wording), TestFlight gets marketing version 0.1.261 with the build number as the commit count, and Android gets `android-update.json` from this tag (its only visible change is the same OpenCode wording). No minimum native client version above the previous release is set by this range.

## Security fixes

None in this release. No commit in this range names a security fix, an advisory or a CVE, and no dependency is added, removed or moved: the lockfile changes only the package version line.

## Known limitations

None known. The merged composer control appears only on a compact-width iPhone; iPad and macOS keep the two separate gauges with their numbers, by design, not as a limit of this release.

## Rollback

The previous tag is v0.1.261-beta.43, commit 68793f4fd9cf25902522538f6c7d2920209a256b (its tag object is c18d545e68c723e325ffe9b3ca2a4284f8a5d479); the tag is on origin, and when these notes were written its release workflow run (44265072707) was still queued, so it had no GitHub Release assets yet. This range adds no database migration, so an application-only rollback to that tag is schema-safe: nothing is left to undo, no backup or restore step is needed, and no data is affected. Rolling back restores the older behaviour: the iPhone composer returns to the two separate gauges (its plan bar tappable only on its stroke), and a new coordinator of a project is again sent every answered question whose blocked task is still open, one turn each, with no "Owner answers in force" section in its opening digest. Rolling back only the server to beta.43 leaves the merged iOS composer control working, because it is a client-side change against the same API; against a server older than beta.43 nothing on the client side depends on this range.
