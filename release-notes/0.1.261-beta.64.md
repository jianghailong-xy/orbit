# Orbit 0.1.261-beta.64

## Summary

This release carries three user-facing features and the two additive migrations they need. **An agent can now fix the
owner's own Settings instead of describing where the row is**: it proposes the change on a `SETTINGS_CHANGE` card, the
owner saves or declines it, and the Settings row then keeps a grey "Turned on from <conversation> · <time> · Undo" line
(`4603b650cc`, `a9ee2116cf`, `806d286671`, `f4adbdaf66`); web, macOS/iOS and Android all draw the card, the Open in
Settings link and that line (`a6575bd829`, `35b05fdde5`, `5e29938bb3`). **Schedules gained a sub-daily EVERY rule** —
every N minutes inside a window on chosen weekdays — with a planned end that can be an end date or a run count, one
"Stopped as planned after N runs" push, and one faint row for a streak of missed slots (`fc285104ff`, `c066cf584a`,
`79a25b3345`). And **the owner can give every model of a built-in engine its own subagent tier** from Model tiers, on
web, macOS/iOS and Android (`a774c01c5b`, `6f7065ea56`, `e7f934907e`, `84cbe7fedd`). An operator will also notice that
permanently deleting a trashed session no longer fails with "Internal server error" on a loaded database
(`35e80b04b0`).

## Upgrade impact

- **Database migrations: two, both additive.** They apply on boot, as before.
  - `1273_owner_request_settings_change` files the new `SETTINGS_CHANGE` owner-request kind. It adds one nullable
    `owner_request.payload` JSONB column, widens the `owner_request_kind_chk` check to include the new kind, adds a
    check that `payload` is set exactly on those rows, and one partial unique index
    (`owner_request_settings_change_pending_key`) allowing at most one pending card per asking session. No row is
    written, and every existing row passes every check.
  - `1304_schedule_max_runs` adds the planned end by count. It adds two nullable columns with no default
    (`schedule.max_runs` with a `>= 1` check, and the bookkeeping column `planned_end_told_at`), two partial indexes
    (`schedule_planned_end_untold_idx`, `schedule_run_started_idx`), and marks every schedule already ENDED as told so a
    deploy pushes nothing about an end that happened before it. Nothing is dropped or rewritten.
- **Configuration: nothing to fill in.** No new `ORBIT_*` variable is read and no `.env` edit is needed.
- **Runner and agent tools: the runner changes in this range.** `src/runner-go/` gains `settings_get` and
  `settings_propose` and the `orbit settings get|propose` commands, and carrier primer 1.4.4 (`806d286671`);
  `schedule_create`/`schedule_update` gain EVERY rules and `maxRuns` (`9453a5c923`) and now say to propose at once when
  a span and frequency are stated (`7ba21ff538`). **The runner served at `/dl` is built from this tag**, so a runner
  fetched from it has these tools; a runner older than this tag keeps working against this server unchanged.
- **Clients:** macOS beta users get the DMG and Sparkle appcast from this tag on the beta channel; TestFlight gets
  marketing version 0.1.261, with the build number as the commit count; Android gets `versionName` `0.1.261-beta.64`,
  the next `versionCode` and `android-update.json` from this tag. No minimum client version is enforced and no one-time
  step is required on a Mac, iPhone or Android device. An older client still reads an EVERY schedule as weekly: the
  server always writes `time` 00:00 and all seven weekdays so the shipped decoders fall back to weekly
  (`fc285104ff`, `aa55b2f920`).

## Security fixes

None in this release. No commit in this range names a security fix, an advisory or a CVE.

## Known limitations

- **A client older than this release shows an EVERY schedule as weekly.** The rule is written so shipped decoders read
  it as a weekly rule (`fc285104ff`), and the new decoders keep that path tested through a copy of the old one
  (`aa55b2f920`). The workaround is to upgrade the client, which then draws the every line, the planned end and the
  collapsed missed row.
- **On a narrow column the scheduled row's sentence line can still be truncated; the planned end never is.** The end
  moved to its own line under the rule line for that reason (`b25c767fa3`), including the Mac page's own row
  (`b9c5a8ff18`).

## Rollback

The previous tag is v0.1.261-beta.63, commit `136fc0fc5d8d60369b01b611c958ed4edcb96461` (its tag object is
`cca8e18c4219a371ed1c31478344aa370c6273c0`), the `chore(release): prepare 0.1.261-beta.63` commit. A server deployed
from this tag rolls back to that commit; the native clients roll back by installing beta.63's build from its tag.

An application-only rollback to beta.63 is schema-safe: both migrations only add nullable columns, check constraints,
indexes and a kind value, and the beta.63 code neither reads nor writes them (it cannot file a `SETTINGS_CHANGE`, and
its checks still pass over every row). No backup or restore step is needed. One behavior does not roll back with the
code: a schedule that had a `max_runs` set keeps that column, and beta.63's server does not enforce it, so such a
schedule keeps starting runs past its count until a server that reads the column is restored. See
[Release process](../docs/release-process.md#rollback-decision-and-procedure).
