# Orbit 0.1.261-beta.110

## Summary

This release is a small set of fixes over beta.109, with the web spawn card as the one an owner will notice: a `session_create` card in the web transcript now reads the child session as it is now instead of the answer it was born with, so a child that has since been renamed or started shows its current title and run state instead of "New session · pending" for the rest of the conversation. On the runner, a self-update download now gets 300 s instead of 120 s to finish, so it no longer aborts mid-body over a slow link. On Android, the hold that keeps an opened waiting card in place now waits for the card to report where it stands, which stops `WaitingCardHoldShellTest` timing out on CI about one run in four. On Apple, the change is a test only: `ToastHostWiringTests` now expects the fifth `"merge"` result card (a merge that opened a pull request), which had kept OrbitKit red and skipped client.yml's Build OrbitApp step since that card landed.

## Upgrade impact

- **Migrations:** none. No file under `src/apiserver/prisma/migrations/` changes in this range, so there is no migration to name, nothing to backfill and no schema change of any kind. An existing database needs no step.
- **Backfill:** none.
- **Configuration:** none. No setting, environment variable or Compose service changes in this range.
- **Server and web:** the apiserver, the link gateway and the database are unchanged. Only the web bundle changes (the transcript's spawn card), so the web client can be deployed on its own against the beta.109 server; it calls the link-preview machinery a conversation view already provides, not a new route.
- **Runners:** the runner served at `/dl` is built from this tag. The only `src/runner-go` change is the self-update download timeout in `installRelease`, 120 s to 300 s; the binary also reports this release's version. A runner on beta.109 that has no trouble updating needs no action, and one on a slow link can now update where it previously aborted; nothing the control plane accepts from a runner changes.
- **Clients:** web and Android change; Apple's change is test-only and no shipped Apple app behavior differs. The web transcript draws a spawned session by its current title and state; the Android client waits for a card's reported position before holding it. There is no minimum client or runner version and no one-time step on a Mac, iPhone or Android device.

## Security fixes

None in this release. No commit in this range names a security issue or a fix for one.

## Known limitations

- The web spawn card reads the live session only inside a conversation view, where the view's link previews are available. On the shared page or in an export, which have no previews, the card keeps showing the call's answer as before.
- The Android hold waits up to 30 frames for the card's reported position. A card that has still not reported it by then is held anyway, so on a device slower than that it can still be left unheld; the test now names the pending, held and reported focus state when it gives up, so a further timeout names its cause.
- The runner's self-update timeout is one 300 s budget for the whole release body, about 10 MB. It is a longer deadline, not an unbounded one: a link slow enough to need more than 300 s for the body still aborts the update.

## Rollback

The previous tag is v0.1.261-beta.109 (commit `bc438bdb72f5f34b1653924b2b303ae1239e9da8`).

Application-only rollback is **schema-safe**: no migration runs in this range, so a beta.109 server, web and gateway read and write exactly the tables they already knew. No down-migration or backup/restore step is needed, and rolling back any one of the server, web or gateway is independent of the others.

Rolling the web bundle back to beta.109's returns the `session_create` card to the call's answer, so a child renamed after creation reads "New session · pending" for the rest of the conversation again.

Rolling the runner back to beta.109's binary restores the 120 s self-update download timeout, so a self-update over a slow link can abort mid-body again. That is the only runner difference.

Rolling Android back to a beta.109 build returns the waiting-card hold to a single frame after the bring-into-view, so an opened card can be left unheld when it reports its position late. Rolling the Apple clients back changes no shipped behavior: the only Apple change in this range is a test expectation, and both builds ship the same app code.
