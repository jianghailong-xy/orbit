# Orbit 0.1.261-beta.34

## Summary

A two-fix release on top of v0.1.261-beta.33, both in the runner's scan for a secret the owner removed: a turn
ending while a scan runs no longer loses every diff, and the scan itself reads only what is not already published.
Web, macOS/iOS and Android fold the old per-file withheld-diff notices into one row. No server behaviour change
and no migration.

- **A removal scan withholds only the diffs that match.** While a scan ran, a turn ending waited 30 seconds and
  then had every patch withheld, with a warning per file: permanent orange rows for files that held nothing, and
  the session's stored diffs replaced by an empty list. The filter now checks each patch in the order the merge
  guard uses — values the runner holds, then values still pending in a removal scan, then the recorded objects —
  and withholds only the patches that match, with a per-file warning naming the file. A record that cannot be read
  still withholds every patch, now with one summary notice per turn (`secret_patches_withheld`: count, reason, no
  paths).
- **The scan reads only unpublished history, and asks git cheaply.** Temporary `_integrate-*`/`_rebase-scratch-*`
  checkouts have no `orbit-base` ref, so each one's whole reachable history (~215k objects, ~8 GB on a runner with
  357 checkouts) was read, and `git status` refreshed stat-dirty indexes in every checkout. History is now scanned
  excluding objects reachable from origin's remote-tracking refs — already published, as the base exclusion
  assumed — while a scratch checkout's unpublished commits are still scanned. A checkout whose HEAD equals its
  base has no history to scan; its index and working tree are still read every time, and nothing is cached between
  scans. Candidate files come from `diff-files`, `diff --cached` and `ls-files --others` instead of status, which
  does not refresh the index, and up to `min(8, NumCPU)` checkouts are scanned at once. A read-only benchmark over
  one runner's 357 checkouts measured 195.6 s → 18.2 s, under heavy host load.
- **A run of old temporary notices folds into one row.** Web, the OrbitKit transcript shared by macOS and iOS, and
  Android fold consecutive per-file "diff withheld while a removal scan ran" notices within one turn into a single
  row, so transcripts already stored from older runners stop carrying a row per file. Real-match warnings are never
  folded, and the fold does not cross a turn boundary.

## Upgrade impact

- **Database migrations:** none. The diff between v0.1.261-beta.33 and this tag under
  `src/apiserver/prisma/migrations/` is empty.
- **Configuration:** nothing to change.
- **Server:** nothing to redeploy for behaviour; the diff between the two tags contains no apiserver file at all.
- **Runner:** the fix and the faster scan are `src/runner-go`. The runner served at `/dl` comes from the web image
  of a production deploy, so runners get this fix once production is deployed from this tag; until then `/dl`
  keeps serving the runner built from the deployed commit.
- **Clients:** web carries the fold in `src/web/src/components/Transcript.tsx`, macOS and iOS in
  `src/macos/OrbitKit/Sources/OrbitKit/Transcript/TranscriptReducer.swift` (OrbitKit, which the iOS target builds
  from `../macos/OrbitKit`), and Android in
  `src/android/app/src/main/kotlin/io/orbitd/android/reader/TranscriptRows.kt`. Each client builds from this tag:
  macOS beta users, TestFlight (marketing version 0.1.261, build number = commit count) and Android via
  `android-update.json` are offered it.

## Security fixes

None in this release. What a removal scan withholds is unchanged — a patch is withheld when it holds a delivered
value, when a value is still pending in a removal scan, or when it names a recorded blob; only the waiting and the
notice changed.

## Known limitations

- The fold applies only to the two temporary notice texts older runners wrote, within one turn; a real-match
  warning keeps its own row, and the new per-turn summary is already a single row.
- The limitations v0.1.261-beta.33 named still stand, since nothing they touch changed in this release: help is
  web-only on all clients, and Ask runs on Claude only, on a machine whose runner declares `help-ask/v1`.

## Artifacts and verification

The tag is v0.1.261-beta.34, and this file is in the release commit's tree. The release publishes the macOS DMG
and Sparkle appcast (beta channel), an iOS TestFlight build and the Android APK with its `.sha256` and
`android-update.json` on the same GitHub Release, all from this tag. The runner at `/dl` is not built by this run:
it comes from the web image of a production deploy, so this release's runner reaches `/dl` once production is
deployed from this tag.

The full runner suite passed for both commits: 7,521 passed, 0 failed at eac63d12f, which its message records, and
7,518 passed, 0 failed at 37dc2a848, which records no check itself. The web Transcript and copy-language tests
passed (151 tests), and Android's `TranscriptRenderingTest` passed. The OrbitKit (Swift) change was not compiled on
Linux. The 195.6 s → 18.2 s measurement is a read-only benchmark over the 357 checkouts of one runner, under heavy
host load; it does not include the record write. Beyond these, verification rests on release.yml's identity gate
and its macOS, iOS and Android build jobs; no release run is recorded in these commits.

## Rollback

The previous tag is v0.1.261-beta.33, commit 8b8be08e7. This release adds no migration — the diff between the two
tags is runner source and tests, three client transcript files with their tests, and a benchmark — so an
application-only rollback to v0.1.261-beta.33 is schema-safe, and with no server behaviour change there is nothing
server-side to undo. Rolling the deployment back also restores the older runner, since `/dl` serves the runner built
from the deployed commit: the slow scan and the withhold-every-diff behaviour return with it, and rolling the
clients back restores a row per old temporary notice. See
[Release process](../docs/release-process.md#rollback-decision-and-procedure).
