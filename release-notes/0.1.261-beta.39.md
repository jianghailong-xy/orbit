# Orbit 0.1.261-beta.39

## Summary

This release is the server and runner half of condition triggers — work that starts when something outside Orbit
becomes true — and it draws no condition on any screen: web, iOS, macOS and Android have no client UI for conditions
in this release, and their screens are separate, unfinished work. Beside it, a SubAgent a coordinator left running at
handover now keeps its model gateway, and production push stops failing for one APNs environment.

- **Condition triggers (server, runner and agent tools; no client UI).** A scheduled task can now carry a WHEN rule: a
  probe command the owner approves, run by its workspace's runner, whose reading the server holds to a comparison, and
  each crossing starts a run — once, or again every `repeatSeconds` while the comparison keeps holding. A task can
  carry `startWhen`: it starts once, when its condition first fires. The runner declares the capability
  `condition-probe/v1`, reads `conditionProbes` from its heartbeat answer, runs each approved command in its workspace
  directory on its interval (hash checked first, timeout and 64 KiB output bounds, one run per condition, no stdin),
  and sends what it read as `conditionSamples` on its next heartbeat; a failed beat keeps the samples, bounded at 200
  per condition. The runner reports and never decides — the server stores samples, runs the state machine (a crossing
  fires once, `holdSeconds` must hold across samples, re-arm, three failed checks or three silent intervals give
  UNKNOWN, which never fires and restarts the hold), sweeps silence, and opens the `CONDITION_UNKNOWN` Waiting on you
  item with a push (none for `RUNNER_ASLEEP`). The agent tools: `schedule_create` takes `rule {kind: "WHEN", condition}`
  and refuses it without a baseline; `task_create` and each `task_create_batch` item take `startWhen`, required
  baseline, exclusive with `runAt` and `startNow` (its card offers no "Create and start"); `condition_get` reads a
  condition's state, newest samples and events through `GET /runner/conditions/:id`; there is no `condition_create`.
  `orbit task create` gains `--start-when JSON`. Agent Contract 1.11.0 adds the contract's fifth timer, catalogue
  1.9.0, primer 1.4.1.
- **Repeat while a condition holds (server).** A WHEN condition's `repeat_seconds` (WHEN rules only, at least 900 s and
  at least the condition's interval) makes a FIRED condition whose comparison still holds fire again that long after
  its last firing, until it re-arms; a false sample short of the re-arm stops the repeats and restarts the clock from
  the sample that holds again, and UNKNOWN never repeats. Each repeat is a FIRED marked repeat and takes the same fire
  hook — one CONDITION run under the schedule's overlap, budget and start checks — and its run block names the first
  firing and the runs started since. `schedule_create` accepts `repeatSeconds` in the condition, and a change to it
  applies at once as a revision.
- **startWhen and waiting work (server).** A `startWhen` task is held until its condition has fired: the due SQL and
  both ready predicates are vetoed until it has, and a fired run's brief says it was started by a condition and must
  check again. The start that keeps the task ends the condition and clears the pointer, a terminal status ends it by
  trigger, and creating or ending a condition wakes its runner at commit. A condition that has not fired for 30 days
  asks the owner once (`CONDITION_STILL_WAITING`): Keep waiting asks again in 30 days, Stop ends it and leaves the task
  OPEN. A paused or ended schedule ends its condition and resuming brings it back. At most 20 conditions that are not
  ENDED per account, samples kept 30 days and the latest 1000 per condition.
- **An active condition keeps an Orbit Cloud workspace awake (server).** A condition that is not ENDED, on an ACTIVE
  WHEN schedule or on an OPEN startWhen task that has not started, is work its workspace's managed runner holds
  (`ACTIVE_CONDITION`): the manager starts no drain and calls one off while it exists, the instance's acceptance is
  refused, and the sweep wakes a sleeping runner that has one. Paused, held, ended or deleted schedules, started or
  cancelled tasks and ended conditions release it; self-managed runners and the switch off are untouched.
  `RUNNER_ASLEEP` is now only the reason while a woken runner comes up, and a runner that cannot come back by itself
  reads `RUNNER_OFFLINE`. The condition read gains `keepsWorkspaceAwake`, and the server's two create cards carry
  "Keeps this cloud workspace awake while it waits." on an Orbit Cloud workspace.
- **A SubAgent left running by a handover keeps its model gateway (server and runner).** On production, 11-17, a Codex
  SubAgent its coordinator left running when it handed over failed about 13 s later, mid-sleep: the child reaches its
  model through Orbit's gateway on a token bound to the parent session, and the handover completed the parent, so the
  child's next request was answered `401 orbit_gateway_token_invalid`. A session that ended by a completed (or
  completing) coordinator handoff now keeps serving its gateway tokens while one of its SubAgent runs is RUNNING; the
  run's end ends that, and every other end refuses them as before. On the runner side, a FAILED SubAgent's result now
  names the engine's own error even when the model already wrote text, and carries the end of the engine's stderr,
  both logged.
- **Apple push (server).** Production's APNs key is rejected for one environment (`403 BadEnvironmentKeyInToken` on
  each send to the sandbox tokens). The server now takes an optional key per environment
  (`APNS_SANDBOX_KEY`/`_KEY_ID`, `APNS_PRODUCTION_KEY`/`_KEY_ID`) falling back to `APNS_KEY`/`APNS_KEY_ID`, never
  pairs one key's contents with another's id, and after that rejection skips the environment with one warning until
  the API restarts, keeping device registrations.
- **Also.** A startWhen's baseline names no repeat after the repeat columns landed; the runner's agent-tools guide and
  recorded Claude init frame are regenerated for `project_ruling_record`; the API reference lists
  `GET /runner/conditions/:id`; the conditions route, writes, retries and column are in the write and tenant censuses,
  and the trigger census counts 1060's `condition_ended_with_task`. The condition-triggers design doc and its iOS board
  are docs only and not user-facing.

## Upgrade impact

- **Database migrations: four, all additive.** The diff of `src/apiserver/prisma/migrations/` between v0.1.261-beta.38
  and this release adds `1030_conditions`, `1040_schedule_when_rule`, `1050_condition_repeat` and
  `1060_task_start_when` (309 lines, no deletes). `1030_conditions` creates the `condition`, `condition_sample` and
  `condition_event` tables with four new enum types and adds one nullable `owner_request.condition_id` column with no
  default, widening `owner_request_kind_chk` with `CONDITION_UNKNOWN`; `1040_schedule_when_rule` adds the
  `CONDITION` value to `schedule_run_trigger` and two nullable columns with no default (`schedule.envelope_command_hash`,
  `condition.resumed_at`); `1050_condition_repeat` adds two nullable columns with no default, one boolean with a
  constant default and a CHECK; `1060_task_start_when` adds the nullable `task.start_when_condition_id` with a unique
  index and a CHECK, the nullable `condition.keep_waiting_since`, widens the kind check again, and adds the
  `condition_ended_with_task` and `condition_probe_changed` triggers. Every migration states it is backward
  compatible: no stored row is rewritten, and the only CHECKs added are ones every stored row passes.
- **Server:** conditions, the WHEN rule, `startWhen`, the repeat, the workspace keep-awake, the SubAgent gateway fix and
  the APNs fix are apiserver changes, so the apiserver must be deployed from this commit or later. Until then, no
  condition exists or is evaluated, a SubAgent left running at a completed handover still fails at its next model
  request, and a send to an environment Apple rejects still fails. The web client ships with the same deploy; its only
  change in this range is the regenerated agent-tools guide.
- **Runner:** this range changes `src/runner-go` (the condition probe loop and wire types, the condition agent tools,
  and the SubAgent failure detail), and the runner served at `/dl` is built from this tag. A runner must declare
  `condition-probe/v1`, which a runner from this tag or later does, to be handed a condition's probe.
- **Configuration:** four optional variables are added for Apple push — `APNS_SANDBOX_KEY`, `APNS_SANDBOX_KEY_ID`,
  `APNS_PRODUCTION_KEY`, `APNS_PRODUCTION_KEY_ID` — each falling back to `APNS_KEY`/`APNS_KEY_ID`. An environment with
  incomplete credentials is skipped and warned once per API process rather than mixing one key's contents with
  another's id. `docker-compose.yml` passes all four through, empty by default, so no existing deployment must set
  them. No other variable is added.
- **Clients:** no client source change draws conditions in this range. The macOS and Android copy tables gain the one
  envelope-card title `PROBE_COMMAND`, which no condition screen reads yet, and web only regenerates the agent-tools
  guide. macOS beta users get the DMG on the beta channel, TestFlight gets marketing version 0.1.261 with the build
  number as the commit count, and Android gets `android-update.json` from this tag. No minimum native client version
  above the previous release is set by this range.

## Security fixes

None in this release. Nothing in this range fixes a security issue, and no advisory or CVE is named; the SubAgent
gateway and Apple push changes are availability fixes, and the approval and access enforcement are unchanged.

## Known limitations

- **No client draws conditions.** Web, iOS, macOS and Android have no screen for a WHEN rule, `startWhen`, a
  condition's state or its history in this release; those screens are separate, unfinished work. Until they ship, a
  condition can be created only through the agent tools (`schedule_create` with a WHEN rule, `task_create`/batch with
  `startWhen`) and read only through `condition_get` or `GET /runner/conditions/:id`.
- **A probe needs a runner from this tag or later.** A runner that does not declare `condition-probe/v1` is handed no
  probe, so a condition on its workspace reads no samples and its silence counts toward UNKNOWN.
- **Repeat is WHEN-only.** `repeatSeconds` is refused on a `startWhen` condition, and must be at least 900 seconds and
  at least the condition's interval.
- **The workspace keep-awake is for Orbit Cloud.** A managed runner keeps its Orbit Cloud workspace awake while an
  active condition is work it holds; self-managed runners and an account with the switch off are untouched.
- **An Apple push environment can stay off until a restart.** After `403 BadEnvironmentKeyInToken` the server skips
  that environment until the API restarts, and it cannot discover a key's environment restriction before Apple's first
  rejection. Correct the credentials and recreate the API to resume sends; other environments and channels continue,
  and device registrations are preserved.

## Rollback

The previous tag is v0.1.261-beta.38, commit 9b50aff37dd. Every migration in this range is additive — new tables, new
enum values, nullable columns with no default, widened CHECKs and triggers — so an application-only rollback to that
tag is schema-safe: no SQL needs undoing and no data is affected. Rolling back restores the old behaviour: no
condition exists or is evaluated, no schedule or task waits on one, a SubAgent left running at a completed handover
fails at its next model request again, and every APNs send uses the single `APNS_KEY` rule. One caution: a server
older than this release does not read `task.start_when_condition_id`, so a task created with `startWhen` and not yet
started would be read as an ordinary open task and could start before its condition fires; cancel or start such tasks
before rolling back. See [Release process](../docs/release-process.md#rollback-decision-and-procedure).
