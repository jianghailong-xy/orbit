# Orbit 0.1.261-beta.37

## Summary

A runner short of disk now holds a session that has never started, and the clients say why: "Low disk space". A
new runner also keeps 10 GB free by default, where Keep Free used to start Off.

- **The gate.** Keep Free (`runner.min_free_disk_mb`) used to hold only the auto-run sweep's task runs. It now holds a
  session that has never run (`started_at` null) while its workspace's free space is under its runner's floor, whether
  it was started by hand, by a task's Run Now or by a spawn. The session list names the gate as `disk_below_floor`. A
  session that has run takes its next message whatever the disk, so an agent can still be asked to free space; no
  floor or no disk reading holds nothing, as before.
- **A new default.** A newly registered runner starts at 10 GB, the smallest tier the runner page offers. Existing
  runners are untouched: their NULL may be an owner's deliberate Off.
- **The wording.** macOS, iOS (which share the changed OrbitKit and OrbitApp sources) and Android no longer say a
  plain "Queued" for such a session. The list line and header read "Low disk space", and the foot-row tag reads
  "Queued · low disk space", opening to web's sentence and how long it has waited, with no Later or Update Now. Web
  words the same wait, and the runner page's Capacity footer and low-disk line say new sessions wait too.
- Also: four OrbitKit test cases no longer depend on the host's time zone or a quarantine value macOS 27 leaves empty; and
  design docs and boards for an upcoming runner browser (not user-facing).

## Upgrade impact

- **Database migrations:** one, `0990_runner_keep_free_default`. Its SQL is a single
  `ALTER TABLE "runner" ALTER COLUMN "min_free_disk_mb" SET DEFAULT 10240` — additive and non-destructive: it changes
  the default for rows created from now on, rewrites no row, and leaves existing runners' values, NULL included, as
  they are.
- **Server:** the apiserver gate needs a deploy of this commit or later. Until then the claim does not hold a
  never-run session for disk, and no client sees `disk_below_floor`. The web client ships with the same deploy.
- **Runner:** the diff between v0.1.261-beta.36 and this tag carries no `src/runner-go` change. The runner served at
  `/dl` is built from the web image of a production deploy, so runners get runner changes once production is deployed
  from this tag — and this tag has none.
- **Configuration:** none. An operator who wants the 10 GB floor on an existing runner sets it in the runner page; a
  managed runner is still created with NULL on purpose, its floor defaulting to a share of its volume.
- **Clients:** macOS beta users, TestFlight (marketing version 0.1.261, build number = commit count) and Android via
  `android-update.json` from this tag.

## Security fixes

None in this release.

## Known limitations

- The migration does not backfill existing runners, so a runner registered before this release keeps whatever floor it
  had — Off if it was never set.
- A session that has already run is not held for disk: it takes its next message even below the floor. That is by
  design, so an agent can be asked to free space.
- The held session's wording is on macOS, iOS, Android and web; it does not change how long the wait is, which is still
  until free space reaches the floor.

## Artifacts and verification

The tag is v0.1.261-beta.37, and this file is in the release commit's tree. The release publishes the macOS DMG and

OrbitKit; no commit message in this range records a run result for the PostgreSQL spec, web or Android tests. The
full OrbitKit suite ran at commit 2a4f92b2c, which includes the disk-gate commits, on a macOS 27.2 Mac (Xcode 27):
5,532 tests, 0 failures, `QueuedDiskLowTests` among them.

## Rollback

The previous tag is v0.1.261-beta.36, commit 123ef213d5. Migration 0990 changes only a column default, so an
application-only rollback to v0.1.261-beta.36 is schema-safe. Rolling back restores the old behaviour: a session that
has never run starts on a runner below its floor, and new runners start with Keep Free off. See
[Release process](../docs/release-process.md#rollback-decision-and-procedure).
