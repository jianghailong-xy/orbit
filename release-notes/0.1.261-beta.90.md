# Orbit 0.1.261-beta.90

## Summary

- **Orbit Files is now Documents.** The + menu reads File / Image / Documents on web, iOS, macOS and Android; on web and macOS the sidebar, the page heading, the root folder names, the storage page and the token scope group say Documents. Web's page is at `/documents`, and `/files`, `/files/trash` and `/files/storage/...` redirect there with the query string kept.

- **The drive is mounted at `~/Documents` on hosted runners, and old `~/Files` paths still resolve.** `driveHomePath` and the mount's display root move to `/home/orbit/Documents`; `driveMountRelative` and the Plan-mode drive roots keep accepting `~/Files` and `/home/orbit/Files`.

- **The API and the token scope say documents; the old names are still answered.** The server serves `/documents` and keeps `/drive` as an alias for bundles and runners already deployed. The token scope is `documents`, and `files` is still read as `documents` on a stored token and on a request to mint one, so no existing token loses access; the web and macOS token dialogs ask for the new name. The runner's door is `/runner/documents`, with `/runner/drive` kept.

- **Agent tools are documents_*, and the drive_* names are still served unlisted.** `tools/list` names documents_put/get/list/move/delete and the CLI is `orbit documents put|get|ls|mv|rm`; a runner links a file as `orbit-document:<id>`. `drive_*` calls (and `ORBIT_MCP_TOOLS` lists naming them) and `orbit drive` are still served, unlisted, and `orbit-drive:` links in stored transcripts still draw the same file and transfer cards. A check-only schedule run denies the Documents tools under the names Claude now sees (`mcp__orbit__documents_*`), and a FILE citation of an `orbit-document:` link is refused as a drive file and pointed at `file_upload`, as `orbit-drive:` already was. Agent-facing instructions, tool descriptions, CLI help and the evidence error say Documents.

- **The hosted-runner CSI driver is `documents.orbit.dev`, mounted at `/run/orbit-documents`.** The manager builds runner Pods with the new driver; the mount daemon is now `orbit-documents-mount` (`src/documents-mount`) and the manifests are `documents-csi`. Until Pods from before the rename drain, admission also admits `files.orbit.dev` only at `/run/orbit-files`, and the runner finds the drive under whichever root its Pod has, counting either FUSE type as the drive.

- **Settings are `ORBIT_DOCUMENTS_*`, and the old `ORBIT_FILES_*` names are still read.** The apiserver, `docker-compose.yml` and the backup sidecar read each `ORBIT_DOCUMENTS_*` setting and fall back to its `ORBIT_FILES_*` name when the new one is unset or blank, so a host `.env` written before the rename keeps working; the mount daemon still reads `ORBIT_FILES_MOUNT_TOKEN` when `ORBIT_DOCUMENTS_MOUNT_TOKEN` is unset.

- **Apple (iPhone and Mac) gets the Landing section and pull request landing states web already has.** A port of web's workspace Landing section (Pull request default, Push as me faster, permissions and refusal notices as the board's amber box, in light and dark) and of the pull request card, decoded from the server's own read models; the Faster tip hides on Push as me; an attempt held on its pull request reads waiting for GitHub in the landing row and job list instead of queued; and the card holds its place while the workspace read runs.

- **Android gets the same Landing section and pull request card.** The workspace Landing setting, the pull request card on the project landing card, the task's Landing section and the Landings window; an attempt held on its pull request reads Waiting for GitHub instead of stopped, a failed GitHub check is named, and the project line says waiting for GitHub; the tip's Landing settings link opens the workspace page scrolled to its Landing section.

- **Server and runner.** The drive module, controllers, services and DTOs are `Documents*`; routes are `/documents` and `/runner/documents` with their `/drive` aliases; the Prisma models and the ten drive tables are `document_*`. Agent Contract 1.13.0, operation catalogue 1.11.0 and primer 1.4.6; the snapshots, operation catalogue, agent tools guide (web, macOS) and playbooks are regenerated for them.

## Upgrade impact

- **Migrations:** two, applied in order on the first boot.
  1. `1550_pat_scope_documents` — a **data update**: every stored personal access token and pending device login holding `files` now holds `documents` in its place, so a token keeps exactly the grant it had under the new name; a row already holding `documents` only loses the old name, so no scope appears twice. No row is added or removed, and no table, column, trigger or function is touched. It runs twice safely.
  2. `1551_documents_tables` — **not additive**: it renames the ten drive tables (`drive_staging`, `drive_staging_chunk`, `drive_version_chunk`, `drive_trash_group`, `drive_entry`, `drive_version`, `drive_commit`, `drive_removed_entry`, `drive_change`, `drive_mount_credential`) and every constraint, index and sequence on them whose name begins `drive_` to the same name beginning `document_`. It is catalog renaming only — every row, column, value, default and reference is unchanged — and it creates nothing. Because the old names disappear, **a deploy must stop the old apiserver before starting the new one**: an older apiserver still running finds no `drive_*` table and answers its drive requests with an error until it is replaced, and nothing it fails to write is lost, since uploads, mounts and tools retry their commit. It takes its locks in 1 s tries, up to 40, so a waiting rename does not queue every later reader, and it runs twice safely.
- **Kept names:** `file_blob` and `src/apiserver/src/files` are the generic attachment store, not the drive, and keep their names; `share_link`'s `drive_entry_id` and `drive_version_id` columns and its `share_link_drive_*` constraints keep theirs. `1551` does not add the `document_commit` owner foreign key that `schema.prisma` declares and migration 1327 never made — that is the same drift as before, left for a separate change after a production count of orphan rows.
- **Configuration:** no change is required. New `ORBIT_DOCUMENTS_*` names (`BACKEND`, `DIR`, `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION`, `QUOTA_BYTES`, `STORE_QUOTA_BYTES`, and the mount daemon's `MOUNT_TOKEN`), with each old `ORBIT_FILES_*` name read when the new one is unset or blank. Moving to the new names at leisure is enough; nothing breaks if you do not.
- **Server:** the first boot applies both migrations. The one operational rule is the 1551 one above — stop the old apiserver before starting the new one; no old and new apiserver can serve the same database across it. There is no backfill beyond 1550's scope rewrite.
- **Runners:** the runner served at `/dl` is built from this tag and carries the renamed tools and CLI, keeps `drive_*` and `orbit drive` as hidden aliases, calls `/runner/documents`, and finds the drive under `/run/orbit-documents` or, in a Pod from before the rename, `/run/orbit-files`. Orbit Cloud runners get it from the `orbit-cloud-runner:0.1.261-beta.90` image, built from this tag. The `documents.orbit.dev` CSI plugin is installed on the cluster separately, beside the old one (deploy/managed-runner/documents-csi/README.md). An older runner keeps working: `drive_*` calls, `orbit drive`, `/runner/drive` and `orbit-drive:` links are still served.
- **Managed runners:** the manager builds new Pods with `documents.orbit.dev`; the admission guard also admits `files.orbit.dev` at `/run/orbit-files` until the old Pods drain. The driver's README says how to run the new one beside the old, drain, then remove the old driver and its namespace.
- **Clients:** web arrives with the deploy of this commit; macOS (beta channel DMG), iOS (TestFlight) and Android (APK) come from this tag. An older web bundle keeps calling `/drive` and drawing `orbit-drive:` cards, which the server and the new web still answer and draw, and it shows the old labels. The Apple and Android Landing section and pull request landing states need this release's builds; web had them already. No one-time step on a Mac, iPhone or Android device.

## Security fixes

None in this release. One property of the rename is worth naming, since a scope changes name: migration 1550 gives every stored token exactly the grant it had under the new name, the old `files` name is still read as `documents` wherever a scope arrives, and a token is always minted and shown under the current name — so no existing token loses access and none gains a scope it did not hold.

## Known limitations

- The old names are deliberately still read during the transition: the `/drive` and `/runner/drive` routes, `drive_*` tools, `orbit drive`, `orbit-drive:` links, `files.orbit.dev` and `/run/orbit-files` in Pods from before the rename, and the `ORBIT_FILES_*` settings. Remove the old CSI driver only after the old Pods have drained.
- The `document_commit` owner foreign key that `schema.prisma` declares and 1327 never created is still missing, so `prisma migrate diff` reports the same drift on these tables as it did before this release.
- An older apiserver cannot run beside this one once 1551 has applied: it answers drive requests with an error until it is replaced, so the deploy must stop it first.

## Rollback

Previous tag v0.1.261-beta.89 (`29584a463c`). Application-only rollback is **not** schema-safe: 1551 renamed the ten `drive_*` tables and 1550 rewrote stored token scopes, and the previous release reads `drive_*` table names and knows only the `files` scope. Prisma's startup migration does not undo applied migrations, so restore the pre-upgrade off-host database backup (docs/postgres-backup-restore.md) and then deploy the previous tag. Orbit Cloud runners are pointed back at the previous tag's image by a deploy of an earlier commit, and each moves to it once idle.

Client rollback is to the last published builds, v0.1.261-beta.89's DMG, TestFlight build and `orbit-android-0.1.261-beta.89.apk`.
