# Orbit 0.1.261-beta.82

## Summary

**A runner now reclaims resting session checkouts by one rule under every free-space floor, and a roomy disk keeps at most 64 of them.** `27a11c3c58` fixes a sweep that had left almost every resting checkout in place: on the HPC runner on 2026-11-23, 378 checkouts held 471 GiB of a 915 GiB disk, and in the week before only 10 resting checkouts went. A runner without a storage budget asked that nothing in a checkout be written for two weeks and that every commit be on a remote; because the runner pushes no session branch, 223 clean checkouts (250 GiB) and 99 with branch-only commits (126 GiB) could never go. Under a machine's floor those two rules now stay set aside, and above it the sweep reclaims the least recently used resting checkouts once more than 64 are on disk, as it already did for finished sessions beyond 32. Nothing that exists nowhere else goes: a checkout is taken only when its work is on its branch, and it comes back from that branch on the session's next claim.

No client reaches users with a change of its own in this release. Besides the runner, two commits after the release commit ship in no build: `e7220b01eb` makes the two-stage deploy write `runner.imageRevision` together with `runner.image` (Kubernetes shows Update Now only when the profile names the image's source commit), and `fc9f263c84` corrects a contract test fixture. v0.1.261-beta.81 published in full; it is the previous installable release.

## Upgrade impact

- **Database migrations:** none. No file is added under `src/apiserver/prisma/migrations/` between v0.1.261-beta.81 and this tag, so the upgrade applies no schema change; the rest of the schema is as v0.1.261-beta.81 left it.
- **Configuration:** none. No environment variable, setting or runner declaration changes. Keep Free and a storage budget keep their existing meanings; the difference is only which resting checkouts are eligible once the sweep runs.
- **Runner** (`src/runner-go`): changed. A resting session's checkout is now reclaimed, oldest first, with no idle wait to serve and with a commit on the session's own branch counting as kept, since the branch and its commits stay in the repository and the checkout comes back from the branch (`git rev-list HEAD --not --remotes <branch>` empty). That rule applies under every floor, not only under a storage budget; above the floor it runs only while more than 64 resting checkouts are on disk, and the existing cap of 32 finished checkouts is unchanged. "Oldest" is the newer of the checkout directory's modification time and its `HEAD` reflog's, which costs two stats, and the sweep walks a checkout only when it is about to take it. Reclaim logs name the reason: under the storage budget's floor, under the free-space floor, or over the cap of 64. The supply-chain job builds the runner binaries from this tag, and **the runner served at `/dl` is built from this tag**; a production deployment is what puts it there, so the runner at `/dl` shows this tag after the next production deploy.
- **Engines:** unchanged. No commit in this range changes an engine version, and the managed-runner image is not published by this tag.
- **Clients:** no client source changes in this range, so no user-facing client change ships. The tag still publishes the macOS beta-channel DMG, an iOS TestFlight build (marketing version 0.1.261, build number the commit count) and a signed Android APK (`versionName` `0.1.261-beta.82`, the next `versionCode`, plus `android-update.json`), and each carries the same code as v0.1.261-beta.81's build. Web and the app server are unchanged and reach users with whatever deployment runs them.
- **One-time step:** none. An operator should expect the checkouts of resting sessions to be reclaimed sooner than before, including on a disk with free space to spare: resuming such a session re-creates its checkout from its branch and reinstalls dependencies and rebuilds output, while every commit stays on the branch. A checkout holding an ignored file that cannot be made again — a local `.env`, a report — is still kept, however old it is.

## Security fixes

None in this release.

## Known limitations

- The cap is enforced by a sweep on the claim loop, which runs every five minutes and never while a message is being claimed, so a burst of new checkouts can still take a volume past its free-space floor before a sweep catches up, and writes then fail with "no space left on device" (`27a11c3c58`).
- Whether a checkout is in use is read from `/proc`, so on macOS and Windows a resting session's checkout is never reclaimed.
- A resting checkout is kept by any ignored file that cannot be made again from its name — anything outside the listed dependency and build-output directories, such as a local `.env` or a saved report — so such a checkout still holds its disk however old it is.

## Rollback

The immediately previous tag is v0.1.261-beta.81, commit `a202b5c9d629074dcd9fb26747b32e2d8a245c1c`, and no migration lies between it and this tag, so an application-only rollback is schema-safe: there is nothing to restore and no table to reverse. Rolling a runner back is safe as well — an older runner returns to asking for two weeks unwritten and a remote for every commit, which reclaims less rather than more, and any checkout this release reclaimed comes back from its branch on the session's next claim.

No client source changed in this range, so this tag's macOS, iOS and Android builds differ from v0.1.261-beta.81's only in the build number; rolling a client back means installing v0.1.261-beta.81's build. v0.1.261-beta.81's release run published every artifact, and this range adds no migration of its own.
