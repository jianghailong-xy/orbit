# Orbit 0.1.261-beta.42

## Summary

This release is the conditions pass: a schedule or a task that waits for a condition is drawn on the Scheduled page, in its inspector, on the create cards, in a run's header and in Waiting on you on web, iOS and Android, and the Mac's timeline shows each condition row's newest reading, with a condition that cannot be read going under Needs you. It also lets the owner land a landing that is still queued or running without its landing check, lets a runner commit beside a live background job instead of refusing it, retries a translator that is unreachable or answers 429/5xx, holds auto-run tasks whose engine is signed out instead of dispatching them every minute, and replaces the web control plane's hand-kept key-prefix whitelists with each cached read's declared entities, so the project page's own reads re-read when a task event arrives. It adds no database migration.

- **Conditions on the Scheduled page and in Waiting on you (web, iOS and Android).** A Scheduled page gains a "Waiting for a condition" group above Today holding WHEN schedules and startWhen tasks, each with a gauge and its newest reading and age in place of a timed row's circle and time, and a condition that cannot be read under Needs you as Can't read. Waiting on you draws the can't-read card (Pause, Look into it) and the 30-day question (Keep waiting, Stop), and a startWhen task shows its waiting line. iOS is the board's reference client (`docs/mocks/condition-triggers` frames 2 to 6) and Android ports its surfaces; the Mac's Scheduled timeline draws a condition's newest reading and age ("6.9% · 1 min ago") where a timed row shows its time, and the title's count and the empty state count the tasks waiting on their startWhen.
- **A condition's inspector, cards and a run's header (web, iOS and Android).** A WHEN schedule's inspector shows Condition (reading, gauge bar, firing and re-arm lines, the rule in words, the repeat) and How it checks (interval, runner, command, approval, keeps-awake), and Fired / Fired again / Ready again lines in the history with each firing folded with the run it started. The schedule create card draws the When lines and the command; the task create card draws Starts when, Today and If never; the widen card shows a changed probe command verbatim; and a run its condition started names the firing in its header ("Fired 03:12 · 90.4% for 10 min").
- **The server reads those surfaces need (server).** `GET /schedules` lists the OPEN tasks waiting on their startWhen (`waitingTasks`), `GET /conditions/:id` names its runner (`runnerName`), and an owner request carries its `conditionId`; a CONDITION_UNKNOWN item's owner read carries that `conditionId` too. The web client reads all three as optional fields, so a client from this tag talking to an older server draws no waiting group rather than failing.
- **Apple condition detail.** The iPhone composes a condition's lines in the web's words, OrbitKit's `ScheduleRule.when` lets a WHEN schedule decode instead of failing, the task create card's "Create task that starts on a condition?" wraps to two lines and gives up the "new task" badge it says already while the Starts when, Today and If never labels get a column wide enough for "Starts when", and the condition row's gauge takes a font token, not a bare system size.
- **The owner can land an in-flight landing without its landing check (web and server).** The owner's skip-merge-check door now also takes a landing that is still queued or running: it stops that generation through the shared J-T8 stop and lands the next one with the landing check not run, recorded as skipped by the owner. A queued or timed-out generation is replaced on the spot; a live claim is asked to stop, and the result transaction queues the unchecked generation once the runner answers, unless it landed. It is refused past the push boundary, when a stop was already asked, when the generation already skips the check, and when the project has no landing check. `inFlightJobs` carries `skippable` (the same rule as the door) and `skipCheck` (STOPPING / SKIPPED); the web landing card offers "Land without the check" behind a confirm step and says where a skip stands in place of "Nothing to do". Contract revision 39.
- **A commit runs beside a live background job (runner).** A background job is a test run, a build, a dev server or a wait on CI, not an edit of the session's work, yet since d7352a3d46 a commit or discard was refused for as long as one ran in the checkout, so a long test suite held the owner's Commit button hostage. A commit runs beside the job again and its receipt names the jobs it ran beside; a turn in the checkout still refuses it.
- **A task filed to fix an open MAIN_SYNC conflict can land (server).** M2 held every later landing on a repository-and-ref while a MAIN_SYNC INTEGRATION_CONFLICT item was open, exempting only the conflicted task's own landings, so a separate fix task (`fixesOpenItemId` = the item, `task_create`'s documented route) waited behind the item it was filed to close and the lane deadlocked. The claim now also passes over that item for a landing whose task has `fixes_open_item_id` = the item, while a fix for any other item and every other landing stay held; the two readers mirror the claim, and the fix's landing hands the item back to the coordinator (X-D4 (5)) rather than closing it. The pg spec `project-exception-todos` reproduces the deadlock on the old claim and walks the fix landing, a repeated conflict, the hand-back and the release.
- **Push no longer stops to ask (web, macOS and Android).** Pushing a project's branch from the review drawer no longer raises a confirmation dialog; the managed-branch line still says the push skips the project's landing check.
- **A translator that is unreachable or answers 429/5xx is retried (server).** `translate()` tries a transient failure up to three times in all, pausing 0.5 s and 1.5 s, inside the same 20 s bound its callers wait on; a 4xx, a truncated, empty or mangled reply is still final.
- **Auto-run tasks on a signed-out engine are held, not dispatched (server).** The auto-run sweep offered a ready task on a runner reporting its engine signed out to dispatch every minute and `sessions.create` refused it with `EngineSignedOutConflict`, logging one warning per task per pass — 308 in 2.5 hours on production for two tasks on one Mac. A signed-out gate now judges each task the way the preflight does and holds those tasks beside the disk and clone holds, counted and not dispatched, with one aggregate line per sweep naming runner and engine; it lifts on the sweep after a heartbeat reports the engine signed in.
- **Web views are refreshed by the entities they declare (web).** Every query options object under `src/web/src` now declares `meta.entities`, and the control plane marks stale every cached read that declares an entity an event names, in one linear scan per coalescing window, replacing the two hand-kept key-prefix whitelists and `isProjectPageRead`. The project page's task tree, its children and the project detail were on neither list and poll nothing, so a task the Automatic dispatcher started stayed `ready` on screen until a manual reload; they are reached now. The guest page is left to its own stream, so a session event no longer re-reads it and draws its events twice, and the cost exclusions the whitelists bounded stay declared.
- **Also.** The failed-translation sketch (decision B) and the condition-triggers evidence boards and probe kits for the iPhone, the Mac and Android are docs and test material only and not user-facing. The rest of the range is tests: the managed-runner volume switch spec stops the background passes its `useValue` provider started, a pg spec leaves 1070's `project_open_item.translation` out of 0453's frontier compare, and the web control-plane changes arrive with the specs above.

## Upgrade impact

- **Database migrations: none.** The diff of `src/apiserver/prisma/migrations/` between v0.1.261-beta.41 and this release is empty: no migration is added, changed or removed. The newest migrations remain 1070_owner_card_translation and 1080_owner_card_translation_more from v0.1.261-beta.41, both additive (nullable JSONB columns and one new table), which an apiserver already at that tag applied on boot; there is no manual step in this release.
- **Server:** the condition reads, the landing-skip door and the auto-run signed-out hold are apiserver changes, so the apiserver must be deployed from this commit or later for them. The web client ships with the same deploy.
- **Runner:** this range changes `src/runner-go` — a commit or discard is admitted beside a live background job and its receipt names the jobs, and `docs/operation-catalog.md` is regenerated to match (content hash `171cbcea63edce02cc55ff09bfd5b1cd514bde63717d467abc30abf424dc9034`). The runner served at `/dl` is built from this tag. No commit names an engine version change, and no minimum runner version is set: a runner from an earlier tag keeps working and does not carry the commit-beside-a-job change until it is upgraded.
- **Configuration:** no variable, compose file or deploy script changes in this range; nothing must be set before or during the upgrade.
- **Clients:** macOS beta users get the DMG on the beta channel, TestFlight gets marketing version 0.1.261 with the build number as the commit count, and Android gets `android-update.json` from this tag. A client from this tag talking to a server older than this commit draws the condition surfaces' optional fields as absent — no waiting group, no `runnerName`, no `conditionId` — and no minimum native client version above the previous release is set by this range.

## Security fixes

None in this release. No commit in this range names a security fix, an advisory or a CVE, and no dependency is added, removed or moved.

## Known limitations

None known. A condition that cannot be read is surfaced under Needs you rather than guessed at, and the failed-translation sketch in this range is a design document only: nothing in it ships in this release.

## Rollback

The previous tag is v0.1.261-beta.41, commit c4e87955f018bcefc70dc19cf3cf7da0a6313a27 (its tag object is 001797c6b209b54ee9b9907d0eefaed48e2132bd), which is published. This range adds no database migration, so an application-only rollback to that tag is schema-safe: nothing is left to undo, no backup or restore step is needed, and no data is affected. Rolling back restores the older behaviour: the condition surfaces disappear from Scheduled, Waiting on you, the inspector and the run headers, the owner cannot skip the check on a landing that is still queued or running, a commit is refused again while a background job runs in the checkout, a fix task filed for an open MAIN_SYNC item waits behind that item again, pushing a project's branch asks for confirmation again, the translator's transient failures are final again, auto-run tasks on a signed-out engine are dispatched and refused every minute again, and the project page's task tree and detail wait for a reload. Clients from this tag would then talk to an older server, which serves none of the condition fields; the web client reads them as optional, so those surfaces draw as before. See [Release process](../docs/release-process.md#rollback-decision-and-procedure).
