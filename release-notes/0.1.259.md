# Orbit 0.1.259

## Summary

Everything in [0.1.258](0.1.258.md), plus three small changes. When an agent's reply links a file the runner
will not attach, because it is outside the session's working directory and uploads directory, the reply now
ends with one line naming the file and saying why it cannot be opened, instead of showing a broken image with
no explanation. On the machine page, Max Concurrent reads as a meter ("3 of 16 running" with a bar) and its
limit changes from an Edit dialog, on web, macOS/iOS and Android. In the web app, keyboard focus on project
and session list rows shows as the hover tint instead of a blue ring.

## Upgrade impact

- **Runners update themselves.** `0.1.259` orders above `0.1.258`, so runners self-update from `/dl` as
  usual (a busy runner waits until it is idle). The note on unattached files is added by the runner, so it
  appears only in replies written after a runner has updated; earlier replies are unchanged.
- **No database migrations** beyond those listed in the [0.1.258 notes](0.1.258.md).
- **Deployment.** No configuration changes are required. The 0.1.258 deployment notes apply unchanged.
- **Clients.** No tag is cut for this version yet, so no new macOS, iOS or Android build ships with it; the
  native Max Concurrent change reaches them with the next client release.

## Security fixes

None in this release.

## Known limitations

- The note covers only links refused for being outside the session's directories. A file inside them whose
  upload fails is still left as written with no note.
- Main's CI was red when this version was cut (`Swift core / Test OrbitKit` and
  `JavaScript / Test what install and upgrade do for the runner link`); the release went ahead at the
  owner's request without those being investigated.
- The known limitations of [0.1.258](0.1.258.md) still apply.

## Artifacts and verification

The version of record is `package.json` `0.1.259`; `/dl/version.json` names it once the server built from
this commit runs. The reply-file note was checked at its commit: its unit test passes and fails against the
previous `reply_attachments.go`, and the full runner Go suite passed apart from one timing test in
unrelated code (`TestV2ProgressReportsInsideEveryWindowForALongCheck`, 209 ms against a 200 ms window
under load), which passed three times on its own.

## Rollback

Roll back to 0.1.258 (or, if that was never served, to the release production ran before it). No schema
change is involved, so an application-only rollback is safe. Runners do not move back by themselves: roll
them back with the `/api/runner/release` pointer. See
[Release process](../docs/release-process.md#rollback-decision-and-procedure).
