# Orbit 0.1.261-beta.46

## Summary

This release is about a red landing saying whether it is the task's fault. A project on a project branch can now set its landing check — a command and timeout, blank inheriting the merge check's — when it is started and in its run settings on web, macOS/iOS and Android, behind a confirmation card headed "Change project integration settings?". A landing check that fails is now re-run by the runner on the project branch with the latest main and without the task's work, and the result is recorded with the exact tree it measured; when that baseline also fails, the job is marked baseline-red and landings on that branch are held behind one shared open item — "Baseline checks failing on <branch>" — that lists the held tasks, the upstream, project tip and combined baseline SHAs and the command, and landings resume when it is resolved. Scheduled runs on Claude Code now run in Auto rather than the access level's mode, and every workspace's session list gains a built-in "Scheduled runs" folder that holds its runs' sessions. A session can now be moved to another workspace or filed in a folder from inside a session, through `orbit session move` and the `session_move` MCP tool. Android's session list no longer stalls on ObjectId comparisons, two translation fixes reach the clients that draw them, and the managed-runner and apiserver images carry Codex 0.170.0 and Antigravity CLI 1.5.11. It adds two database migrations (0518 and 1101), both catalog-only CHECK changes on `project_integration_job_event`.

- **The landing check is set where a project is started and in its run settings (web, macOS/iOS, Android).** The server already carried `landingCheckCommand` and `landingCheckTimeoutSeconds`; the clients now read and write them. On a project-branch line, the Start project card and the project run settings draw a Landing check row — Command and Timeout (seconds) — with the copy "Runs when a task lands on the project branch.", the placeholders "Leave blank to use merge check" and "Leave blank to use merge check timeout", and the inherited command and timeout named under each box ("Uses merge check: …", "Uses merge check timeout: … seconds"). On a main line the row reads "Not used when tasks land directly on main." The same copy table (`LANDING_CHECK_COPY` on web, `LandingCheckCopy` on macOS/iOS and Android) draws it on all three clients. A proposal to change these settings is confirmed on a card headed "Change project integration settings?" that shows, for the landing and merge layers, the command and timeout now and after, with "Confirm" (web, macOS/iOS, Android), and "Applies to the next claimed landing job." The web's project run settings also refuse a landing-check timeout that is not a whole number above zero, and a blank box means the merge check's.
- **A red landing check is attributed to the branch or the task (runner, server).** When a landing check fails and the task had work to land, the runner re-runs the same command on a baseline tree — the project branch with the latest main, without this task — records the result with scope BASELINE, and now records the exact tree it measured (`treeSha`) before the check ran (823d856948). If the baseline also fails, the job's result is `baselineRed`. The relay accepts a report from a runner that does not send the tree (91ac85a954) and preserves the check's scope and its timeline copy (fd88dcf63a), so the timeline says "Checked the project branch with main, without this task · passes" or "· also fails".
- **A red baseline holds landings behind one shared item (server, web, macOS/iOS, Android).** A baseline-red failure opens one `INTEGRATION_CHECK_FAILED` item per serial key, deduplicated by the reported upstream and target SHAs (`ICB:`), and each further failure appends its task to the item's `heldTaskIds` instead of opening a card of its own. The next landing generation on that serial key is queued with cause `BASELINE_HELD` and blocks as `WAITING_BASELINE`, naming the item; the card's title is "Baseline checks failing on <branch>" and it draws "The project branch with the latest main fails its checks without this task.", the held count ("Landings on hold"), Upstream, Project tip and Combined baseline SHAs, the check command and "View held tasks" (a link per held task), with "Landings resume automatically when this open item is resolved." (web, macOS/iOS, Android). The item stays owed until resolved (`openItemOwed`), a plain landing does not resolve it, and a task filed to fix it lands the item as LANDED once its fix lands on the failed job's serial key. The task landing status reads "Waiting for baseline fix" with the resume line.
- **Scheduled runs run in Auto and get a Scheduled runs folder (server, web, macOS/iOS, Android).** Every scheduled run on Claude Code is claimed in Auto whatever its access level, and so are the SubAgents it starts, local or remote — a SubAgent used to take the session's stored mode (Accept Edits or Default) and waited two hours on an unanswered approval. The level's deny lists still apply in Auto, a check-only run's denials are refused by the server rather than asked, and a model with no Auto runs as Default; other engines keep the level's mode, since their Auto has no classifier. A run's session now opens in Auto in its mode picker (it showed the level's Accept Edits or Default). Each workspace's session list gains a built-in "Scheduled runs" folder row at the top, shown while the view has a run of that workspace, with its count, needs-you count and a running dot, polled every 30 s; its page lists `GET /sessions?scheduled=1` in the view it was opened from and keeps only rows whose `runSource` is SCHEDULE. Every other list still leaves runs out. A run's session opens as an ordinary session page: the web drops the "Scheduled › … › run of …" crumb, the run's own header line and the hidden Follow chip, the drawer lights the run's workspace, and the contract drops "this session is not in your session list".
- **Move a session from inside a session (server, CLI, MCP).** The Move panel's REST route existed but nothing on a runner reached it. `POST /runner/sessions/:id/move` now runs the same `SessionsService.move`, guarded like end and complete (orchestration credential, no service token, and the permission-mode reach table with a new `move` act); only an ended session changes workspace, and a refusal is the service's 409 and reason. `orbit session move SESSION_ID [--workspace-id ID] [--folder-id ID | --no-folder]` reaches it in a session's shell and `POST /api/sessions/:id/move` as the owner; a bare call is refused rather than silently unfiling, and `folderId: null` on the `session_move` MCP tool means out of any folder. The tool is on the check-only deny list, and the agent-tools guide, operation catalogue and API reference are regenerated.
- **An answered question keeps the language its card was shown in (server, web, iOS, macOS).** The pending AskUserQuestion card draws the server's translation, but once answered the transcript redrew it from the engine's English input. The translation is stored on the Approval row, so the approvals list now takes a `toolName` filter and web, iOS and macOS read the session's question cards — keeping live cards' translations as they pass — to draw the answered record, folded and open, in the owner's language. The answer is still read off the English result, so picks keep their index. The API reference gains that query row.
- **A reply already in the owner's language is drawn once (web, iOS/macOS, Android).** When the translator hands back the reply itself, the clients drop the translation and draw the reply as it is: no "Translated · Hide original" foot, no second copy under "Show both languages", and no "Translates when the reply is done" chip, since a translation did arrive.
- **Android's session list no longer stalls on ObjectId comparisons (Android).** `ObjectId.canonical` compiled its UUID regex on every call and decoded Base62 ids through BigInteger each time, and the drawer — composed even when closed — compares every open session's workspace with every workspace on each directory change, so on a real account the main thread spent about 93% of its time there: 1–4 s frames and a list fully drawn about 6.3 s after launch on a Pixel 11 Pro XL. The pattern is now compiled once, each spelling's canonical form is remembered in a bounded LRU of 4096, and each side of `same()` is canonicalized once. Measured on the same phone and account: fully drawn in about 0.7 s, 90th-percentile frame 8 ms, no frame over 700 ms, canonicalization at 0.6% of main-thread time.
- **Engine versions (managed runner, apiserver images).** Codex 0.169.1 → 0.170.0 (the managed-runner image and the apiserver image), with the npm registry checked and the platform layout (`vendor/<triple>-unknown-linux-musl`) unchanged; Antigravity CLI 1.5.10 → 1.5.11, with the linux-x64 and linux-arm64 sha512s taken from the vendor manifests and confirmed against the downloaded tarballs. Claude Code 2.1.327, OpenCode 1.19.6, Kimi Code 2.6.3 and Cursor CLI are current.
- **Also.** The rest of the range is server-internal and test and design material. The project liveness audit SQL now spells `openItemOwed`'s `EVIDENCE_UNDECIDED` branch as the TypeScript does, before `LANDING_LEASE_EXPIRED`, and `open-item-owed.pg.spec`, `landing-lease-expired.pg.spec`, `project-provenance-epoch.spec` and `landing-observation-schema.pg.spec` follow it (c85229f33b). Test-only commits raise the Apple orchestration family count to 23 for `session_move` (27dbfdc0e1), point the Apple Open items count parity at the web's sign-in waits (82cca19de3), and keep the landing-check web fixture beside the turn openers (b5fa3de2ab). Documentation commits add the "settings changed from a conversation" design and its mock board (f7eb1f971f, f1e82fe0b8), regenerate `docs/api-reference.md` after the approvals `toolName` row and after a merge (7bafd59c28, 8c1389c55b), and describe the integration contract revision 36 (c6fb435972, ad26752549). No user-facing change comes from those files.

## Upgrade impact

- **Database migrations: two, both additive and catalog-only.** `0518_integration_baseline_hold` adds two CHECK constraints to `project_integration_job_event`: `project_integration_job_event_enqueue_cause_chk` (an `ENQUEUED` event's `data->>'cause'` is null or one of `DONE`, `RETRY`, `SKIP_CHECK`, `BACKFILL`, `BEHIND_WORK`, `BASELINE_HELD`, `DECISION`, `AUTOMATIC`) and `project_integration_job_event_baseline_held_chk` (cause `BASELINE_HELD` only on a `LAND_TASK` event). `1101_integration_enqueue_skip_check` drops `project_integration_job_event_enqueue_cause_chk` and re-adds it with the same admitted causes, keeping the owner's unchecked landing generation admitted. Neither writes a row and neither is destructive: the added constraint only validates stored events, and the dropped-and-re-added constraint admits exactly what the previous one did. The apiserver applies both on boot with `prisma migrate deploy`; there is no manual step. Both are new at this tag even though `1101` sorts below `1110`, which v0.1.261-beta.45 shipped; the newest migrations before this release remain `1110` and earlier.
- **Server:** the baseline attribution and hold, the `WAITING_BASELINE` blocking reason and the shared baseline item, the scheduled-run Auto claim and the `GET /sessions?scheduled=1` folder read, the approvals `toolName` filter, the session move route and the liveness-audit wording are apiserver changes, so the apiserver must be deployed from this commit or later for them. The web client ships with the same deploy.
- **Runner:** the runner served at `/dl` is built from this tag. It carries `orbit session move` and the `session_move` MCP tool, and it records the baseline check's `treeSha`. No minimum runner version is set: a report from an older runner that omits the tree is accepted, and a runner from an older release keeps landing as it did.
- **Configuration:** no Compose file or deploy script changes in this range, and nothing must be set before or during the upgrade. The managed-runner image and the apiserver image pins do change (Codex 0.170.0, Antigravity CLI 1.5.11), so an operator who rebuilds those images gets the newer engines.
- **Clients:** macOS beta users get the DMG on the beta channel, TestFlight gets marketing version 0.1.261 with the build number as the commit count, and Android gets `android-update.json` from this tag with `versionName` 0.1.261-beta.46. Every new read is optional, so a client from this tag against a server older than this commit keeps working: the baseline card and its held rows, the Scheduled runs folder and the answered-question translation simply do not appear, while the landing-check settings are read from fields that server already carries. An older client against this server ignores the new fields. No minimum native client version above the previous release is set by this range.

## Security fixes

None in this release. No commit in this range names a security fix, an advisory or a CVE, and no dependency is added, removed or moved: `package-lock.json` is unchanged between v0.1.261-beta.45 and this tag's base, and the release commit itself changes only its package version lines. The managed-runner pins bump two agent CLIs (Codex 0.170.0, Antigravity CLI 1.5.11), which the commit records as a version refresh and not as a security fix.

## Known limitations

None known. The Auto claim covers Claude Code only — the commit says other engines keep the level's mode because their Auto has no classifier — and the landing check runs nothing when tasks land directly on main, both by design. When the baseline check times out or never produces an exit code, the job is not marked baseline-red and opens no baseline item.

## Rollback

The previous tag is v0.1.261-beta.45, commit 33ec18283f737674b40591f24884bb5f1afed2e6 (its tag object is d72bb592c3fc74e2231926e90f0a28b154612240), on origin. This range adds two catalog-only migrations that add and re-add CHECK constraints on `project_integration_job_event` and write no row, so an application-only rollback to that tag is schema-safe: the older apiserver writes only the enqueue causes the constraint admits, nothing is left to undo, no backup or restore step is needed, and no data is affected. Rolling back restores the older behaviour: scheduled runs on Claude Code again run in the access level's mode, there is no Scheduled runs folder, `orbit session move` and `session_move` are gone, no baseline check holds landings and no baseline card is drawn, an answered question redraws in the engine's English input, and a reply already in the owner's language is drawn a second time. A client from this tag against a server older than this commit keeps working, with the new cards and folders simply absent. See [Release process](../docs/release-process.md#rollback-decision-and-procedure).
