# Orbit 0.1.261-beta.109

## Summary

This release is the new web Drive page and an owner being told when a machine goes offline on its own. The web Drive page moves onto the session console's type scale, puts the folder path in the title, replaces the header's Trash and Storage buttons with an icon-only Settings gear whose menu holds a storage meter and a Trash row, and replaces the round chat button and the upload tray with one primary Agents button whose panel carries the activity view — `GET /drive/activity`, the owner's drive work grouped by session and by day — with Retry, Pause and Cancel moving onto the list's pending upload rows. The server keeps a Drive sync that ended with failures until it is handled (`POST /drive/syncs/:id/handled`) and hands it to an agent (`POST /drive/syncs/:id/fix`, `Have the agent fix it` / `Fix in a new chat`). A runner that crashes or loses its network now pushes "<machine> is offline: Orbit hasn't heard from it for 5 minutes" once it passes the 5-minute reap line, and "<machine> is back online" once it returns. All three clients learn that a merge which opened a pull request names and links it instead of reading as a failure, that a folder, project and workspace row spin while a session's row does (the separate breathing jobs mark is gone), and that a removed Default engine is hidden once its login is gone from the machine. On the runner side, a remote SubAgent can `file_fetch` a file its parent session kept, and a runner sends the heartbeat's sessions list in SessionID order.

## Upgrade impact

- **Migrations:** four, all additive. `1780_drive_move` creates a new `drive_move` table (one row per move or rename, kept 30 days) with no foreign key to the entry, folder or session, so it scans and rewrites nothing; its foreign key to `user` takes a short lock in 45 tries of 2 s. `1781_drive_activity_indexes` builds two indexes, `drive_version_owner_created_idx` and `drive_chat_change_owner_created_idx`, each `CONCURRENTLY`, without blocking writes. `1790_drive_sync_handled` adds three nullable columns to `drive_sync` (`handled_at`, `fix_session_id`, `fix_requested_at`), catalog only with no row rewritten. `1800_runner_offline_alerted_at` adds one nullable column to `runner`, catalog only. No column is dropped, no default is set, no row is backfilled, and every migration is safe to run twice.
- **Backfill:** none. `drive_move` starts empty; the three `drive_sync` columns and `runner.offline_alerted_at` are null, which means "not handled" and "no offline alert open".
- **Configuration:** five optional settings, `ORBIT_BACKUP_S3_TARGET`, `ORBIT_BACKUP_S3_ENDPOINT`, `ORBIT_BACKUP_S3_REGION`, `ORBIT_BACKUP_S3_ACCESS_KEY_ID` and `ORBIT_BACKUP_S3_SECRET_ACCESS_KEY`, passed to `pgbackup` by `docker-compose.yml`. Each is empty unless `.env` sets it, so an existing deployment mirrors its archive over rsync to `ORBIT_BACKUP_SYNC_TARGET` exactly as before; setting `ORBIT_BACKUP_S3_TARGET` moves only the archive to a bucket and leaves the files copy on rsync. Endpoint, region and either key fall back to the Drive bucket's, and the documentation asks for a key of its own that the apiserver does not hold. A deployment that sets any of them recreates `pgbackup` only. No other setting is added or changed.
- **Server and web:** the apiserver, web and link gateway all change and must be deployed together. The apiserver adds `GET /drive/activity`, `POST /drive/syncs/:id/handled` and `POST /drive/syncs/:id/fix`, keeps failed syncs past their 24 h pruning window until handled, accepts a remote SubAgent's runner on `file_fetch`'s describe and bytes routes when it names a `RUNNING` run of the session handed to it, and publishes link-heartbeat counters on `/metrics`. The web client draws the new Drive page against those routes. A beta.108 server does not answer `/drive/activity`, `/fix` or `/handled`, so the new Drive page's activity view and its fix buttons need this release's server.
- **Runners:** the runner served at `/dl` is built from this tag. `src/runner-go` changes: `file_fetch` from a remote SubAgent appends its run to the describe and bytes routes (as upload and pin already did), the `delegate` tool description tells a parent it may `file_upload` a file for a SubAgent to `file_fetch`, and the heartbeat's sessions list is sorted by SessionID so unchanged content no longer gets a new fact digest and is resent whole. The binary differs from beta.108's in those behaviors and in the version it reports.
- **Clients:** all three change. Web gets the Drive page; iOS and macOS (shared code under `src/macos`) and Android get the merge pull-request line, the spinning aggregate rows without the jobs mark, the removed-Default line and the two runner-presence push kinds. Android and Apple builds older than this one do not recognise `runner-offline` and `runner-online` (Android's allow-list rejects kinds it does not know), so they show neither push; everything else they draw they still draw against the same server.

## Security fixes

None in this release. No commit in this range names a security issue or a fix for one. The backup commit's note to give the archive bucket a key of its own, one the apiserver does not hold, is a new deployment's configuration advice and changes no existing one.

## Known limitations

- The Drive page, its Settings gear, its Agents panel and the activity view are the web client's. No file under the Apple clients' Drive sources differs in this range, so iOS, macOS and Android keep the Drive surfaces they had.
- A runner is pushed offline only if it was last heard from within the hour before the sweep; one that went silent earlier is not pushed, so an owner is not told of every machine they stopped using at once. Signed-off, draining (stop or update) and Orbit-managed runners are never pushed, and a runner held by the reaper's startup grace, a database refusal or a mass disconnection sends nothing.
- The "back online" push is sent only for a runner whose offline push was sent, and the two carry one collapse id, so a device that still shows the offline alert sees it replaced rather than a second alert.
- The offline alert fires once per silence. A runner that keeps flapping is pushed each time it crosses the reap line again.
- `drive_move` rows name an entry, folder and session by id with no foreign key, so a deletion for good or an ended session leaves the history readable by id; the owner's own deletion takes the rows with it.
- The link-heartbeat metrics are counters since the apiserver process started, and the gateway's wire-byte figure is a sampled deflate estimate over 16 KiB pieces, not an exact transfer count.

## Rollback

The previous tag is v0.1.261-beta.108 (commit `7192531a313892b845363ac2fbfa613f6442cdb0`).

Application-only rollback is **schema-safe**: all four migrations in this range are additive — a new table, two indexes and four nullable columns, with nothing dropped, no default set and no row rewritten — so a beta.108 server reads and writes the tables it already knew and ignores what it does not. No down-migration or backup/restore step is needed. Roll the server, web and gateway back together: the new web Drive page's activity view and its `Have the agent fix it` buttons call routes a beta.108 server does not have, and a beta.108 web against this release's server simply does not show them.

Rolling the runner back to beta.108's binary loses the two runner changes: a remote SubAgent's `file_fetch` is refused again (its runner is told the file is not its session's), and the heartbeat's sessions list goes back to map order, so unchanged content is resent and rewritten more often. Neither changes what the control plane accepts from a runner that stays on this release.

Rolling iOS, macOS or Android back to a beta.108 build returns those screens to reading a merge that opened a pull request as a plain failure, drops the two runner-presence pushes, and draws the jobs mark again beside a folder, project or workspace row.
