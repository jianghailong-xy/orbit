Architecture & security boundary

Local execution, visible controls, honest limits.

Orbit coordinates and supervises agents. It does not turn an operator-managed runner into a sandbox or a hosted reliability service.

How the pieces connect

Web / macOS / iOS ── REST + SSE ──▶ Control plane + PostgreSQL tasks · history · approvals queue · audit · usage ▲ │ outbound poll │ Runner + local agent runtime optional git worktree
  • The control plane owns users, workspaces, projects, tasks, sessions, approvals, runners, and history.
  • Runners make outbound connections; the control plane does not require inbound access to a runner.
  • Worktrees reduce checkout collisions. Processes still inherit the runner OS account's permissions.

Before attaching sensitive infrastructure

Important: a worktree is not a security boundary, and an agent is not guaranteed to finish correctly without review, approval, or a human merge decision.

  • Use least-privilege runner accounts and credentials; isolate hosts when the trust boundary requires it.
  • Use HTTPS before network exposure, protect unique secrets, restrict the gateway, and test off-host backups and restore.
  • This is not a hosted service, HA guarantee, zero-data-loss promise, SLA, compliance certification, or enterprise support contract.
  • Provider billing, model features, resume behavior, and usage data vary by engine; the provider's bill is authoritative.

FAQ

Know what you operate.

Short answers for the first visit. The repository docs carry configuration and troubleshooting detail.

Is Orbit hosted for me?

No. You run the control plane and PostgreSQL, decide where it is reachable, and put TLS and access controls in front of the included HTTP gateway before exposing it to a network.

Do credentials leave the runner?

Supported agent CLIs use the runner's local configuration and credentials. The control plane stores coordination metadata and transcripts; provider behavior and billing remain the provider's responsibility.

Is a worktree a security sandbox?

No. It reduces checkout collisions. Processes run as the runner OS account and can access whatever that account can access.

What if a runner or browser goes away?

The task graph and session history live in the control plane. A runner that loses heartbeats is treated as offline; exact resume behavior varies by engine and provider, so verify the behavior you need.

Which runtimes are supported?

The control plane and runner know about Claude Code, Codex, Kimi Code, and OpenCode, plus configured compatible providers. Install and authenticate the runtime on the runner and start with orbit doctor.

What should I run in production?

Orbit is pre-1.0. Pin a tagged release, review upgrade notes and the hardening guide, and treat main as a development branch rather than a supported release.

Version & roadmap

Adoption gates before bigger promises.

Roadmap direction is public; delivery dates and production guarantees are not implied.

Current release posture

  • Orbit is a pre-1.0 open-source project under active development.
  • Pin deployments to a tagged release and review upgrade notes before changing versions.
  • The latest published release receives best-effort security fixes; main is a development branch and older releases are not supported.

Direction, not dates

  • Now: repeatable clean-install evidence and one consistent version story.
  • Next: screenshot-led onboarding, operator configuration reference, public changelog, and stronger community operations.
